01项目定位与理念层

理念层与架构层已冻结；实现层进行中。

LH 要解决 AI 辅助学习的两个核心痛点：

① 上下文管理

一次学习短则数周、长则数月。学习产品的上下文观是 「一段跨越数月的、有结构的成长史」，而不是「一段对话」。

② 因材施教

「材」有双面：作为学生的用户（学习者模型）与 用户持有的学习资源（资源模型）。匹配是双向的。

明确拒绝的两条路线

  • 百万上下文力大砖飞——成本拒绝广大学习者；且 lost-in-the-middle、注意力稀释意味着质量本身随上下文规模退化。
  • 硬编码 skills 覆盖教学法——把教学法知识冻进代码，无法生长、无法被懂教学的人编辑。

服务对象与差异化判断

服务对象是初高中之外的广大自学者（备考 / 技能掌握 / 自我提升），目标高度异构。

核心判断：学习者的异构性（目的、资料、方法、节奏）是问题域的本体， 因此教学策略本身必须可插拔——这是采用 Harness 架构的根本原因。

差异化不在工具，而在编排与约束：什么时机注入什么信息、允许/禁止模型做什么、记忆怎么沉淀。

分层法律（治理模型，共四条）

法律内容状态
第一条一切皆插件：内核只负责机制，不含任何教学判断与领域逻辑已冻结
第二条事实归内核，解释归插件；派生资源必须带血缘回流已冻结
第三条第 N 层未书面冻结前，禁止讨论第 N+1 层有效但已被第四条约束
第四条（产品法律）任何时刻，必须存在一条用户可感知的完整闭环在运行。允许被冻结的层次，只能是这条闭环已经走过的层次。ADR-011 新增

第四条法律是项目的一次自我修正：它把「冻结」的度量方式从"文档想清楚"改成"闭环跑通过"，直接推翻了导致项目停滞的旧规则。

02程序形态：三方分层与插件编排

宿主 dsh 提供内核机制 → Cordis 提供插件框架 → LH 只产出契约、词汇表与插件。

宿主 · 内核机制

dsh（DeepSeek Harness）0.1.1-rc.2 · MIT · 开发者预览版

提供并视为已冻结：append-only 会话日志（dsh-session）、投影与投影持久化、 上下文拦截点 agent/pre-step、系统提示词组装、工具注册与执行管线、插件加载与可逆卸载、撤销回滚。

插件框架

Cordis（依赖注入 / 服务定位容器）

服务定位 + 声明式注入（inject）+ 生命周期 + 可逆副作用（ctx.effect）。 换来三件事：可替换性（换 LLM 实现不改消费插件）、加载顺序自动解析、测试替身免费。

LH 层

LH = 事件词汇表 + 插件 + 契约

内核自研已于 ADR-011 终止。LH 的资产是契约（LH内核契约-v0.1.md、 PLUGIN_CONTRACT.md）、自持的事件信封（data/events.jsonl）、以及 7 个插件。 判据落到文件边界：只有适配层允许 import 宿主包，领域层只 import LH 自己的类型。

用户可感知

客户端半经宿主插槽投放（shell.overlay、tool.call.toolview）， 配色只在 LH 会话内生效。壳级前端（整体切进 LH 自己的页面）已推迟（ADR-013）。

03内核契约（架构宪法要点）

LH内核契约-v0.1.md 定位：内核语法 + 不变量 + 验证方法。一切需要"判断"的事物不归它管——它们属于插件。

总原则

  • 内核拥有语法，插件拥有判断。试金石：它做的是格式约定还是内容裁决？
  • 事件溯源为基座。append-only 事件日志是唯一事实源；一切状态是日志的投影。
  • 写细读粗。写入端往细记（"没记"不可逆），读取端由投影定义粗粒度。
  • 内核连「什么值得记」都不知道。记录器是插件；发行版有立场，内核保持无知。

内核五概念（其余皆是插件）

概念一句话
节点（课程树）课程节点 = 作用域 + 自己的事件日志 + 自己的 agent + 自己的建模插件 + 自己的策略集；节点间只有父子关系。深度纪律：先冻结三层（元课程 / 课程 / 会话）。
事件统一信封：id / timestamp / schema_version / actor / type / provenance / session_ref / scope / content_ref。演进纪律：只做加法。
投影投影是插件；原始的可重放，派生的可重算。抽象梯子 L0 操作 → L1 交互 → L2 证据 → L3 断言 → L4 决策。
Handoff一等事件 HandoffInitiated：父节点 agent → 子节点 agent，带交接上下文包。导师递条子，不代课。
Agent 注册表区分持久 agent（有身份、有事件流）与一次性 function call（无身份）。默认任何插件只能读自己作用域的事件。

三个承重的领域设计

用户侧四元组：answer / ask / interpret / explain

全部是生成性行为（generative acts）——测量的是生产而非暴露，理论支撑来自 self-explanation effect、 generation effect、learning by teaching 与 ICAP 框架。证据强度阶梯：explain > interpret > ask > answer。 进度条 / 清单测量暴露，落于最低级。

反奖惩立场：生成行为停滞时把数据显示给用户（显化），而非扣分——因为奖惩挂生成行为会触发 Goodhart 定律且可被 AI 代写作弊。

L3 断言层：不做确定性画像

不做「掌握度 72%」，做带出处和置信度的断言集：

「系统认为用户在极限计算上薄弱；依据：事件 #341、#389；置信度：中。」

两个性质：可审计（每条判断回溯到证据）、可争议（用户反驳本身是极高质量的学习事件）。 信息沿树向上流动，且只以 L3 断言形式流动；原始事件永不跨作用域。

L4 策略层：策略作为数据，教学动作强制携带预测

策略 = 声明式片段（自然语言描述 + 适用条件 + 约束 + 预期产出），由模型在运行时解释执行。 懂教学不懂代码的人可编辑策略；坏策略被数据淘汰。

每个教学动作事件必须携带：目标断言、预期证据、时间窗。 策略评估 = 假设检验：动作是干预，学习者模型是测量仪器，后续事件流是观测数据。 测量仪器质量是策略评估的天花板。

验证方法：把架构从一张图变成一组会自动报警的断言

八条不变量（每条配可执行检查）——含"两次重放结果一致""上下文组装不得超预算（超预算走降级，不得截断）""每个教学动作携带预测字段""插件只能追加，不得直写投影""资料删除后派生状态无痕迹""原始事件不跨作用域""全部历史事件在新 schema 下仍可重放""事件永不迁移节点"。

五个黄金场景（端到端）——中断回归（中断 18 天后"我们继续吧"）、跨课程调度（handoff）、资料生命周期、分类器升级重放、用户争议断言。

题库数据（必须知道的三处缺陷）

工作区那份 49 题题库（考公刷题-片段阅读与逻辑判断.json）是两份资料合并的 （片段阅读 20 题 + 逻辑判断 29 题），两份题号都从 set1-q1 开始，跨资料会撞车。另有三个具体缺陷（都还没修）：

  1. 它从未经过 import_questions，所以事件流里没有它的 lh/resource/questions-imported；
  2. 它的 provenance 指向 @lh/extractor —— 这个插件不存在（是脚本直接落盘时写下的）；
  3. 它的 topics 只有 13/49 道有值（试点产物缺文件出处，只能保守匹配）。

第 3 条背后是一次代价很高的教训（ADR-021 结论八）：产物没有稳定标识，等于没产出。 试点产物只记 set1-q1 这种"资料内编号"，没有文件名、没有题干，于是按题号匹配会把片段阅读的知识点写到逻辑判断的题上—— 不报错、只是全错，而且事后无法从产物里发现。最终 49 道只有 13 道能安全写入，其余如实留在报告里。

07工程治理体系

这套东西是项目最独特的部分：它把"开发过程本身"也当成要被建模的对象。

三类记录，各司其职

载体回答什么形态与数量
docs/decisions/决定了什么、为什么、错了会怎样ADR，一条决定一份，30 份（001–030）
docs/experience/学到了什么、怎么学到的按「角色 / 日期」分文件，12 份（默认不记，滥记会稀释价值）
docs/WORKFLOW.md开发过程本身该怎么约束当前 v0.4，随实践修订（v0.1→v0.4 共 4 版，都因实践失效而改）

ADR 六项必填（验收标准：陌生读者或另一个模型能重建出合理解释）

  1. 决定了什么（一句话，可执行）
  2. 当时有哪些别的选择（至少两个，包括"什么都不做"）
  3. 为什么排除别的（真实理由，不是事后合理化）
  4. 依赖什么前提 / 假设（前提塌了，决策就要重审）
  5. 怎么知道它错了（可观察的信号）—— 最容易省也最重要：没有失效信号的决策不是决策，是信念
  6. 证据在哪（文件路径、代码行、命令输出、外部链接）

WORKFLOW v0.4：人做判断，AI 做其余

  • 人的提问权没有上限；AI 不得因为"这会增加认知负担"而不回答。
  • 一个工作单位最多一个目标；一次交付不超过 3 个待回应项（选项必须带后果与推荐，说不清后果就别端出来）。
  • 分段依据是任务的客观难度，不是墙钟时间或对话轮数；可观察但不设时间上限。
  • 破坏性操作一律白名单——只允许"明确列出要删的东西"，不允许"删掉所有不匹配的"。
  • 不阻塞记录：未决是禁止状态，"临时答案"是合法状态。

协作者模型：把"AI 对这个人的感知"写成可反驳的断言

WORKFLOW §6 与内核契约 §4.1 是同一套规矩的自我应用——LH 的学习者模型该怎么长，先在作者身上长一遍。 COLLABORATOR_MODEL.md 现有 A1–A9（能力与状态）、B1–B18（协作偏好）、C1–C22（AI 自己的错误，必须留痕供核对可靠性）、 D1–D7（低置信度猜测）、E1–E18（行为准则）。每条带出处、置信度、可推翻条件。

其中一条被反复验证、也最能说明项目气质：作者的纠正系统性地指向同一个问题—— 「这个决定该由谁拥有？」AI 的默认倾向是"系统替用户做安全选择"（工程习惯）， 作者的默认倾向是"把选择权和后果交给用户，系统负责把后果说清楚"。 这与内核契约 §3.1 的反奖惩立场是同一个原则——他的工程判断与他的教学理念是同源的。

闸门的边界（必须知道，否则会变成假的安全感）： 它们证明的是"能 import / apply 不抛错 / 声明齐全 / 副本是新的 / 路径一致"， 不能证明宿主真的会这样调度，也不能证明逻辑对。最终仍需要一次真启动。

而且：闸门自己要先对着"已知坏的状态"红一次，才算被验证过。 已有一条反直觉推论被写进契约：把"装载期抛错"改成"用的时候拒绝"会让某道闸门变绿而底层仍然是坏的—— 所以改掉一个错误行为时，要同时问"原来是谁在替我报警"，并把这个警报器补回来。

如实记下，不粉饰——这是项目自己的纪律（"没验证的写未验证，不要写成规则"）。

类别内容
