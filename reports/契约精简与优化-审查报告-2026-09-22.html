1.2 审查结论：契约为什么在限制开发

① 机器能查的写成了人肉清单§七 28 条里 12 条已被 check-* 脚本全/部分覆盖，文档却不区分“机器把守/人工把守”，每次开发都要通读 571 行逐条人肉对照——“契约限制 agent”的最大来源。处置：P2 逐条标注。
② 一条规则散布 3–5 处且已漂移“破坏性白名单”写在 WORKFLOW 规则 4、COLLABORATOR_MODEL E-4/C10、PLUGIN_CONTRACT 严重级三处；修订记录叫它“规则 5”、正文是“规则 4”；COLLABORATOR 头部引用“§2 规则 5”实际指规则 6。处置：合并（W8/W9）+ 权威出处声明（R6）。
③ 两条字面禁令在伤害开发“第 N 层未冻结禁止讨论第 N+1 层”+“新窗口只允许从 §5 取题（上限 10 条）”直接限制探索与提问，且项目自己已认定它们有害——COLLABORATOR_MODEL A5 把“项目停滞”归因于这两条。处置：R1/R4 改正向。
④ 过期内容与索引脱节HANDOFF 是一次性事故交接；ARCHITECTURE §6 索引停在 ADR-011（实际已有 034）；LH内核契约 §9 待决清单两项已被 ADR 决掉还挂着“待决”。处置：删 / R5 / K2–K4。

寄生而不 fork（ADR-001/011/023）LH 全部能力以插件形态挂进 dsh；版本控制只覆盖自己的目录。这决定了 PLUGIN_CONTRACT §一/§二的 schema 只能是“宿主注册 schema 的子集用法”，不能发明字段。

env 惰性（§四）环境变量在 apply() 里惰性求值，保证 profile 移植/隔离开发（ADR-031）时不固化错值。

5.5 对协作与治理的指导影响

  • 第四条产品法律（ADR-011）是整个体系的“准绳”：任何时刻必须存在用户可感知的完整闭环——它直接推导出“文档不得先于闭环扩张”（R1），也是本次删两条禁令的依据：限制讨论顺序并不会加速闭环，A5 断言已实证过。
  • WORKFLOW §2 六规则 + §4 七义务约束 agent 的每一次交付：单一上下文、≤3 待回应项、可观察不设时限、破坏性白名单、不阻塞记录、反馈接收——本次合并后它们与 §7 行为准则成为同一份文档，不再互相漂移。
  • 协作者模型（§7）是治理层的“自省装置”：断言带出处/置信度/可推翻（内核契约 §4.1 语法），C 组错误台账强制 AI 留痕——它不是评价，是协作建模，且作者本人可随时推翻。
  • 事件溯源式留痕贯穿文档体系：代码有 events.jsonl，文档有 ADR + 修订记录 + 经验台账——任何一条现行规则都能回答“它是被哪次事故/决定推出来的”（出处可追溯），这就是删掉死条款、改正向表述时不会丢失历史的保证。
