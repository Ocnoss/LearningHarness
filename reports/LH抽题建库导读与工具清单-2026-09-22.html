三条贯穿全文的设计红线（整合时不可破坏）
  • 答案不进主会话：录题走 subagent（import_questions_from_source），主会话只回收计数与样例 id；题干与答案留在子 agent 侧。实测反例：一次录 20 题产生 106 次工具调用、答案被念进对话——那正是要根治的形态。
  • 模型的答案绝不进题库 answer（ADR-021 决定 3）：answer 一律来自解析册【参考答案】的规则抽取或子 agent 对解析页的转录，answer 为空宁可不入库（宁空不编）。
  • 结构上不可能作弊：取题路径（get_questions / /bank）只给题面（toPresentableQuestion 显式剥答案）；作答历史只在判分后随 submit_answer 返回；模型代答与人作答分开计数（ADR-018 决定 6）。整合时若合并接口，这三条必须保持"数据不在那条路上"的结构，而不是靠提示词。

§1 功能域一：题目提取入库

入库前的路有两条：规则侧脚本链（可复现、零成本、走 build_bank.py）与模型侧（extract-questions.mjs 离线流水线，或 import_questions_from_source 在线 subagent）。两者最终都汇入同一个 importQuestions()（校验→派 id→合并→落盘→记资源事件），入库收口只有一处。

1.1 规则侧脚本链

scripts/align_by_question.py （555 行，子命令 plan / match）

  • 职责：把题本页与解析页按题对齐（对齐单位是"题"不是"页"），产出对齐报告（每题：套号、题号、题本页、解析定位 located_at、题干全文、选项）。
  • 关键函数：locate_by_stem（滑动窗口子序列匹配题干，相似度阈值 0.86）；单调性检查（解析定位必须随题号单调推进）；<0.85 的进 LLM 复核通道。
  • 设计理由：两本书分页不同，页级对应必然错；按题干文字在解析全文里找锚点才稳定。
  • 读码注意：RE_SET 的"套"字必须可选——写成必匹配会把没有"套"字标记的整套题静默跳过；噪声行（页眉页脚）跳过但延续当前块，页眉可能插在题中间。

scripts/extract_answers.py （383 行）

  • 职责：从解析册里规则抽取【参考答案】+ 讲解 + 选项评注，每条带自校验与 confidence。
  • 关键函数：load_full_text(ocr_dir)（按页序拼全文保留页界）；strip_promo(text)（切推广文字：公考最新资料/微信XXX 等，逐行截断）；parse_option_annotations(text)（抓 A. …（评注））；extract_one(block, answer_letter, options, annots)（核心：三重校验+置信度）；main（--report --ocr --out --source-root）。
  • 三重自校验：①选项标注法（被指为正确的选项不该带"有误/无中生有"等负面词 NEGATIVE 表）②讲解提及法（"对应C选项，当选"等正则印证）③完整性（每题恰好一个【参考答案】且落在本题范围内，否则报出不猜）。
  • confidence 只用两个可靠信号：answer_in_options + explanation_mentions_answer。选项评注刻意不参与判断（双栏页边批注被 OCR 串行，逐行挂不准——measure_loose_annotations.py 实测 20 题只捞对 3 题），评注照实保存但只当证据。
  • 读码注意（每个都是实测踩过的）：①RE_EXPLAIN 曾是 [^\n【]*——捕获类遇换行即停，49 题里 46 题解析被截成 26 字残句，且 analysis_available 因"非空"照常显示（不完整比没有更坏），现已改为取到下个标记或块末；②页脚会把答案与所属题隔开——本题范围找不到【参考答案】时向后探 1200 字（窗紧，防捞下一题答案）；③选项评注只在【参考答案】之后取——块范围 [本题解析起点, 下一题解析起点) 会把下一题的选项行包进来（实测 Q9 的评注来自 Q10）；④extract_one 的 annots 必须由调用方传入，在函数内重新解析会把调用方的修正覆盖掉。
  • 输出：setNN-extracted.json——items[{set, no, answer:[字母], confidence, analysis, analysis_is_placeholder, option_notes, wrong_option_notes, question_type, …checks}]。讲解不做"干净散文"承诺：正文常只有"文段分析见批注。"8 字指针，此时 analysis_is_placeholder=true，由 build_bank.py 转成 analysis_kind 如实标注。

scripts/build_bank.py （222 行）

  • 职责：规则侧单侧建库——把对齐报告（题本侧 stem/options）与抽取结果（解析侧 answer/analysis/question_type/confidence）合成题库 JSON。
  • 字段分工（ADR-020 决定 4）：stem/options 题本取；answer/analysis/question_type/confidence 解析取。
  • 关键函数：derive_id（与 question.js 的 deriveQuestionId 同算法，离线校验用，改一处必须同步另一处）；clean_analysis（不假装完整：占位解析留空 + provenance.analysis_kind 标注来路与质量）。
  • 三产出：题库 JSON + .option-notes.json（选项评注单独放，不塞进题面）+ .extract-report.json（抽取质量报告）。

1.2 模型侧流水线

scripts/extract-questions.mjs （599 行，plan / run / verify 三模式）

  • 职责：题干+选项的模型抽取流水线。run 模式真调 mimo-v2.5-pro（env XIAOMI_TOKEN_PLAN_AMS_API_KEY）。
  • 关键函数：scanPageAnchors + planWindows（切窗三层：分组锚 → 题数预算 14 → 跨页回退）；buildWindowPrompt（单窗提示词）；normalizeForCompare + lcsLength + verifyExtraction（三道独立校验、不合成总分：文本保真 LCS ｜ 边界可信题号对账 ｜ 数量对账防幻觉——目录页曾幻觉出 15 道幽灵题）；crossCheck（重叠窗口=免费独立复核，键 (group, number)）。
  • 读码注意：词表从插件 import（canonicalTopic 等），不复制——插件是词表唯一实现；导出 RE_GROUP/RE_QUESTION_NO 供下游复用。

scripts/assemble-bank.mjs （350 行）

  • 职责：模型侧题干列表 + 规则侧答案列表 → 题库 JSON（两侧合流的收口）。
  • 用法：node scripts/assemble-bank.mjs --questions … --answers …；arg() 同时支持 --k=v 与 --k v 两种写法。
  • 读码注意：①解析侧字段名是 set/no（不是 set_number/question_no）；②出处回填必须在 normalizeQuestion 之后按 id 回填（normalize 只搬认识字段，先填会被丢——2026-09-20 修复）；③复用插件的 normalizeQuestionList / buildBank / fingerprintStem / canonicalTopic；④renderAnalysis 含【各选项评注】拼装。

scripts/install-bank.mjs （118 行）

  • 职责：把题库三件套（题库 JSON + .option-notes.json + .extract-report.json）复制进 <workspace>/lh-questions/。
  • 装后验证：用插件自己的 loadBank / listQuestionBanks / getQuestions / getPracticeStats 跑一遍 + 答案泄漏检查（确认题面路径拿不到 answer），并产 .预览.md。

§2 功能域二：题库内查询检索整理对应

纯函数层三模块构成"题目对象"的全部语义：question.js 定义一道题是什么、bank.js 定义题库怎么落盘、topics.js 定义标签词表。查询工具都只是这三者之上的薄壳。

plugins/lh-question-bank/question.js （354 行，题目对象层）

  • 常量：QUESTION_KINDS = ['single_choice','multiple_choice','fill_blank','other']；BANK_SCHEMA_VERSION = 1。
  • id 派生（唯一一处）：deriveQuestionId({sourceRoot, sourceFile, number, stem}) = 'q-' + sha256(sourceRoot|sourceFile|number|fingerprintStem(stem).slice(0,40)).hex.slice(0,12)；fingerprintStem 去空白+全角标点映射半角。题号不是身份，"套号+套内题号"才是（每套题号从 1 重启）——number 形如 set1-q7（assemble-bank 侧还有 ${group}-q${number} 全局唯一化）。键（source 等输入）退化时 id 变化是静默的：同题会当新题重复入库而不是替换。
  • normalizeAnswer(raw, kind)：显式分隔符才拆；连写 'AC' 只对选择题拆（填空可能是答案字符串 "AC"）。
  • normalizeQuestion({raw, origin, provenance})：报错不猜（缺题干/答案无法解析/选项标签越界/单选多答案都 throw）；只搬认识字段（多余字段静默丢弃——出处等要后补的字段必须normalize 之后按 id 回填）；topics 过 normalizeTopics，认不出的进 unmapped_topics 如实带。
  • normalizeQuestionList({rawList, origin, provenance}) → {questions, errors[{index,message}], unmappedTopics}：逐题收集错误不遇错即停；number 取 rawList[i]?.number ?? origin?.number ?? i+1。
  • buildBank({questions, meta})：同 id 去重保 first + duplicate_ids 如实报告；validateBank(bank) → {ok, errors}；pickQuestions({bank, ids})。

plugins/lh-question-bank/bank.js （175 行，题库落盘层）

  • BANK_DIR_NAME = 'lh-questions'；safeBankName(name)（Windows 非法字符替换、结尾点/空格修剪、60 字上限）；resolveBankPath({workspaceRoot, bankName})。
  • loadBank(path) → {bank, errors}：去 BOM（PowerShell 写文件带 BOM 的坑）；文件不存在不算错误；校验不过仍交出内容+errors（调用方决定怎么处置）。
  • saveBank({path, bank})：tmp + rename 原子写（防写一半被读走）。
  • mergeIntoBank({existing, questions, meta}) → {bank, added, replaced}：同 id 覆盖=修正语义，replaced 如实报。
  • extractRawQuestions(input)：容忍数组 / {questions} / 单对象三种输入形态。

plugins/lh-question-bank/topics.js （279 行，两轴封闭词表）

  • 词表：QUESTION_TYPES 17 项（题型轴）× DOMAINS 5 项（领域轴）。插件是词表唯一实现，脚本一律从插件 import（防漂移）。
  • canonicalizeLabel / splitTopicLabels / canonicalTopic(raw)：归一化（"主旨概括"→"中心理解"）；normalizeTopics(raw) → {topics, unmapped}——unmapped 如实回报不吞；describeTopicVocabulary()（工具描述文案从实现生成）；validateVocabulary()（自检）。
  • 两轴之外的说法会被归一化认领或如实标"没有匹配的题"——不猜。

2.1 查询检索工具

⑥ list_question_banks （index.js:1387）

参数：（无） 输出：bank_count, banks[{ name, ok, title, question_count, source_root:string|null, generated_at:string|null, errors[] }]
  • 扫工作区 lh-questions/ 全部题库并 validateBank；ok=false 表示题库文件坏了需要修。

⑦ get_questions （index.js:1451，取题·无答案）

参数：bank_name* ｜ count（默认 1）｜ order（sequential/random/unseen/attempted/missed） ｜ topic（词表写法，同 start_practice）｜ ids（给了就忽略 order）｜ exclude_ids 输出：bank_name, total_in_bank, question_count, order（实际生效，可能退化）, note（策略如何被调整）, questions[questionShape]

⑨ get_solution （index.js:1724，只读题解）

参数：bank_name* ｜ ids* 输出：bank_name, solutions:[{ id, number(如 set1-q7|null), stem, options, answer, accept, analysis, analysis_kind }], missing[]

④ verify_pairing 见 §1.3——它是"整理对应"语义在入库侧的把关件；入库后的对应关系体现在 question.source.{resource_ref, path, number, page} 与 get_solution 的 number（学习者在纸质资料上找得到的编号）。

§4 功能域四：整理做题历史

事件体系的分界（ADR-009/017）：题目=资源（lh/resource/questions-imported + 题库文件），作答=事件（lh/user/attempt + events.jsonl）。作答不可重来、不可取代，所以进事件日志；题目可重排版重导，所以是产物。

plugins/lh-question-bank/attempt.js （224 行，作答事件与判分）

  • 常量：ATTEMPT_EVENT_TYPE = 'lh/user/attempt'；ATTEMPT_SOURCES = ['human','llm','imported']（人与模型的作答必须可区分——否则"模型答对了"会被算成"我会了"）；ATTEMPT_SCHEMA_VERSION = 1。
  • judgeAttempt({question, response}) → true|false|null：三值——null=无法判定，不默认算错（混进 false 会让正确率凭空变低且在数据里看不出来）。选择题=选项集合相等（多选顺序无关）；填空题=fold 空白+小写后匹配 answer∪accept，不做同义替换（"四十二"与"42"是两回事，靠 accept 显式声明）。
  • buildAttempt({question, response, source='human', correct, durationMs, sessionRef, seq}) → 可直接交 lhEvents.append 的 data{question_id, response, correct, source, duration_ms, context:{session_ref, seq}}。context 是"现在不记以后没有"字段（写细读粗，契约 §1.3）；response 原样保留（归一化留给判分与统计）。
  • extractAttempts(events) → {attempts, malformed}：malformed 如实报告不丢弃。
  • summarizeAttempts({attempts, source})：accuracy 分母只算判得了的（judged=0 时是 null 不是 0——"没数据"≠"全错"）；last_at/last_response/last_correct 三个字段必须在同一 if 里更新（分开写迟早漂移："上次答了 X"配另一个时间，且没人会发现）。

plugins/lh-event-store/index.js （186 行，inject=['sessions']）

  • 提供事件存储（@lh/event-store/store 的 lhEvents：append / all）与路径（@lh/event-store/paths：events.jsonl 定位）。它自己不写事件（判断归记录器，ADR-006）。
  • 投影 key 'lhEvents' 原样返回同一引用（Object.is 变更门，防重复触发）；自检失败不抛错但跳过投影注册。

§7 整合接缝速览

面向"agent 端到端处理、数据流动顺畅"的集约整合，现状里已经收口与仍靠人/脚本串的分界如下：

已收口（整合时保留这些单点）
  • 入库收口：importQuestions() 一处（校验→派 id→合并→原子写→资源事件）
  • id 派生：deriveQuestionId 一处（build_bank.py 的 derive_id 是镜像，需同步）
  • 判分口径：judgeAttempt 一处（对话/面板两路共用）
  • 去答案：toPresentableQuestion 一处（"是职责不是调用方的自觉"）
  • 词表：topics.js / style.js 各一处，工具描述从实现生成
  • 校验策略：忽略 + 如实回报 ignored，一处 per 域
仍靠人/脚本串（整合的着力点）
  • 离线链 7 个脚本要人按序敲命令（ocr→align→extract_answers→build_bank / extract-questions→assemble-bank→install）——无一个总入口
  • 规则侧与模型侧的选择（哪份资料走哪条链）是人判断
  • extract-questions.mjs 的 run/verify 与 import_questions_from_source 的 subagent 抽取是两套并行的模型侧，产物形状不完全同构
  • 答案侧字段名两套（规则链 set/no ↔ question.js setN-qM）靠 assemble-bank 翻译
  • build_bank.py 的 derive_id 是 question.js 的手工镜像（改一处要人记得同步）
  • probe_spawn 是临时探针（验完即删），占着工具位
  • 作答历史的"导入"（ATTEMPT_SOURCES='imported'）只有字段，没有导入工具
  • verify_pairing 与 import_questions_from_source 各自 spawn 子 agent、各自一套 JSON 解析重试（重复的宿主交互骨架）
整合时的三条不可破坏约束（再强调一次）
①答案不进主会话（子 agent 隔离）②模型答案不进 answer、answer 空不入库 ③取题路径结构性无答案、history 只在判分后、human/llm 分账——这三条是结构不是提示词，任何接口合并方案都要保持"数据不在那条路上"。
