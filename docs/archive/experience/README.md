# 经验记录（docs/experience/）

> 记录**开发过程中学到的东西**。按「角色 / 日期」分文件，文件内一条经验一个模板。
>
> ## 和 `decisions/` 的分工
> | | 回答什么 | 形态 |
> |---|---|---|
> | `decisions/`（ADR） | 决定了什么、为什么、错了会怎样 | 一条决定一份 |
> | `experience/`（本目录） | 学到了什么、怎么学到的 | 一条经验一节 |
>
> 一条经验如果升级为**硬性约束** → 写进 `docs/WORKFLOW.md`；升级为**架构判断** → 写进 `docs/decisions/`。

## 目录约定

```
docs/experience/<角色>/<YYYY-MM-DD-HHmm>-<主题>.md
```

- **角色**：`插件开发者` / `项目作者` / `决策记录者` / `学习者建模者`……
  同一个 AI 在不同任务里可以换角色，换角色就换目录。
- **时间戳**：`YYYY-MM-DD-HHmm`。**每次记录新文件**，不追加旧文件——
  追加会修改已有文件的 mtime，导致"文件是否变化"这个信号失真（吃过一次亏）。
- **主题**：简短 slug，便于排序查找。

## 什么值得记（最容易被违反的一条）

**默认不记。** 记录是稀缺资源，滥记会稀释它的价值——翻十条才能找到一条有用的，等于没有。

够得上记录的，应当至少满足其一：

| 门槛 | 说明 |
|---|---|
| **会复发** | 换个任务、换个插件、换个人，同样会踩。 |
| **反直觉** | 结论与"照文档/照直觉该有的样子"相反。 |
| **代价高** | 不记下来，下次排查要重付同样的时间。 |

**明确不记**（这些留在这轮对话或 commit 里就够了）：

- 一次性的手感问题、拼写/编码/时区这类环境小坑，重跑一次未必再犯；
- 某个 API 的具体签名——查类型定义比翻经验快；
- 已经写进代码注释或工具脚本注释的易错点（**注释比文档更容易被看到**）；
- 同一轮排查的中间过程：只记最后那条站得住的结论。

**写在代码旁边 > 写进经验文档。** 能靠注释、类型、断言、脚本自检解决的，就不要记成经验——
经验只留给"没有合适位置安放"的东西。

## 谁来写

**不要求人手动写。** 主要流程是：人给出反馈 → AI 按模板填写并归档。
后续可以把这件事交给便宜模型（例如配置好的 MiMo）针对 AI 的输出内容自动记录——
那本身就是一个"插件"，见 `docs/decisions/` 里关于插件形态的记录。

人也可以直接写，或被要求确认某条记录。但**记录不是人的义务**。

**AI 在主动记录前应先自问**："这条删掉，下次会付出多大代价？"答不上来就不写。
人被问烦了、或要求"少记点"，是**最高优先级的接口变更**——立即照做，不要论证。

## 填写方式：模板 - 填写

每条经验固定五个维度，缺项就写"（暂无）"，不要为了完整而编：

| 维度 | 回答什么 |
|---|---|
| **场景** | 当时在做什么、看到了什么现象 |
| **决策** | 当时做了什么选择（包括"什么都不做"） |
| **根因** | 为什么会这样（查证到的，不是猜的） |
| **解决方案** | 实际怎么处理的；没解决就写"未解决" |
| **启示** | 下次怎么做更省事 |

模板见 `TEMPLATE.md`。
