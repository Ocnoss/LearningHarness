## E1. 版本控制：难点不在体积，在边界

- **场景**：作者问 *"dsh 是起在用户文件夹的，一部分内核文件在 `.dsh` 里，
  但 LH 的另一部分部件在工作区里，这种情况要怎么版本控制？"*
  而 `~/.dsh` 给人的直觉是"又大又杂、不好管"。
- **决策**：**先量再答**，不按直觉设计。
  量完发现：该入库的配置只有 **14 个文件、约 12 KB**
  （`.agent-presets/` + 三个 profile 的 patch/package.json/lock）。
  其余全是状态或第三方：`attachments` 144MB、`sessions` 24MB、
  `profiles/*/node_modules` 6MB、`.credentials.yaml`（**绝不入库**）。
  → 一个仓库在 `D:\LearningHarnessv0.1`，`.dsh` 配置以**单向快照**纳入 `dsh-config/`。
- **根因**：直觉把"目录大"等同于"难管"，但版本控制关心的是**哪些是源码**，
  不是体积。而 `.dsh` 里 99.9% 的体积是机器状态与第三方。
- **解决方案**：ADR-023。**并且刻意用「复制 + 显式同步脚本」而不是符号链接**——
  软链看似优雅（改一处两处同步），但它有一个致命失败模式：
  若 `~/.dsh` 被删或重建，链接目标就没了，**dsh 直接起不来**。
  那正是这两天一直在防的事故类型。**优雅输给了"不可能因此起不来"。**
- **启示**：**"这件事复杂吗"要量过再答。** 而且当"优雅方案"和"不可能因此起不来"
  冲突时，**选后者**——尤其在一个刚被启动失败烧过两天的项目里。
  附带一条必须说出的代价：`sessions/` 不入库 = **对话历史没有备份**，
  所以决策必须写进 `docs/`（这正是 ADR 存在的理由之一）。

## E2. 保护机制不能依赖被保护对象能运行

- **场景**：作者要"哨兵回退"（某行让插件树加载失败时自动禁掉那一行），
  并且要求 *"必须要保证**哨兵回退本身也是插件化但是不会出问题的**"*。
- **决策**：**不接受"插件化"这一半**，改成**进程之外的启动包装器**。
- **根因**：一条硬约束——
  哨兵的职责是"插件树加载失败时把那一行禁掉"，
  **而插件树加载失败时，树里的任何东西都没有运行，包括哨兵插件自己。**
  我把它写成一句话记在这里：
  **一个和病人绑在一起的心脏除颤器，在病人心脏停跳时也一起停了。**
  而"不会自己出问题"这件事，恰恰**因为它在进程之外才成立**：
  它不是插件 → 不进插件树 → 它坏了 `npx dsh web` 仍然可用，**退路一直在**。
- **解决方案**：ADR-023 决定 3。形态：预检（跑那五道闸门，都是离线的）→
  **预检红时不自动改配置，只报告**；绿则启动；启动后 30 秒内异常退出才标记可疑行、
  禁用、重试一次。改配置只做一件事（给一行加 `disabled: true`），且改前先复制原文件。
- **启示**：**凡"救 X"的东西，先问一句：X 不运行时，它还在吗？**
  我倾向插件化（一致、可插拔），但**偏好不能覆盖这条物理事实**。
  这条可以推广到任何"自愈机制"的设计。

## E3. 把 schema 变成前置契约，而不是事后 debug 的线索

- **场景**：作者诊断：*"之前遇到的一些插件问题的重要原因一部分在于没有严格遵循
  cordis 内核的插件注册 schema，这个 schema 是必须提到每个插件开发任务中的，
  无论是开始写之前还是 review 的时候，**出现了问题再找这个 schema 来 debug 效率太低了**。"*
- **决策**：写一份**权威契约** `docs/PLUGIN_CONTRACT.md`
  + 一个**可执行的 review**：`scripts/check-plugin-contract.mjs`。
- **根因**：三次"dsh 起不来"，我每一次都是**从报错反推规则**。
  而规则一直存在、而且是**封闭的**（工具 schema 只支持 8 个关键字；
  插槽注册有必填字段；inject 有两处同名但语义不同的声明）。
  它们不是"查不到的隐蔽知识"，是**没被当成前置知识**。
- **解决方案**：契约里每条规则标来源——`[实测]`（带报错原文）/ `[宿主源码]`（带包名与文件）/
  `[闸门]`（带脚本名），**没验证的写"未验证"**并单列一节。
  写的过程本身发现了两件我原先不知道的事：
  ① **`ctx.slots.inject(key, cb)`** 是宿主惯用法（等插槽声明存在再注册，比直接 register 稳）；
  ② **`exports.inject`（服务名）与 `register()` 参数里的 `inject` 是两个不同的东西**——
  后者的语义**我没查明**，所以契约里写"不要照抄"，而不是猜一个解释填进去。
- **启示**：**一份把猜测当规则的契约，比没有契约更危险——因为它会让人停止怀疑。**
  所以"未验证"必须是一等公民，和"已验证"并列写在同一份文件里。
  这条也直接服务于 `lh-plugin-develop`：契约就是它要注入给写插件的 agent 的**前置知识**。

## 与之配套的一条硬教训（已写进 `check-plugin-contract.mjs` 的注释，此处只留结论）

我写完检查器后它报"7 个插件全绿"。按昨天的规矩，我造了一个**故意违规的夹具**去验它——
**它漏了一条**（list 插槽缺 `id` 静默通过）。

根因：检查器为避免"注释里的 `ctx.x` 被当成访问"，
用状态机把**注释和字符串一起抹成空格**；而**插槽名就写在字符串里**，
净化后变成一串空格，那条分支永远走不到。

**结论**：**为消掉误报而做的净化，可能同时消掉真信号。**
检查器有两类失败——误报（噪声，让人忽略它）与**漏报（静默，让人相信它）**。
我一直在防前者，而这次是后者，且它伪装成"全绿"。
修法是保留**两个净化版本**（抹字符串的用于扫 `ctx` 访问，保留字符串的用于读插槽名），
用途分开、不混用。修完后夹具 7/7 被抓到，真实插件仍全绿。
