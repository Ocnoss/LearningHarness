# 插件开发者经验 · 2026-09-15

> 角色：插件开发者（AI）。任务：在 dsh 上挂载第一个 LH 插件，验证"寄生"路线是否可行。
> 阶段：阶段 1（发现与合成）、阶段 2（挂载与激活）、阶段 3（让插件的作用出现在对话里）。
>
> **收录门槛**：默认不记。够得上的至少满足其一——**会复发 / 反直觉 / 代价高**。
> 一次性的环境小坑、查类型定义就能得到的签名、已写进代码注释的易错点，都不收录。
> 同一天一个文件，条目前后顺序即发生顺序。

## E1. 脱离宿主的行为复现会产生假阳性

- **场景**：想不启动 dsh 就验证 preset 能否挂载，手工用 `new Context()` + `ctx.plugin(Loader)` 搭最小环境，调用宿主的 `mountPreset()`。
- **决策**：把它当作阶段 2 的主要验证手段。
- **根因**：脱离 dsh 时 `ctx.loader` 不存在（`cordis-plugin-loader` 导出的 `Loader` 不是可直接 `ctx.plugin()` 的插件形态）。于是 `mountPreset` 的行可用性审计检查的是残缺环境——里面根本没有行，答案是"没有不可用的行"，于是通过。**"成功"是假象。**
- **解决方案**：分两级验证——发现层用宿主导出的纯函数 `discoverPresets()`（可靠，一次同时验证发现、id 合法性、trust、YAML 方言、行形状）；挂载与激活**在真实应用里发起会话**验证。
- **启示**：**用一个弱化版环境验证，得到的成功不能外推**——弱化掉的往往正是被测的那一环。想省掉"跑真实应用"，必须先证明替代环境真的建立了同样的机制。

## E2. 两个"本来该能用"的能力实测不成立

（合并两条同类经验：根因都是"文档描述的能力 ≠ 当前部署里生效的能力"。）

### 一、preset 行里的裸包名解析不到

- **场景**：插件里 `import { z } from 'zod'`，真实会话中 `ERR_MODULE_NOT_FOUND`。
- **决策**：先写"动态 import + 降级 schema"兜住。**这个决策本身是错的**，见 E3。
- **根因**：宿主给 preset 行设"裸包名解析基址"是**有条件的**（`dsh-agent-presets/lib/index.js:708` `if (agentCtx.baseUrl !== void 0)`），实测条件**未成立**。于是裸包名退回 Node 普通解析，从 `.dsh\.agent-presets\lh\plugins\lh-hello\` 向上走，永远到不了宿主。第一方插件不受影响，因为它们住在宿主自己的 `node_modules` 里。
- **解决方案**：插件源码放到**有 `node_modules` 的目录**（工作区），在工作区 `npm install zod`，preset 行用绝对路径指向它。实测 `zod 可用 = true`。

### 二、绝对路径：两处机制不同，不能互相套用

- **场景**：先记录"绝对 Windows 路径不可用（`ERR_UNSUPPORTED_ESM_URL_SCHEME`）"，后来发现 preset 行里可用。
- **根因**：宿主有**两处**不同的 import 实现：

  | 加载位置 | 实现 | 绝对路径 |
  |---|---|---|
  | profile 的 `cordis.patch.yml` | `boot()` **不传** `bareModuleBaseUrl`，做 `isAbsolute → pathToFileURL` 转换的 `Include` 子类**未安装** | ✗ 失败 |
  | preset 行 | `dsh-agent-presets` 的 `PresetTree.import` 做了该转换（`lib/index.js:496`） | ✓ 成功 |

  两处的**相对路径**都以"组合文件所在目录"为基。
- **解决方案**：记录里按"加载路径"分开写并注明出处行号，不给笼统结论。
- **启示**：判断某个 specifier 能不能用时，**先确定它在哪条加载路径上**；"文档说了"不等于"生效了"——`PresetTree.import` 的注释描述了裸包名解析，但那段代码在 `base === undefined` 的分支里，实际没走到。

## E3. 为"万一依赖加载失败"写半成品替身：把一个清晰的错误换成一堆难查的故障

- **场景**：E2 的包解析失败后，写了一个只含 `safeParse` 的"最小降级实现"兜底。副作用：该会话**历史加载失败**，报 `registration.def.wire.viewSchema.parse is not a function`。
- **决策**：当时选了"降级可用"而不是"明确失败"。
- **根因**：投影的 `stateSchema` / `viewSchema` 必须是**真的 zod schema**——宿主读投影快照时调用 `wire.viewSchema.parse(...)`，替身没有 `parse`。错误因此从"注册处"（清晰、带插件名）被搬到"读取期"（远离注册处、只表现为某个会话打不开），而且已被写进投影缓存，**污染了 4 个会话**。
- **解决方案**：① 删掉降级路径，直接用真 zod；② 加注册前自检 `assertSchemaUsable()`，不合格就在注册处抛；③ 写 `scripts/projcache.mjs` 从投影缓存摘除坏单元（自动备份）；④ 记入代码注释。
- **启示**：**依赖加载失败就应该让它失败得清清楚楚。** 判据：替身如果**不具备真实对象的完整契约**，它就不是降级方案，而是新的故障源。

## E4. 修复"已被持久化的坏数据"：必须先停进程

- **场景**：摘除投影缓存里的坏单元后复核"无残留 ✓"；几分钟后再查，**4 处又回来了**。
- **决策**：先查缓存文件 mtime，而不是重跑摘除。
- **根因**：缓存 mtime **晚于**摘除动作——是**运行中的 dsh 写回去的**。内存里那份坏注册还在，任何会话活动（`turn/end`、会话销毁）都会用它重新持久化。同时 web profile 的 `hmr` 行是 `disabled: true`，**插件代码改动在这台进程里根本不生效**。
- **解决方案**：固化顺序 **停 dsh → 清缓存 → 重启**，写成 `scripts/projcache.mjs`（`inspect` 只读查看，`purge <key>` 摘除并备份）。
- **启示**：**改"落盘的状态"之前，先确认没有活着的写入者**，否则会得到"修好了又坏"的假象并误判修法无效。判断依据：**文件 mtime 是否晚于你的操作**。

## E5. 把"没看到"当成"没发生"——一次错误的否定推断

- **场景**：加了"注入系统提示词段"的改动（PHASE4）后让作者测试，模型仍去读日志、没复述标记；我查证据文件**不存在**，推断"连 apply() 都没跑"，开始怀疑 `inject: ['systemPrompt']` 无法解析。
- **决策**：差点据此回退 `inject` 声明——那会掩盖真正的原因。
- **根因**：**dsh 进程启动于 16:55:20，改动在 16:58:07/16:58:14**，进程跑的是旧代码；而旧版的证据文件在更早那次会话里已经写过，**同一进程内一个会话只写一次、不会重复创建**。我把一个**缺少信息**的观测当成了**否定证据**。
- **解决方案**：写 `scripts/check-restart.mjs` 比对进程启动时间与源码 mtime，直接给出"是否已加载最新代码"的结论；每次改动换一个可 grep 的版本标记；测试前清空证据文件，让"文件存在"重新有意义。
- **启示**：**判定一个观测是否定证据之前，先确认它在该条件下一定会产生可辨识的痕迹。** 旁路日志尤其容易犯这个错——它有"写过就不再写"的特性。

## E6. 验证方式的两级：旁路证据 vs 受影响通道

- **场景**：前几轮一直用"插件写日志文件"验证，它成功证明了"插件被加载并激活"，但证明不了"**会话真的运行在这个 preset 上**"——旁路日志影响不到对话。
- **决策**：改为注册 `ctx.systemPrompt.section()`，让标记出现在**模型每轮都能看到的通道**里，再由模型复述。
- **根因**：两类证据的能力边界不同——**旁路证据**（日志文件）能证明"东西存在/被加载"，成本低、可靠，但与系统行为**无因果连接**；**受影响通道里的证据**（提示词、工具、界面）能证明"东西起了作用"，因为它必须经过完整的组装链路才能出现。
- **解决方案**：两级都用——旁路日志作加载证据，提示词段作生效证据；并把后者设计成**可被人一眼判定**的形式（模型复述标记）。
- **启示**：**要证明某个部件"起了作用"，证据必须出现在它影响的通道里。** 这条对 LH 本身也成立：**学习者的证据如果只写在后台日志里，就证明不了学习真的发生了**——证据的通道选择本身就是建模的一部分。而那个提示词段不只是测试手段，它同时是 context compiler 的挂载点。
