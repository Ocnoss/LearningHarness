## E12. 并发 boot + "别的包声明的插槽" = 启动竞态（**闸门已补**）

### 现场

重启 dsh 后起不来：

```
Failed to load plugins
  @lh/practice
  failed to apply loader entry 5a6c689b (@lh/practice):
  slot "shell.overlay" is not declared (a parent entry's children table must declare it)
```

### 根因（结论由协作方查证，与我的复核一致）

1. 浏览器 boot 是 `Promise.all` **并发**拉起所有客户端插件。
2. `shell.overlay` **不是内核内置插槽** —— 它是宿主 `ui-layout` 的 root 条目
   **在它 apply 时才**声明的子插槽；而 ui-layout 还要等 ui-theme 提供 theme 服务。
3. `@lh/practice` 只依赖 `slots` + `sessions`（runtime 核心第一批就提供），
   所以**几乎必然先于 ui-layout 执行 apply**。
4. 那一刻直接 `ctx.slots.register({name:'shell.overlay'}, …)` → SlotCore 抛错 →
   插件 fiber 失败 → **整个界面挂载中断**。

正路是 `ctx.slots.inject('<插槽>', () => ctx.slots.register(…))`：
声明已存在就同步执行，否则**推迟到声明提交那一刻**。

### 最该记住的一句：**"之前能用"是运气**

我原来的注释里写着"面板（`shell.overlay`）用了一个多月，注册不上说明环境坏得没边了"
——**那句话被实测证明是错的**。它一直是竞态，只是之前每次都恰好赢了；
昨天加卡片、改 `inject` 之后依赖图变化，**竞态稳定地输了**。

→ **一般化：一个"一直没出问题"的写法，不等于它是对的。**
  尤其当它有**时序**成分时，"没出问题"只说明"到目前为止没输过"。
  判断依据应该是"宿主保证什么顺序"，而不是"我跑了很多次都没事"。

### ⚠ 我在复核时发现修复只做了一半（这是我的主要贡献）

补修把 `shell.overlay` 的两处注册改成了 `slots.inject`，
**但卡片挂的 `tool.call.toolview` 仍是直接 `register`** ——
而它由 **ui-tool** 声明，**同一种"在它 apply 时才声明"，同一个竞态**。

上一次没暴露的原因很具体：**报错发生在第一个注册（shell.overlay）就中断了 apply，
根本没走到卡片那一行。** 把 shell.overlay 改好之后，执行会继续往下走 ——
于是会换一个插槽名再炸一次。

而第二次的后果**形态不同**（这一点值得单独记）：卡片那段有 `try/catch` 兜着，
所以**不会白屏**，而是**静默地少掉入口**（对话里不再出现刷题卡片，只有 console.warn）。

→ **"少一个功能"比"起不来"更难发现。**
  **抢跑一次是白屏（刺眼、必然被发现），抢跑两次是静默失效（没人会知道）。**

### 修法与防复发

- 三处注册**全部**改挂 `slots.inject`（面板、卡片、兜底入口）。
- **状态从布尔改成三态**：`'pending' | 'registered' | 'failed'`。
  因为注册现在会**推迟**，"还没轮到"既不是成功也不是失败；
  用布尔会把"推迟中"误判成"失败"（兜底按钮乱闪），
  或把"失败"当成"已成功"（兜底入口永不出现 → 学习者没有入口）。
  兜底入口的判据是 `!== 'registered'`（推迟中也要给一条路）。
- **新增普查式闸门**：`scripts/check-client-slot-timing.mjs`。
  用一个**什么都不声明**的假 slots 把每个客户端 bundle 真的 apply 一遍，
  断言：① 不抛错；② **零注册**。
  它**按插件普查**，而不是按"已知出事的插槽"打补丁 ——
  因为"某个插槽要小心"这条经验救不了下一个插件。

## E13. 一个**为了迁就实现而预先满足前提**的测试，等于绕过了要守的东西

补修时加了一条测试，里面写着：

```js
declareSlot('tool.call.toolview') // 卡片插槽已声明（直接 register 的老路不受影响）
```

**这行注释把测试布置成看不见剩下的那个 bug。** 卡片确实是直接 register，
但被"预先声明"喂住了，于是**同一个竞态在测试里永远不会暴露**。

→ **一般化：测试的前置条件必须照抄生产的真实状态，而不是照抄"让实现能跑通的最小条件"。**
  生产那一刻的真实状态是"**什么都不声明**"。我把测试改成从空集开始，
  它立刻红了，而且红得精确：

```
[lh-practice] 卡片注册形状被拒：… slot "tool.call.toolview" is not declared
[lh-practice] ⚠ 对话里的刷题卡片**注册失败**（三条形状都被拒）
```

### 附带发现：**假实现里的 bug 会把测试结论整个翻过来**

那个假 `slots` 的 `declareSlot` 写的是：

```js
for (const rec of pendingInjects.splice(0)) { if (rec.key === key) rec.callback() }
```

`splice(0)` 清空整个队列 → **声明一个插槽会把别的插槽的待办悄悄扔掉**。
于是"卡片那条推迟注册"永远等不到自己的声明，一条本该验"推迟后能注册成功"的用例永远红。

→ **假实现出错比真实现出错更隐蔽**：真实现出错会炸，假实现出错**只是把结论写反**，
  而人还会更相信测试的结果（"测试说的"）。
  所以测试桩的行为也要照抄真实语义（这里就是 SlotCore 的"未声明即抛"），
  并且**判据本身要先对着已知坏形状验一次**。

| `scripts/check-client-slot-timing.mjs` | **普查**所有会注册插槽的客户端 bundle：抢跑时必须不炸、零注册；自带"判据自检" |
| `selftest-client.mjs` 的假 SlotCore | 现在真的会像生产那样对未声明插槽抛错；`declareSlot` 不再丢弃别的插槽的待办 |
