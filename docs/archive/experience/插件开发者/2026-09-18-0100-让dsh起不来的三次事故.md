# 经验 —— 2026-09-18 事故日：让 dsh 起不来的三次恶性 bug

> 作者对今天的判断：**"今天的经验尤其珍贵，因为这种导致无法启动 dsh 的恶性 bug
> 对于非专业学习者是非常致命的。"**
> 所以这份文件的重心不是"修了什么"，而是**为什么这三类失败会发生、以及怎么在写的时候就不让它发生**。
>
> 作者的另一句定调：*"这种问题都是常有的，发现问题解决问题就好。"*
> —— 这份文件不写成检讨，写成**给未来系统的规格**。

---

## E1. 先说最贵的那条：一类失败会夺走整个产品

三次事故的症状各不相同，但代价是同一个：**dsh 完全无法启动**。

| # | 症状 | 触发点 | 谁修的 |
|---|---|---|---|
| 1 | `plugin tree failed to load` → 启动即崩 | profile 某行导入失败（相对路径） | 我（依赖链改包名） |
| 2 | 启动屏 `Failed to load plugins` | 客户端半没导出 `inject`（写在 package.json 里了） | 作者 |
| 3 | 启动屏 `Failed to load plugins` | list 型插槽注册缺 `options.id` | 作者 |

**对非专业学习者意味着什么**（这是作者强调的点，也是我认为最该记住的）：

- dsh 起不来 → **他没有任何入口**。不是"某个功能不能用"，是**整个工具打不开**。
- 错误信息是给开发者看的（`ERR_MODULE_NOT_FOUND`、`cannot get property "x" without inject`、
  `list slot "y" requires options.id`）。学习者**不可能**据此自救。
- 而且它发生在一个**他刚被告知"已经做好了"的功能**上——期望与现实的落差会直接消耗信任。
- 前两次还叠加了一个更糟的因素：**我的 shell 也挂了**（`0xC0000142`），
  于是连"AI 帮你修"这条退路也暂时不通。他只能靠重启电脑。

**→ 结论（应当写进 lh-plugin-develop 的硬约束）**：
**任何会导致宿主无法启动的改动，都必须先在生产路径上被一道闸门拦住；
不能把"它能不能起来"这件事留给重启去发现。**

## E2. 失败位置的不对称：我防了小的，没防大的

这是我自己的一处判断失误，值得单独记。

| 失败位置 | 后果 | 我此前的态度 |
|---|---|---|
| agent preset 某行未激活 | **该 preset 的所有会话**不可用 | 我非常小心（加行前写筛子、写注释纪律） |
| **profile 行导入失败 / 客户端半 apply 失败** | **整棵插件树加载失败，dsh 完全起不来** | **完全没有防范** |

我花了大量精力防前面那个（因为它踩过、且代价是"某个预设不可用"），
却对更严重的后者毫无准备——**因为我从没在 profile 层加过需要跨插件引用的东西**，
于是没意识到那一层的爆炸半径更大。

**→ 规格**：**按"爆炸半径"而不是"踩过的次数"来分配防范力度。**
新引入一种加载方式 / 新进入一层之前，先问"这一层坏了会波及什么"。

## E3. 三次的具体根因，以及它们共有的形状

### ① 相对路径导入只在源码目录成立

```js
import { … } from '../lh-question-bank/index.js'   // 只在 plugins/ 下成立
```

pnpm 装包时是**复制而非软链**，而且**目录名由包名派生**
（`@lh/question-bank` → 目录 `@lh/question-bank/`）。
所以相对路径 `../lh-question-bank/index.js` 要找的 `@lh/lh-question-bank/` **永远不存在**。

**修法**：改包名导入 + 在各包 `package.json` 里声明 `file:` 依赖。
**连锁性**：闸门第一次跑就报出 **`@lh/question-bank` 自己也在用相对导入** ——
问题不止一处，是**整条依赖链**。只修 `lh-practice` 就重启会立刻撞第二个同样的错。

### ② 声明写错地方：配置文件 vs 模块导出

| 写在哪 | 宿主读不读 |
|---|---|
| `package.json` 的 `dsh.client.inject`（**包名**数组） | 只进 boot manifest，**不装配 fiber 的 inject** |
| 模块导出的 `exports.inject`（**服务名**数组） | **门禁认这个** |

对照宿主自己的包可证：`dsh-session-log-export` 导出 `inject = ["slots", "locale"]`。

### ③ 校验不只是"有没有声明"，还有"注册形状对不对"

`list slot "sidebar.footer.action" requires options.id` —— list 型插槽的注册
必须带 `options.id`（该插槽内唯一）。宿主自己的写法：
`{ name: "conversation.input.overlay", id: "command-popup", order: 1 }`。

### 三者共有的形状

**它们都是宿主在运行时才执行的校验，都是"声明/形状"类的错，
而且都要真启动到那一步才暴露。**

- 类型声明里看不出来（`dsh-client-ui-slots` 的实现被打包进了前端 bundle，只有 `.d.ts`）；
- 我所有的离线验证**都到不了这一步**；
- 报错信息精确但**只对懂的人精确**。

**→ 规格**：**"声明/形状"类错误需要"按生产路径真跑一遍"的闸门，而不是"读文档写对了就行"。**

## E4. 最有价值的方法论：测试跑的路径必须等于生产路径

第①次事故里，我的断言**全部绿的**，而生产一启动就崩。原因只有一句：

> **测试跑在源码目录，生产跑在 install 后的副本里——两条路径的模块解析不同。**

我离线跑了 18 项断言，它们恰好绕过了真实路径。
于是我拿到了一个**"全绿"的假象**，而它比"没测试"更危险——因为它让我停止了怀疑。

这一条是我今天最大的收获，也是**四道闸门的共同设计原则**：

| 闸门 | 跑在哪条路径上 | 拦的是哪次事故 |
|---|---|---|
| `check-plugin-imports.mjs` | **profile 里的副本**（`import()` 它） | #1 |
| `check-profile-apply.mjs` | 同上，用记账式假 ctx 真跑 `apply()` | #1 的下一层 |
| `check-client-inject.mjs` | 源码 + profile 副本都扫 | #2 #3 |
| `check-preset-mount.mjs` | agent preset 的行 | preset 层失败 |

**并且闸门自己要先被验证**：我让导入闸门**对着当时还坏着的状态**跑了一遍，
确认它报出的正是用户看到的那条错误——**而不是假设它能抓到**。

**→ 规格**：**写闸门时，先让它在已知坏的状态上红一次。**
一个没在坏状态上验证过的闸门，只是一个希望。

## E5. 一个具体的、可复用的技术判断：两端不在同一棵树时，消息怎么传

刷题面板要由对话启动，而：

- 工具注册在 **agent preset 作用域**；
- 面板与 HTTP 路由在 **profile/host 作用域**。

**内存信号传不过去。** 这是同一个坑的**第二次**——早期 `lh-event-store` 在 preset 里
等一个 host 面提供的服务，永远等不到（ADR-014 补充决定 6）。

**这次的处理：用文件做会合点**（`practice-signal.json`）。
它不需要任何新服务、不依赖宿主的推送机制（宿主没有服务端→客户端的通用推送；
`ctx.provide` 是客户端插件之间发布服务用的，方向不对）。

而且信号被刻意设计得很小：**一个计数器 + 时间戳**，不是队列。
语义只有"请打开面板"——重复打开无害（面板自己会取题），所以不需要可靠投递、顺序、ack。

**→ 规格（可复用的模式）**：
跨作用域通信，按这个顺序选：
1. 能不能**同作用域**解决？（改架构）
2. 不能 → **文件/共享状态**（最朴素、无新依赖）
3. 还不能 → 才考虑自己实现通道（SSE 等，但要付长连接生命周期的代价）

**并且**：信号的语义要设计成**幂等**的，这样就不需要可靠投递。

## E6. 三次"判定器比被测对象更脆"，指向一条纪律

事故之外，今天还有一类反复出现的错误，我把它单列出来因为它**每次都差点让我否定一个正确方案**：

| # | 我的判定器错在哪 | 差点导致的错误结论 |
|---|---|---|
| 1 | 真值只给"末尾 10 字"，模型给的是更长的**正确**片段 → 字面不等 | "LLM 标不对空位位置" |
| 2 | 判定器没考虑**全角/半角引号**差异 | 同上 |
| 3 | 测试 harness 的 `makeReq` 会**自动推空 body 并 end**，于是被测路径根本没跑 | "坏 JSON 没被正确拒绝" |

**→ 纪律**：**判定器与被测对象之间，判定器必须更宽容。**
如果一次验证的结论是"对方不行"，**先问"我的判定是不是太严"**。
（误判的代价不是"少一条通过"，而是**否掉一个可行的方案**。）

## E7. 环境与工具的几个具体坑（可照抄的检查清单）

| 坑 | 现象 | 处置 |
|---|---|---|
| pnpm 对 `file:` 依赖用**复制**，且不因源码改变而刷新 | 改完代码 `pnpm add` 后副本还是旧的，`Already up to date` | 删 `node_modules/@lh/<pkg>` 再 install；或 bump 版本 |
| profile 副本 vs 工作区根：**一个复制一个软链** | "改了没生效" | 用 **hash 比对**源码与副本，而不是看时间戳 |
| PowerShell 的 `>` 重定向写 **UTF-16LE** | Node 按 UTF-8 读全变 `\u0000`，所有 ASCII 正则失配 | 要写文本文件用 Node 写，不要 shell 重定向 |
| `Select-Object -First N` **掐断管道并杀掉子进程** | 脚本尾部逻辑没执行（落盘失败） | 要截断输出就重定向到文件，别用 `-First` 接管道 |
| Node/PowerShell 全部子进程返回 `0xC0000142` | 环境层面的进程创建失败（疑似桌面堆耗尽） | **重启机器**；这不是代码问题，别去改代码 |
| 读日志"没看到某条" | 可能是**读早了**，那行还没发生 | 先问清时间线；"没看到"≠"没发生" |

## E8. 我这轮犯的两个"没对齐就动手"

1. **交互形态**：作者说"像有的网页端 AI 那样，点对话里的一个链接或框，右侧弹出报告页面"。
   我做成了"agent 一调工具，浮层面板自己弹出来"——**擅自替换了他要的形态，且没确认**。
   → 正确做法：**复述一遍我理解的行为，让他确认，再动手**。
2. **profile 层加东西**：我第一次在 profile 层加需要跨插件引用的包，
   沿用了 preset 层的写法（相对导入），**没有意识到那是另一种加载机制**。
   → 正确做法：**进入一个新的加载层/作用域之前，先把那一层的规则问清**。

**共同形状**：**我按"上一处的经验"直接套用到"这一处"，而没有先确认这两处是否同构。**
这和 E4 是同一条：**路径/层不同，规则就可能不同。**

## E10. 明天要谈的两件事（作者提出，尚未想清）

### ① 这些闸门应当是 `lh-plugin-develop` 的核心部分

作者原话：*"如果你还记得我之前说的 lh-plugin-develop 插件，
那避免这种问题一定是这个插件很核心的部分。"*

我的理解：`lh-plugin-develop` 是**让 agent 写插件**的插件（作者早前的构想：
*"agent 调用 lh-plugin-develop 将用户的意愿、学习方法落地成插件"*）。
那么"新写出来的插件不能让宿主起不来"就是它的**第一职责**——
比"生成正确的业务逻辑"更靠前，因为后者坏了只是功能不对，前者坏了**整个产品打不开**。

**已经可用的素材**：四个闸门。它们已经是"按生产路径验一遍"的形态。
**还缺的**：一个**分级判据**——什么样的错属于"能起不来"，
必须在写入插件的那一刻就检查（而不是等重启）。初步想法：

| 级别 | 例子 | 何时检 |
|---|---|---|
| 致命（会夺走入口） | 导入失败、apply 抛错、inject 未导出、插槽注册形状错 | **生成插件后立刻**，且**安装到 profile 后立刻** |
| 严重（功能不可用） | 工具 schema 被宿主拒绝、路由注册撞名 | 生成后 |
| 一般（逻辑错） | 判分口径不对、边界没处理 | 常规测试 |

### ② "克隆一个 dsh"来做开发/测试隔离

作者原话：*"我还在考虑是否需要'克隆'一个 dsh 进程，然后开发与测试进行隔离，
这样我可以一直在测试端重启重启，测试端出了内核级别的 bug 无法进到 dsh，
我也能用开发的 dsh 进行 debug，但具体的做法和逻辑我还没想好。"*

**他要解决的是今天暴露的真实困境**：
- 他在**正在跟我对话的这个 dsh** 上测插件；
- 插件坏了 → 这个 dsh 起不来 → **对话也没了**（今天发生了两次，第二次还叠加 shell 挂掉）；
- 于是"测试"这个动作本身**会摧毁测试者所在的房间**。

**这是一个真正的问题，而且不是"小心点"能解决的。**
明天要谈的是做法与逻辑（我只有问题，没有方案）：
- 用哪个 profile 隔离？（`dev` profile 已存在，但早前实测它的 `llm` adapters 注册不上）
- 隔离的粒度：进程？profile？工作区？
- "测试端起不来"时，开发端如何仍然可用（今天连 shell 都被波及）
- 测试端的插件来源是否指向同一份源码（否则"改一处要同步两处"）

**注意**：作者明确说"明天再说"，所以以上只是**把问题记清楚**，不预设方案。
