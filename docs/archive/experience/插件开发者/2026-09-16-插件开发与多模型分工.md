## 一、宿主机制（读源码得到的事实，避免重查）

### E1. 挂载失败的代价不是"插件不工作"，而是**整个会话不可用**

- **场景**：`lh-recorder-trace`（preset 行）声明 `inject: ['lhEvents']`，等一个不存在的服务。
- **现象**：新建 LH 会话失败，**已有的 LH 会话重新进入也失败**。错误为
  `preset "lh" failed to mount: 1 row(s) did not activate: lh-recorder-trace: waiting for lhEvents`。
- **根因**：`mountPreset()` 在 agent 创建时抛错，于是该 preset 的**所有**会话都建不起来。
- **下次怎么做**：
  1. preset 行的任何依赖必须是"**加载时就能确定可用**"的，不能是"将来某刻会可用"的；
  2. 新增 preset 行之后**必须在真实会话里验证一次**——`discoverPresets()` 的 `broken` 字段
     只做 YAML 形状检查，**查不出**"行在等一个不存在的服务"；
  3. 报错里的 `waiting for X` 直接点名缺失的服务，**先信它**。

### E2. Cordis 的 `Service` 子类必须在构造函数里 `super(ctx, name)`

```ts
// cordis/lib/types/service.d.ts:38 —— 真实契约
constructor(ctx: Context, name: string)
```

我写了一个带 `static name = 'lhEvents'` 的普通类、用默认构造函数——**服务从未被注册**，
消费者等的是一个不存在的东西。`static name` 不是注册机制。

### E3. preset 是 agent 作用域，**够不着 host 面发布的服务**

- 即便 E2 修对了，`dsh-agent-presets` 的 `mount()` 也会**拒绝"往 root realm 发布服务"的行**：
  > "a preset service must sit behind an `isolate` realm or move to the host composition"
- **结论**：**preset 插件之间共享逻辑用直接 import**（要求被导入模块是纯 JS、只依赖 Node 内置模块）。
- **已知代价**：profile 面与 preset 面各装载一份模块，会有两个实例、写同一个文件。
  同一文件以 append 模式逐行写入不会交错（单机单用户成立）；将来需并发写入时，
  应改为单一写入者（把写入收进 host 面服务），而不是继续直接 import。

### E4. specifier 解析有**三处**不同路径（别记成两处）

| 加载位置 | 裸包名 | 相对路径 | Windows 绝对路径 |
|---|---|---|---|
| **preset 行**（`agent.cordis.yml`） | 常失败（见下） | 以 preset 目录为基 | ✓ 可用（宿主转 `file:` URL） |
| **profile 的 `cordis.patch.yml`** | 从宿主安装目录解析 ✓ | 以 profile 目录为基 | ✗ **失败** |
| **直接 `node` 跑文件** | 从该文件向上找 `node_modules` | 同左 | ✗ 失败（需 `pathToFileURL()`） |

- **preset 行的裸包名为何失败**：宿主设"裸包名基址"是**有条件的**
  （`dsh-agent-presets/lib/index.js:708` `if (agentCtx.baseUrl !== void 0)`），实测该条件**未成立**。
  于是裸包名退回 Node 普通解析，从 preset 目录（在用户 home 下）向上走，**永远到不了宿主**。
  实测：`@deepseek-ai/dsh-llm`、`@deepseek-ai/dsh-tools` 都报 `ERR_MODULE_NOT_FOUND`；
  而工作区里的 `zod` 能解析（因为插件源码就住在工作区）。
- **profile 行的绝对路径失败原文**：
  ```
  Only URLs with a scheme in: file, data, and node are supported by the default ESM loader.
  On Windows, absolute paths must be valid file:// URLs. Received protocol 'd:'
  ```
- **下次怎么做**：给 profile 的 patch 行写路径时**一律用 `pathToFileURL()`**；
  插件源码放在**有 `node_modules` 的目录**（工作区）并用相对导入。
- **为什么值得单独记**：同一个"绝对路径"在 preset 行能用、在 profile 行不能用，
  而两处报错完全不同（一处静默、一处明确报 scheme）。**记成表才能一眼查。**

### E5. 其它确认过的机制

| 事实 | 值 / 结论 |
|---|---|
| 客户端插件入口 | **是"服务端行"**——宿主扫描 Loader 的 entries，看哪行的 name 对应声明了 `dsh.client` 的包 |
| `exports` 必须暴露 | `"./package.json"`（宿主用 `require.resolve('<包名>/package.json')`），**漏了是静默失败** |
| 客户端 bundle 格式 | 懒注册的 CJS 工厂（`window.__ModuleLoader__.load({ id, factory })`），**可手写，不需要构建链** |
| 客户端状态读取 | `ctx.sessions.list` 是 `ObservableSnapshot`（`getSnapshot` + `subscribe`），**不需要 React** |
| 服务端改动生效 | **必须重启**（web profile 的 `hmr` 行是 `disabled: true`，上游注释："TODO: Re-enable ... after its reload lifecycle is tested"） |
| 客户端 bundle 改动 | 只需浏览器刷新（宿主按内容哈希取版本） |
| 工具注册 schema | 要**字面 JSON Schema**；`defineTool` 的 DSL 会被它内部编译掉，**不能照抄**（见 E9） |
| 主题机制 | 两对样式块：静态调色板（两模式**取值相同**）+ 别名映射（66 个别名在两模式指向色阶**相反两端**）。所以只给**一条连续色阶** |

## 二、我踩的坑（按教训的通用性排序）

### E6. 验证环境必须与生产环境**同构**，否则验的是别的东西

- **场景**：为了"不打扰作者的 GUI（web profile）"，我另起了一个 **dev profile** 来验证
  "preset 插件能否调用宿主模型服务"。在 dev 里得到 `listProviders() = 0`，
  于是追了六七轮：查配置差异、查 profile patch、查 node_modules、查设置加载……
- **真相**：切回 web profile 一测，`listProviders() = 3`，一切正常。
  **dev profile 的 0 是那个环境自身的问题，与架构无关。**
- **代价**：六七轮往返 + 一次让作者重启。**而且如果我只在 dev 里验证，
  会得出完全错误的架构结论**（"通道不通，要换方案"）。
- **下次怎么做**：
  1. 先问"**我要验证的行为发生在哪个环境**"，然后在**那个**环境里验；
  2. 换环境的唯一正当理由是"该环境与生产同构"，不是"这样不打扰人"；
  3. **在这种取舍上先问一句**，不要自己绕道——绕道的成本远高于问一句。

### E7. 把"我以为只删自己的数据"当成了保证——**删掉了作者的真实记录**

- **场景**：清理"我自己验证产生的旧格式产物"，用启发式判据
  "`content_ref` 不含冒号就删"。结果匹配到了**作者测试时产生的两条真实资源记录**。
- **根因**：那条判据**从一开始就在猜**。它识别的是"我的旧格式"，但旧格式与作者的数据同形。
  而我说的是"只清我自己的"，**那句话没有对应的机制**。
- **损失**：那两条是确定性扫描的产物（15ms 可重放），内容无损；**损失的是信任**。
- **下次怎么做**（已写进 `docs/WORKFLOW.md` §2 规则 4）：
  1. 破坏性操作**只允许白名单**（明确列出要删的 id），不允许"删掉所有不匹配的"；
  2. 先跑**报告模式**（只列出"将要删什么"及其判据）；
  3. 执行前**自动备份**并在报告里写出备份位置；
  4. **一次清理只做一件事**——清理与验证不混在同一条命令里，否则两者互相掩盖。

### E8. 整文件重写的脚本必须输出"改前 → 改后"，否则事后无法自证

- **场景**：我改 `workspace.json` 修正一个拼写，脚本只打印"修正 1 处"。
  后来作者问"为什么我的修改没生效"，而我**无法用证据排除"是我覆盖的"**——
  因为我没记录改动前后的对比。
- **下次怎么做**：整文件读-改-写的脚本，输出**每个被改对象的改前值与改后值**。
  一句"修正 N 处"在争议时等于没有信息。

### E9. 注册工具时不能照抄 `defineTool` 的 DSL

- **现象**：照抄 `dsh-tool-todo` 的 `parameters: { x: { type:'string', required:true } }` 交给
  `ctx.tools.register`。
- **根因**：那个 DSL **不是注册表接受的形态**。`defineTool` 内部会编译：
  ```js
  const parameters = parameterSchemaSpecToJsonSchema(options.parameters)   // required 变根级数组
  const outputSchema = valueSchemaSpecToJsonSchema(options.output.schema)
  ```
  而 `defineTool` 来自 `@deepseek-ai/dsh-tools`——**工作区解析不到**（E4），既不能 import，
  也不能指望注册表替我们编译。
- **支持的构造**（实测自 `assertSupportedJsonSchema`）：
  `type` / `oneOf` / `properties` / `required` / `additionalProperties` / `items` / `enum` / `const`
  \+ 注释类键（`description` / `title`）。
- **启示**：看到第一方插件的写法，**先问"这是源码写法还是编译产物"**。
  带 `defineTool` / `schemastery` / `zod` 这类构造器的地方，源码形态 ≠ 运行时形态。

### E10. preset 插件的 `{ global: true }` 监听器会伸到**整个进程**——学习史被开发记录污染

- **场景**：坐标记录器上线后，作者查看日志发现"记录了整个 dsh 的所有会话"。
- **实测比判断更糟**：LH 日志 75 条涉及 3 个会话，**全部跑在 standard / cordis 上**，
  其中 68 条来自**作者与 AI 的开发对话**。学习会话的记录：**0 条**。
- **根因（两条规则叠加）**：
  1. **preset 在进程内只挂载一次并长期驻留**（宿主 README：the standing mount
     "survives every agent"；被取代的 generation "stays mounted until the process ends"）。
     所以反复挂载会**累积**监听器——trace 里实测到 5 次以上 `LISTENING`；
  2. **`{ global: true }` 观察整棵树的事件**，于是每个累积的监听器都能看到**全部会话**。
- **解决**：**订阅仍用 `global: true`**（唯一能确保不漏的方式），把筛选放进**回调**：
  `session.header.agentPreset === '<本 preset id>'`。
- **启示**：**插件的"作用域"要自己守，不能指望宿主替你守。**
  派生规则：**任何写共享存储的插件都必须显式判断"这条该不该我记"**——订阅面几乎总是比你以为的宽。
- **附带**：这类污染**不报错**，只让数据悄悄变脏。发现它靠"作者去看了一眼数据"——
  **定期看一眼真实产物是必要的**，不能只依赖日志与自检。

### E11. 会话的 preset 在**两个**地方有值，只有会变的那个是真相

- **场景**：筛选条件写成 `session.header.agentPreset === 'lh'`，结果**所有 LH 会话都被判为"非学习会话"**。
- **根因**：`session.header.agentPreset` 是**创建时的事实**、被深冻结；
  而空白会话可以**切换** preset——切换会写一条 `agent-preset/selected` 事件，header 不变。
  实测：作者新建的会话 header 是 `cordis`（创建时的默认），
  `agent-preset/selected` 是 `lh`——**用户选的确实是 LH，是我读法错了**。
- **解决**：照抄宿主的 `resolveSessionPreset` 逻辑——
  **取最后一条 `agent-preset/selected`，没有则退回 header**。
  并按 `surface.replaceGeneration` 缓存（那个会话有 27 万条事件，每条都扫一遍不可接受）。
- **启示**：**同一事实有多处表示时，要问"哪个会在生命周期中变化"。**
  宿主若提供了 `resolve*` 这样的函数，那是在明说"别直接读字段"。

### E12. 空字段是**静默故障**：字段位置必须查证，不能猜

- **现象**：抽"模型身份"时按 `event.data.message.model` 取——**取到空，且不报任何错**。
- **真相**：位置是 `event.data.message.source.{provider,model}`（`source` 是 tagged union，
  对 assistant 消息 `kind === 'model'`）。`message` 上只有 `role, content, source, id`。
- **下次怎么做**：
  1. 抽字段前**先解压一个真实样本、把该类型事件的键打出来**；
  2. 抽完用**真实形状**的事件喂一遍验证；
  3. 记住：**空字段不报错，只静默丢信息**——运行期毫无征兆。
- **启示**：**"没报错"不等于"取到了"。**

### E13. 处理 JSON 用 Node；处理**任何文本文件**也用 Node

- **场景**：E12（前一天）已记下"不要用 PowerShell 改 JSON/JSONL"。但改一个 `.mjs` 脚本时，
  又用了 `Set-Content -Encoding UTF8`——**BOM 立刻出现**（`ef bb bf`）。
- **根因**：那条规矩我写窄了。问题不在"JSON 怕 BOM"，而在
  **PowerShell 5 的 `-Encoding UTF8` 永远写 BOM**。对 `.json` 它立刻炸；
  对 `.mjs`/`.md` 它**不炸**——所以它更危险：没人会注意到。
- **下次怎么做**：**本工作区改任何文本文件都用 Node**；核对时看字节
  （BOM = `ef bb bf`，正常 JS/Markdown 开头是 `2f` / `23`）。
- **启示**：**把一个教训写窄了，等于没写。** 规则要写在其真正的边界上。

### E14. 不要在 PowerShell 里内联跑 JS

- **现象**：至少四次被咬：`-e "..."` 里的正则 `[...]` 与嵌套引号被 PowerShell 解析器吃掉，
  报 `Missing type name after '['` / `SyntaxError: Invalid or unexpected token`。
  **最坏的一次是脚本没执行成功，而我没察觉**（以为改了文件，其实没改）。
- **下次怎么做**：**JS 一律写成 `.mjs` 文件再 `node` 跑**。临时脚本放 `scripts/`，
  用 `--once` 之类的显式参数而不是靠内联。
- **启示**：**工具边界也是"会静默失败"的地方**——命令没生效比命令报错更危险。

### E15. 改了函数签名，忘了改函数体

- **现象**：探针里把 `tryCall(ctx, ...)` 改成收"llm 实例"，但函数体仍写 `ctx.llm.stream(...)`。
  于是 `TypeError: Cannot read properties of undefined (reading 'stream')`，
  **两次真实调用都失败**，而前面"通道存在"的结论完全正确——**是探针自己的 bug 掩盖了结论**。
- **下次怎么做**：改签名时**同时改调用点与函数体**，并跑一次；
  参数名与用法对齐（收 `llm` 就叫 `llm`，不叫 `ctx`）。
- **启示**：**验证工具的 bug 会被误读成被测对象的缺陷。** 所以"失败"要先自查工具。

## 三、今天确立的设计约定（还没全部落地，但已定）

### E16. 模型档位：**建议而非要求；告知而非阻断；降级必须留痕；问由 agent 在自然边界做**

经过与作者四轮讨论收敛的结果（每一轮都是他在纠正我）：

| 约定 | 内容 | 为什么 |
|---|---|---|
| 插件声明**档位**，不写模型名 | `recommend_model: 'flash'` | "哪个用途用哪个模型"是使用者的决策，不是插件的属性（作者纠正） |
| 档位是**建议** | 不满足时给提示，**不阻断** | "弱模型做不了"是插件的**猜测**，它没有这个知识；硬拒绝等于用拒绝惩罚用户，与契约 §3.1 的反奖惩立场同构（作者纠正） |
| **不做** `must-not-degrade`、不隐藏工具 | 全部可见 | 隐藏工具 = 系统替用户判断"你做不到这件事"（作者纠正） |
| **降级必须留痕** | 结果里带 notes，写进 LH 事件 | 不是惩罚，是**出处**：仪器降级会让"策略失败"被误判。契约 §5.3 说测量仪器质量是评估的天花板 |
| **modeltier 绝不弹框、绝不阻断** | 永远尽力而为，把"发生了什么"作为**数据**返回 | 弹框时机由调用点决定，而调用点可能在**工作流深处**——那正是最差的时机（作者的体验论证） |
| **问由 agent 做，且在自然边界** | agent 在计划开头（刚知道需要它）或调用刚开始时问 | 作者的关键洞察：**"计划了 5 分钟才要审批，用户也很难决定"**——他已被排除在上下文之外，没法决定一个不知来龙去脉的事 |
| 上下文里写**档位可用性** | 几行字，agent 每轮可见 | 让 agent **提前**知道，从而能在好的时机问——这是"提前知道"与"中途打断"的区别 |

**为什么 `ctx.approval` 不进这条路**：它适合宿主的**原生闸门**（工具审批、沙箱升级），
但它的时机由调用点决定；档位问题需要**判断与选项**（换路径 / 配模型 / 终止），
那是 agent 的活。两者不混。

### E17. 降级不只是失败模式，它是**生态的生长机制**

作者提出的情景，我认为是 LH 最重要的一个设计输入：

> 有一个抽象度高的插件，需要很强的智能 → **有人把任务拆成若干小插件**，
> 每个完成各自部分 → **弱模型通过插件组合也能完成复杂任务**

于是用户面对"档位不足"时有**四种**选择，而不只是"接受/放弃"：

| 选择 | 后果 |
|---|---|
| 就这样做 | 接受质量 / 成本后果 |
| **换一条拆解路径** | 用若干小插件的组合完成同一件事——**弱模型也能做** |
| 去配置对应模型 | 补齐能力 |
| 终止 | 明确不做 |

**推论**：agent 问的时候不该只问"要不要降级"（是/否题），而该**给出路径选项**。
而"知道有哪些插件、各自需要什么档位"因此成为 agent 的**规划输入**，不只是执行细节。
**能力缺口会催生专门插件**——这条会写进契约备忘录。

### E18. 工具是 LH 的，不是我的（作者明确要求）

- **建**（写插件、注册工具、定义 schema、写工作流）→ 开发用的 AI；
- **跑**（在 LH 的 loop 里由 LH 的 agent 调用工具完成任务）→ **LH 的 harness + agent**。
- **反例（必须避免）**：作者说"帮我索引某资料夹"，我就自己扫一遍把结果贴出来——
  那样**什么也没验证**，因为真正要验证的是"agent 会不会在对的时机调用它、参数对不对、
  拿到结果后怎么用"。我代做等于绕过被测的那一环。
- 详见 `docs/decisions/015`。

### E19. 档位解析的两级（已验证）

- **预检**：只查 provider 有没有注册（便宜、无副作用）；
  **不查模型在不在目录里**——宿主明说目录是"建议性"的
  （"consumers must not turn absence into request rejection"）。
- **失败降级**：拿 selection 真去调，**调用失败时**再试下一个候选。
  只有真实调用才知道模型 id 是否被适配器接受。
- 因此解析返回的是**完整候选链**，不只是单个 selection。
- 三种降级情形已实测通过：首选 provider 未注册 / 档位没配 / 候选全不可用（返回 `undefined`）。

### E20. 资源索引器的形态（已实测）

- 扫描 **230 个文件 / 5.16 GB / 15ms**，索引文档 16.8 KB ≈ 8,400 tokens；
- **索引文档写进工作区的 `lh-index/`**，事件只记 `content_ref` 指向它；
- **工具返回值只给摘要 + 路径**——全文不进对话。
  （作者实测反馈修正：第一版把全文塞进工具返回值，那是"让它变成一段对话记录"，
  而索引是**产物**。而且全文进上下文会**每轮重发**，还会撞上宿主 50KB 的 spill 阈值。）
- 资源记录走 `appendResource`，带 `derived_from` / `supersedes`（ADR-009）；
  重复索引会建立取代链，**旧记录不被覆盖**（已验证）。
