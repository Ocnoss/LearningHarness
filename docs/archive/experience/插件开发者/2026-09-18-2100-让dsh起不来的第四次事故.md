# 让 dsh 起不来的第四次事故 —— 而它差一次重启才发生

- 日期：2026-09-18 21:00
- 角色：插件开发者
- 相关：ADR-025、`docs/PLUGIN_CONTRACT.md` §五之二～§五之五、
  `docs/experience/插件开发者/2026-09-18-0100-让dsh起不来的三次事故.md`

---

## E1. 一个"改对了"的重构，会在下次重启时把宿主弄坏

**会复发**：任何"把写死的东西改成推导出来的"重构，都有这个形态。

我把 4 处写死的绝对路径改掉了，改成"从模块位置往上找仓库根"。源码树里上方确有仓库，
所以离线测试全绿、手动 apply 也全绿。**但装进 profile 后，包的上方没有仓库**——
`dataDir()` 抛错 → `apply()` 抛错 → 整棵插件树加载失败 → dsh 起不来。

而这个故障一直被**写死的路径**挡着：profile 里那份旧拷贝还写着
`DEFAULT_DATA_DIR = 'D:\LearningHarnessv0.1\data'`，所以"能跑"。

→ **去掉一处写死之前，先问"它是不是正在替谁挡着什么"。**
写死的东西常常在无意中承担了"让某个推导失败的分支不被走到"的职责。

## E2. "测试是绿的"里，"测的是哪一份代码"是一个独立问题

**反直觉**：测试通过这件事本身，不包含"被测对象与生产对象是同一份"。

实测：根 `node_modules/@lh/*` 是**软链到 `.pnpm` 下的拷贝**——最后一跳是真实目录。
所以它看起来是软链、实际是快照。而根 `package.json` 的注释里**断言**了
"pnpm 会用软链指回源码，所以不存在副本陈旧问题"。**那句话是错的**，
而它错得很贵：它让"改了没生效"这个现象失去了怀疑对象。

→ 现在：根改 `workspace:*`（真软链），profile 仍是拷贝所以有 `sync-lh-deps.mjs`，
并且有闸门 `check-installed-copies.mjs` 专门盯"副本是不是旧的"。

## E3. 拆掉一个错误行为时，要问"原来是谁在替我报警"

**代价高**：这次差点被我漏过去，因为**是我自己让闸门变绿的**。

把 `apply()` 里的抛错改成"用的时候拒绝"（这是对的：装载期抛错会让 dsh 起不来），
`check-profile-apply.mjs` 立刻从红变绿——**而底层仍然是坏的**：
profile 里的路径依然解析不出来，只是不再有人喊了。

→ 所以补了 `check-paths-resolution.mjs`：它**不经过 apply()**，
直接对每个加载位置问"数据目录/工作区在哪"，并断言**答案一致**。
"在源码树里问是对的、在 profile 里问是错的"正是这个 bug 的形态。

**一般化：一个修复如果让某道闸门变绿，必须确认"绿"是因为事情对了，
还是因为报警的人被一起修掉了。**

## E4. 闸门自己也要有测试，而且**两个方向**都要断言

**反直觉**：我原来只想到"要见它红过"，忘了"永远红的闸门同样没用"——
人会条件反射地忽略它，那时它连希望都不是，是噪声。

→ `scripts/selftest-installed-copies.mjs`：在**临时目录**造假仓库，
连"副本有未声明的残留文件时必须仍然绿"这条**良性误报**一起断言。
全程不碰真 profile（真 profile 是 dsh 的安装根，为验一道闸门去动它，性价比是负的）。

指标：7/7 通过，包含"活链要如实标注而不是假装比对过"。

## E5. 把"响亮地失败"实现成"装载时抛错"，等于把门锁上

**反直觉**：这违反直觉，因为原写的理由非常正当——
"存储不可用是系统级故障，必须显式暴露，不能静默降级"。

**理由对，位置错。** profile 插件的 `apply()` 抛错 = dsh 起不来 =
学习者失去入口 → **他最需要"该改哪一行"这句话的时刻，说明被自己弄没了**。

→ 响亮应该发生**用的时候**：路由 503 + 修法、工具返回错误 + 修法、顺带打 stderr。

## E6. 环境变量当"唯一配置来源"是一个陷阱

实测：`LH_DATA_DIR` / `LH_WORKSPACE` 在这台机器上**哪儿都没设**
（用户级、机器级、进程级全空），而 dsh 是朴素的 `npx @deepseek-ai/dsh web` 启动的。

一个"每次启动都要记得设"的东西，不是一个能交付的默认值——
**忘了设的代价是起不来，而学习者无法从内部修复它**。

→ `lh-install.json`：装的时候写下，运行时只读。显式（不是猜的），且不需要每次记得。

## E7. 我写的"跑全部闸门"脚本，把整台机器卡死了约 40 分钟

**代价最高的一次。而且是纯粹的疏忽，不是难懂的问题。**

我写了 `scripts/check-all.mjs`：按**命名约定**（`check-` 前缀）发现所有闸门，逐个 `spawnSync` 跑。
而它自己的名字是 `check-all.mjs` —— **它把自己也发现了**。

于是每层扇出约 10 个子进程，其中一个是它自己 → **指数级**。
两分钟生出 752 个 node 进程，吃掉 CPU、内存、进程槽；
第一层被超时杀掉之后，**孤儿后代还在继续繁殖**（杀掉的是父进程，不是那棵树）。
整机卡死约 40 分钟，最后 **dsh 自己崩了**：

```
Error: ENOENT: no such file or directory, open
  'C:\Users\ADMINI~1\AppData\Local\Temp\dsh-subprocess-kusGXR\dsh-subprocess-9128-…-stdout.log'
    at OutputCollector.spillAll (dsh-subprocess-local/lib/index.js:666)
```

dsh 只是**受害者**：它要往子进程输出缓冲里落盘，而临时目录在资源被吃干时取不到了。
学习者看到的是"卡了 40 分钟然后服务挂掉"，根因却是一个**为了省事写的便捷脚本**。

### 为什么值得记（三条全占）

- **会复发**：任何"按名字自动发现自身"的脚本都有这个形状。CI、测试发现、插件扫描都算。
- **反直觉**：错误不在逻辑里——每一行单看都对，错的是**发现规则包含了发现者自己**。
  而且它不报错，只会**变慢**（120 秒没有任何输出），于是第一反应是"再等等"或"再跑一次"——
  **重跑恰好是火上浇油**。
- **代价高**：整机不可用约 40 分钟，宿主崩溃，学习者的会话被打断。

### 修法（两道，缺一不可）

1. **按路径排除自己**（不能按名字——名字正是判据）；
2. **环境变量递归闸**：子进程里发现自己在 `check-all` 之内，直接 `exit 2`。
   第 2 条才是真正兜住的那道——将来若命名规则变了，第 1 条会失效，
   第 2 条仍能让爆炸**停在第一层**，而不是 10ⁿ 层。

同一事故还暴露了第二个缺陷：`check-restart.mjs` **对每个 node 进程各发一次 WMI 查询**
（`Get-Process node | ForEach-Object { Get-CimInstance … }`）。进程少时"能用"；
进程一多，它自己变成分钟级，**还把整机 WMI 拖住**——这就是那 40 分钟里
"不只是慢、而是全都动不了"的另一半来源。改成**一次查询取全部**，并给子进程加**硬超时**。

### 一般化的三条

- **一个工具如果"卡住"而不"报错"，它会诱导人重跑；而重跑正是最坏的反应。**
  所以给每个子进程加**硬超时**：卡住的上限必须是"这一项没结果"，不能是"整台机器卡住"。
- **`spawnSync` 进程树不会因为父进程被杀而消失。** 超时杀掉父进程后要确认**后代**也死了。
- **排查时按命令行精确匹配再杀，绝不能按进程名批量杀**——按名字杀会顺手杀掉宿主。
  （本次排查：一次 CIM 查询列出所有 node 进程 + 命令行 + 启动时间，
  只杀命令行含 `check-all.mjs` / `check-restart.mjs` 的 761 个，显式保留 2 个 dsh 进程。）

### 附带确认：这一天真正修好的东西，被一次真启动证实了

重启后的生产 trace 里能看到：

```
profile/event-store:  STORE_READY  log=D:\LearningHarnessv0.1\data\events.jsonl
profile/practice:     APPLY_CALLED workspace=D:\learning Harness test
                      source=lh-install.json (C:\…\profiles\web\lh-install.json)
```

**没有任何环境变量**，两个路径都自己找到了家。这正是 E1 里那个"差一次重启就爆炸"的故障——
它没有爆炸，而且是被**真实启动**（不是闸门）证明的。
