## Y1. 工具的"使用者"是 LH 的 agent，不是开发用的 AI

- **场景**：我在做资源索引器，方向是"注册一个模型可调用的工具"。作者主动补充了一条要求。
- **决策**：作者明确划清两件事——
  > "你的工作是建立 agent 工作流，然后调用我给你的大模型 api 在你建立的 loop、用你设置的 Harness 来完成，**而不是自己用 dsh 的工具去完成**，此前有一些 llm 会混淆这两者"
  > "以后我说的这些工具都是需要符合宿主的框架，宿主的插件接口协议的"
- **根因**：若开发用的 AI 自己把活干完，**被测的那一环（agent 会不会在对的时机调用、参数对不对、结果怎么用）就完全没被验证**。
- **解决方案**：`docs/decisions/015` 定死"建 / 跑"分离：**交付物是工作流 + 工具 + 配置，不是结果**。
- **启示**：**"我顺手做完了"看起来高效，实际是绕过验证。** 这条约束同时是质量标准。

## Y2. 插件的声明应该小到"agent 填得对"，复杂度收在中间件里

- **场景**：讨论模型档位声明时，我一度担心"agent 要根据用户描述判断该用哪个档位"。
- **决策**：作者否掉了这个担心——
  > "agent 甚至不需要会根据用户描述的工作填推荐档位和是否允许降级，agent 只需要知道**要填**，他可以问，可以推荐让用户选"
- **根因**：把"判断"压给 agent 会让声明变成需要领域理解的东西；而"知道有这个字段、可以问用户"是 agent 本来就会的事。
- **解决方案**：schema 只需**自描述的字段定义**（含义、可选值、默认值）；策略逻辑全归中间件。
- **启示**：**声明的复杂度上限，是"agent 能机械填对"**。超过这个上限，就该把判断挪到别处。

## Y3. 档位名对，模型名错——"哪个用途用哪个模型"是使用者的决策

- **场景**：我按"插件里写 `recommend_model` 字段"去理解，准备写具体模型名。作者澄清：
  > "recommend_model 写死对应模型是我表达的歧义，我的意思就是档位名"
- **决策**：插件声明**档位**（`flash` / `balance` / `max`），档位到模型的映射写在一处配置里。
- **根因**：插件写死模型名的话，换一次模型就要改所有插件。
- **启示**：**插件的属性 vs 使用者的决策，要分清**。这条和 Y5（拒绝服务）是同一种错误的两个形态。

## Y4. "问"是必需的，但**时机**比问法更重要

- **场景**：讨论"档位不可用时要不要找用户审批"。作者先给了正面例子，再给了反例：
  > "agent 如果先调模型工具，发现有问题了，马上问，从思考到调用到问可能就两三行字，那没什么问题，这种体验很好"
  > "但如果 agent 自己决定先计划或者用户在输入里加了类似 spec 或者 plan，思考了 5 分钟，开始动工了，一调用模型发现出问题，要找用户审批，**用户也很难决定**，这种体验就很差了"
- **决策**：
  1. **问**：用户有权在知道"当前模型可能完不成 / 可能更贵"的情况下终止任务；
  2. **但绝不能**在工作流深处才暴露——所以档位可用性要**提前写进上下文**，
     让 agent 在计划时就知道，从而能在**自然边界**问；
  3. **中间件绝不弹框**（弹框时机由调用点决定，而调用点可能在最差的位置）。
- **根因**：**"需要决策"这件事被推迟暴露，比决策本身更伤害体验**——那时用户已被排除在上下文之外。
- **启示**：**该问的要问，但要在人还有上下文的时候问。**

## Y5. 不要"拒绝服务"——告知风险，让用户决定

- **场景**：我提议加 `must-not-degrade`（测量类插件在档位不满足时拒绝服务）。作者反驳：
  > "是否必须存在 must-not-degrade，还是说我只要把风险告知给用户就行"
  > "开发插件的工作，这种显然是需要强模型才能做好的，但用户只有弱模型……或者说用户就是很强的程序员，他用 gpt3.5 也能做"
  > "那 agent 一直拒绝服务也太奇怪了。完全可以给用户展示出提示的内容'建议使用更强模型，当前模型可能影响输出结果'的后果"
- **决策**：**建议而非要求；告知而非阻断。** 去掉 `must-not-degrade`，去掉工具隐藏。
- **根因（我的补充）**：硬拒绝建立在"插件知道任务做不成"这个**它不可能有的知识**上；
  而且它等价于**用拒绝惩罚用户**——与契约 §3.1 的反奖惩立场同构。
- **保留项**：**降级必须留痕**（不是惩罚，是出处：仪器降级会让"策略失败"被误判）。
- **启示**：**我把工程习惯带进了设计**（"不满足前置条件就拒绝"是常见做法），
  而作者是从"用户该有什么权利"出发的。这类纠正值得记住。

## Y6. 降级不只是失败模式，它是**生态的生长机制**（本日最重要的设计输入）

- **场景**：作者在讨论中提出一个情景，我认为它是 LH 最重要的设计输入之一：
  > "有一个抽象程度比较高的插件，他能完成很全面的功能，但需要很强的智能，但这时有一些专业人员或者开发者对这个任务做了拆解，拆解出了若干的小插件，每个插件完成各自的部分，**使得低智能的模型通过插件的组合也能完成复杂的任务了，这是非常好的生态情景**"
  > "一个强的主导 agent，甚至能够发现不同的插件组合去完成某个工作的路径，**就是有什么材料做什么菜**"
- **决策**：用户面对"档位不足"时有**四种**选择，而不只是"接受 / 放弃"：
  照常做 / **换一条拆解路径** / 去配置模型 / 终止。
  因此 agent 问的时候该**给出路径选项**，而不是问一个是/否题。
- **推论**：agent 需要知道"有哪些插件、各自需要什么档位"——**插件清单成为规划输入**，不只是执行细节。
  **能力缺口会催生专门插件。**
- **启示**：这条把"降级处理"从一个防御性话题变成了**产品的生长机制**。
  AI 自己想不到这一层——它是从"生态该怎么长"出发的。

## Y7. 以后的插件主要由 agent 写，所以"方便人写代码"的设计不必要

- **场景**：作者说明后续的开发模式：
  > "插件开发时基本不会是人来写的代码，我之后会立即开发'**lh 插件开发**'相关的插件，插件内包含 schema、接口协议以及一些可能的 skills，总体来说还是人与 agent 对话，agent 调用'**lh-plugin-develop**'将用户的意愿、学习方法落地成插件"
  > "所以很多为了方便人写代码的设计不是很必要"
- **决策**：设计插件接口时，**优化对象是"agent 能否一次写对"，不是"人写起来方便"**。
- **根因**：开发者是人还是 agent，会改变"什么算易用"。
- **启示**：这条会影响后面每一个 schema 的设计取舍——**它是设计前提，不是偏好**。

## Y8. 反复重启可以接受，不必为它中断开发

- **场景**：我因为连续三次让作者重启 dsh 而提议"先停下模型这条线，专门把重启问题解决"。
- **决策**：作者答：
  > "重启问题其实没那么大，也不必须修，我已经重启并在 lh 会话中说话"
- **根因**：AI 高估了这个摩擦对他的影响。
- **启示**：**不要用自己推测的摩擦感去改变优先级。** 该问的时候问一句，比自行调整方向便宜。

## Y9. 文档工作：直接写，不必汇报"更新了什么"

- **场景**：作者要求总结今日经验并更新协作者建模时，加了一句：
  > "不需要告诉我更新了什么，直接写文档"
- **决策**：文档类工作**直接执行**，汇报只在有需要他决策/知悉的事项时给。
- **启示**：这和前一天（`2026-09-15-协作方式反馈.md` 的 Y3）"产出是默契，不是文档数量"是同一个方向：
  **过程汇报要有信息量，否则是噪声。**
