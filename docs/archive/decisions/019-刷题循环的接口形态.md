# ADR-019：刷题循环——同一份题、两种界面、一个不可绕过的作答

- **背景**：作者定了下一步：*"我们不妨先把 lh 做成刷题工具，把做题这个循环给它做好了。"*
  对象与接口（ADR-017/018）已冻结，但**循环是断的**：agent 手上没有"取题"这个动作，
  也没有"取回解析"的动作。本 ADR 记录补上循环时做的决定。
- **作者对两条路的要求（原话）**：
  *"两条都要，但是两条路径不是独立的，我赞成对话可以先做，用于考验工具调用，但至少要有打字以外的输入方式，
  比如说选择题的点击，刷题最好能有比对话更不容易误触、更流畅、更沉浸的方式。"*
- **作者对 OCR 路径的判断（原话）**：*"目前的题目还都是图片的，用 llm 的多模态读图也有些贵，
  所以可能还需要一个 ocr 组件先把图片转文字，然后 llm 对文字做分块和归类。"*

## 决定

**1. 题的线格式是结构化的，不是一段拼好的文本。**

工具返回的每题形如：

```js
{ id, kind, stem, options: [{ label: 'A', text: '1954年' }, …], topics, source }
```

**为什么这不是"多此一举的结构化"**：作者要求同一道题未来要被**两种界面**使用——
文本（念出来）与可点击（按钮）。如果工具返回一段拼好的字符串，
点击界面就得回头解析那串文本；**那是脆弱的耦合，而且一旦措辞改了会静默失灵**。
结构化之后：
- 文本界面把 `{label, text}` 念成 `A. 1954年`；
- 图形界面把同一个 `label` 渲染成按钮。

**契约不需要改，界面可以后加。** 这是"两条路径不独立"在接口层的落地。

**2. "取题"与"取答案"是两个不同的动作，且答案只在作答之后才给。**

- `get_questions` 返回的题**不含** `answer` / `accept` / `analysis`；
- 取答案只能通过 `submit_answer`（见决定 3）。

**为什么这是接口设计而不是纪律**：如果把整道题（含答案）交给模型去念，答案就进了上下文，
它可能顺口说出来，或在后续推理里被"看见"。更实际的风险是：
**出题的工具一旦返回答案，任何一次调用都会污染整个循环**，而这种事在日志里看不出来
（工具调用是成功的）。所以"去掉答案"是 `practice.js` 里 `toPresentableQuestion` 的职责，
不是调用方的自觉。

**3. `submit_answer` = 记录 + 判分 + 揭示，合为一个不可分割的动作。**

**为什么不是"记录"和"揭示答案"两个工具**：拆开会打开一个缺口——
agent 可以先调"揭示答案"、再把答案念给学习者；或者先知道答案再"引导"作答。
**合成一个动作，这个缺口在结构上就不存在**：拿到解析的前提是作答已经被写进事件日志。

这是"用接口形状防止误用"，而不是"在提示词里请求模型别那样做"（契约 §1.1：
内核拥有语法，插件拥有判断——而"不许先看答案"是语法，不该指望模型自觉）。

**4. 出题顺序是纯函数，且本版只有机械顺序：`sequential` / `random` / `unseen` / `missed`。**

- `sequential` **不改动题库文件的顺序**。理由：题库是**人的材料**，它的顺序通常有意义
  （按章节、由易到难）。按 id 或字母重排会把那个意义丢掉，学习者会觉得"题是乱的"——
  那是产品问题，不只是排序问题。
- `unseen` / `missed` 在没有相应记录时**退化为 `sequential`**，并如实说明退化了。
  返回空会让"想继续练"变成"工具说没题了"，而实际上题都在。
- 未知的 `order` 值退回 `sequential` 并留痕，**不抛错**：抛错会让一次笔误变成整个循环中断。

**5. 本版刻意不做间隔重复（FSRS）。**

契约 §8.4-A 说 FSRS 直接采用 `ts-fsrs`。**但那要等作答数据够。**
现在做等于在没有数据时发明参数，而且会把"顺序"这个概念的调试难度抬高一个量级。
当前版本的目标是**确定性、可复现、出事能查**——等真实作答数据攒起来再换。

**6. 进度统计以题库为分母，且人的作答与模型的作答分开计。**

- `coverage` = 做过的题 / 题库总题数；
- `accuracy` **只算 `source === 'human'` 且判得了的**（ADR-018 决定 5、6）；
- `llm_attempts` 单列，并在渲染里明说"未计入正确率"；
- `human_unjudged` 单列，不进分母；
- `missed_recent` 按"**最近一次**答错"判定——答对之后就从错题本里消失。
  这是错题本的正确语义：**它反映"现在还不会"，不是"曾经错过"**。

**7. 工具契约同时为"文本界面"和"点击界面"设计，不依赖点击通道是否可用。**

宿主提供了 `ctx.userQuestions`（`@deepseek-ai/dsh-user-questions`），
是一个 **UI 支撑的服务**：`ask({ questions })`，
每项支持 `options: [{ label, description }]`、`multiSelect`、`detail`，
以及一个**开放的呈现意图标签** `intent.kind`（未知标签由 UI 退回通用选项列表，编码不变）。

这意味着"选择题点击作答"有现成通道，且**将来做专用界面不需要改协议**。

**但有一个未验证的前提**：`ctx.userQuestions` 由宿主面（`dsh-web-app`）提供，
而 preset 是 agent 作用域（ARCHITECTURE §0.1 约束 5）。**它能否被 preset 插件注入，尚未实测。**

**所以本条决定是**：不把它作为循环成立的前提。工具的线格式已经带 `label`，
点击界面无论由 `userQuestions` 还是由将来的壳体前端实现，都吃同一份数据。
**先让循环在对话里成立，点击作为增量加上去，不加也不返工。**

## 依赖的前提

1. **题目抽取尚未实现。** 本 ADR 只做"题目进来以后怎么用"。抽取路径见下。
2. **单题难度/区分度未知**，所以顺序策略不做加权——没有数据时加权是编参数。

## 抽取路径（记录判断，不作为本 ADR 的决定）

作者指出题集是图片型的，多模态读图贵，所以路径是
**OCR 先转文字 → LLM 对文字做分块与归类**。这条路径的一个直接好处：
**OCR 的错误是肉眼可见的**（错字、断句），而多模态模型把图读错时往往"读得很像样"——
前者能抽查，后者不能。

已知可离线跑的中文 OCR 方案（本轮检索，供将来选型，未实测）：

| 方案 | 适合什么 | 出处 |
|---|---|---|
| PaddleOCR | 中文识别的主力，批量 PDF/图片 | [PaddleOCR 批量处理 PDF 与图片](https://cloud.baidu.com/article/3676833#1) |
| MinerU | **PDF → Markdown/JSON，保留版式结构**（题集是分栏排版时这条关键） | [MinerU 说明](https://github.com/BerryZhu-ozim/OCR_Server/blob/main/README_zh-CN.md#2#2#2) |
| Umi-OCR | 完全离线的图形界面，批量导入、可排除水印区域 | [Umi-OCR](https://github.com/lllrrr2/Umi-OCR#1) |

**选型不该现在做**：OCR 质量必须拿 `D:\考公资料` 里的真实扫描件测，
而那是下一步的事。本条只是把"要测什么"记下来。

## 怎么知道它错了

| 决定 | 失效信号 |
|---|---|
| 题的线格式结构化 | 出现"下游只想拿一段文本"的需求 → 加一个**投影**去拼，不改本字段（同 ADR-017 的答案数组） |
| 取题不含答案 | 学习者在作答前就知道了答案 → 先查是哪一步把题交给了谁；**不要靠加提示词解决** |
| 提交=记录+揭示合一 | 出现"想只看答案不记作答"的正当需求（如学习者要求直接讲解）→ 那时应加一个显式的、**记为 llm 作答**的路径，而不是拆开提交 |
| 顺序是纯函数 | 出现"顺序必须由模型临场判断"的场景 → 那是策略层的事，不是本层的；本层保持机械 |
| 不做 FSRS | 作答数据攒够（同一题多次作答、跨天）之后仍不换 → 复习效果无从谈起 |
| 统计按题库为分母 | 出现跨题库的"总进度"需求 → 那是另一个口径，另加一个工具，不要改这个的分母 |
| 不依赖点击通道 | 若最终 `userQuestions` 可用且好用，却仍没人做点击界面 → 说明"打字以外的方式"没被当成需求对待 |
| 抽取走 OCR→LLM | OCR 文本错到 LLM 分不出题目边界 → 先修 OCR，不要用更强的模型去补 |

## 未做的事

- **题目抽取**（OCR / 版式解析 / 图表题）：未实现。
- **间隔重复调度**（FSRS）：未实现，见决定 5。
- **点击式作答**：通道已查明存在（`ctx.userQuestions`），但**未实测 preset 作用域能否注入**，未实现。
- **知识点体系**：~~仍待定案~~ → **词的形态已定并落地**（两轴封闭词表，见 ADR-021 结论七），
  但**题库里只有 13/49 道题带标签**（试点产物缺文件出处，只能保守匹配，见 ADR-021 结论八），
  所以按知识点出题目前取到的是少数题。
- **自适应难度 / 区分度**：未实现（没有数据）。

## 修订 10（2026-09-19 晚）：两条路的分工**不能只写在工具描述里**

### 现场（实测，不是推测）

作者反馈：*"按知识点出题看起来是做到了，但也有可能是模型自身的能力，
而且出的题目并不是以刷题卡的形式。"*

从 LH 事件流的 `lh/trace/observed`（`tool/call`）查到那次会话的真实调用：

```
14:24:49  tool/call  get_questions
14:25:13  tool/call  get_questions
```

**`start_practice` 一次都没调。** 所以：没有卡片、题被念成文本、
**作答不进事件日志**——正是决定 3 与决定 7 要防的那种用法。

### 根因

1. **措辞不对称**：`start_practice` 的 `topic` 描述只有一句"慎用"，
   而 `get_questions` 刚拿到词表与归一化说明。两个工具"都能按知识点出题"，
   而模型选了说明更具体、更不像在劝阻它的那个。
2. **规则放错了位置**：`get_questions` 的描述里**早就写着**
   "学习者要刷题时一律调 `start_practice`"（上一次同类事故后补的）。
   **它没被遵守**——因为工具描述是**用到它时**才读到的，
   而"这次该走哪条路"是**计划阶段**的判断（同一发现见 ADR-016 决定 2）。

### 改了什么（不推翻本 ADR 的任何决定）

| 改动 | 位置 |
|---|---|
| 两条路的分工与**各自代价**写进**运行时上下文**（每次组装都出现） | `lh-question-bank/context.js` → `lh:practice-routing`，order 117 |
| `start_practice` 的 `topic` 描述补上词表与归一化（与 `get_questions` 对称，且从 `topics.js` 生成） | `index.js` |
| `get_questions` 的**返回正文**加一句"本工具不写作答记录，要进入刷题请改调 `start_practice`" | `index.js` 的 render |
| `topic` 的归一化收进 `sanitizeSelection`（卡片与工具共用的唯一校验点） | `practice.js` |
| "若没看到卡片，指向右下角兜底入口"写进 `start_practice` 的返回 | `index.js` 的 render |

**决定 1（去常驻按钮）、决定 7（卡片是入口）、决定 3（提交=记录+揭示）都没有变。**
变的只是"怎么让模型在两件事之间选对"。

### 怎么知道这次改错了

| 失效信号 | 说明 |
|---|---|
| 工具调用记录里 `get_questions` 又出现在"刷题/给N题/按知识点出题"这类说法之后 | 上下文那条规则也没被遵守 → 该上**结构解**（见下），不要再加大段文字 |
| 上下文出现后，模型把"进入刷题"也当成"就在对话里问" | 两条路的判据写得还不够机械 → 改成更靠近决定 3 的形态：由**接口**而不是判据来区分 |

### ⚠ 仍然没解决的一层（如实记下，属承重决策）

以上全部是**"用文字请模型照做"**。而本 ADR 决定 3 自己立的原则是
**"用接口形状防止误用，而不是在提示词里请求模型别那样做"**。

真正的结构解是让 `get_questions` 在"进入刷题"的意图下**不可用**——
例如它只允许一次一道、并且必须显式声明"就在对话里问"。
但那会牵动**决定 7**（两条路径都要成立、且决定 4 的 `count` 语义正是为对话路径设计的），
所以它是一次**承重决策**，需要作者先定"要不要为了结构保证而收窄对话路径的能力"。
**本轮不动它，记在这里。**
