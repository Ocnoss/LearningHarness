# ADR-024：部署流程（拉取并部署）与插件的"开发类"归类

- **背景**：作者提出两条具体的事——
  1. **初版获取方式**：*"先在 dsh 官网，用 dsh 的命令 `npx @deepseek-ai/dsh web` 启动 dsh 之后
     （我这里忘记 dsh 能不能自动安装 node 依赖，就算不能，做个视频教用户安 node 也行），
     配置好模型后和 dsh 任意模式的模型说**帮我拉取并部署 LearningHarness**，
     然后把我的仓库地址粘上去，模型就会帮他部署好 lh，重启后就可以使用 lh 的功能。"*
  2. **插件管理**：*"插件越做越多，如何进行插件管理……我是否需要适时 integrate，
     我本来认为我需要，但是想想我可以完全将这些交给 agent 来考虑，
     我最直接想表达的是**对于 lh 插件的开发、测试、检查、debug 应该作为一类插件归类起来**。"*

## 一、当前状态离"可部署"有多远（实测）

**4 处绝对路径写死了作者自己的机器：**

| 文件 | 写死的东西 |
|---|---|
| `plugins/lh-event-store/store.js` | `D:\LearningHarnessv0.1\data` |
| `plugins/lh-model-tier/tier.js` | `D:\LearningHarnessv0.1\data\model-tiers.json` |
| `plugins/lh-question-bank/signal.js` | `D:\LearningHarnessv0.1\data\practice-signal.json` |
| `plugins/lh-practice/index.js` | `D:\learning Harness test`（工作区） |

**外加 agent preset 里的 5 行插件路径也是绝对的。**

**而且这不只是"为了别人"**：今天这些路径里就有一个**已经错了**——
`D:\learning Harness test` 是作者改名后的工作区，而别的代码里还留着 `LearningHarnessv0.1`。
**同一个项目里两套写死的工作区路径**，靠人记住哪个对。

## 决定

### 1. 先做"路径无关"，再做部署。它是前置条件，不是 Cleanup

**规则（写进 `PLUGIN_CONTRACT.md`）**：
- **插件不许写死任何绝对路径**；LH 自己的数据目录从**插件自身的位置**推出来
  （`import.meta.url` → `plugins/` → 仓库根 → `data/`）。
- **工作区路径不许写死**：它必须来自**请求上下文**（工具调用的 `exec.agent.session.header.cwd`）
  或显式配置；**HTTP 路由没有会话上下文**，所以它必须由调用方带进来或落成配置项，
  **不能有一个"默认指向某人的工作区"的常量**。

**为什么这条比它看起来重要**：写死路径不会让插件"跑不起来"，
它会让插件**在别人的机器上跑错目录**——那是静默的错误，比崩溃更难发现。
（这与"环境变量惰性求值"是同一条：**指向外部资源的东西，不能在加载时固化。**）

### 2. 部署用一个专门的插件，而它必须受"启动安全"约束

**流程**（作者的设想，我认可它作为产品形态）：

```
用户：npx @deepseek-ai/dsh web  →  配好模型  →  对模型说
      "帮我拉取并部署 LearningHarness，仓库是 <URL>"
  → agent 调 lh-install 的工具
  → 它：克隆 → 装依赖 → **跑五道闸门** → 写 preset/profile 行 → 告诉用户重启
```

**但它必须满足三条硬约束**（否则部署本身就会变成那个"起不来"的事故）：

| 约束 | 为什么 |
|---|---|
| **先验证，再写入** | 部署的产物是"要加载进宿主的东西"。**没跑过闸门就写 profile 行 = 拿用户的 dsh 做实验** |
| **失败要可回滚** | 它要改 `.dsh` 里的 preset 与 profile。改动前先备份；失败时恢复 |
| **幂等** | 用户可能重复说"部署"；重复执行不许产生第二份 preset 或重复的 insert 行 |

**另外两件必须诚实告知的事**（写进部署输出，不藏）：
- **它需要联网**（`git clone` + `pnpm install`）；
- **它会改 `~/.dsh` 下的文件**——那是用户的宿主配置，不是 LH 的地盘。
  **这件事必须发生在用户明确同意之后**，而不是"顺手做了"。

**关于 dsh 会不会自动装 node 依赖**：作者没记清，**我不猜**。
部署工具应当**检测并报告**（node 版本、pnpm 是否存在、`npx dsh` 是否可用），
缺什么就明确说缺什么——**而不是试图自动安装**（那是系统级动作，超出"部署一个插件"的边界）。

### 3. 不做 integrate。做的是"给每个插件一份可被机器读的自我描述"

作者问"是否需要适时 integrate"，并自己给出了更好的答案（*"可以完全将这些交给 agent 来考虑"*）。
我同意，并补一个理由：

**合并插件解决的是"人记不住"，而这个项目的假设恰恰是"人不记，agent 记"**
（作者早前定过：*"插件开发时基本不会是人来写的代码"*）。
所以合并会把耦合代价付出去，却解决一个不存在的问题。

**要做的是**：每个插件的 `package.json` 里加一段**声明式**的 `lh` 字段：

```json
"lh": {
  "kind": "kernel" | "recorder" | "capability" | "ui" | "dev",
  "summary": "一句话说它做什么",
  "inject": ["tools"],                     // 需要的宿主服务
  "provides": { "tools": ["get_questions"], "contexts": ["lh:model-tiers"] },
  "depends_on": ["@lh/event-store"],       // 跨插件依赖
  "loads_at": "preset" | "profile",
  "verified": { "gates": true, "live": false }   // **哪些验证过了**
}
```

**为什么这正是"list"需要的**：agent 说"现在有哪些插件能干什么"时，
需要一个**机械可枚举、不会过期**的来源。
读 `package.json` 比读文档可靠（文档会忘更新，package.json 是包的一部分）。
`verified` 那个字段尤其重要——它让 **"验过什么、没验过什么"** 变成可查询的事实，
而不是散在经验文件里。

### 4. "开发/测试/检查/debug" 归成一类插件

作者的原话正是这一条，我完全同意。具体是：

**新建 `plugins/lh-devkit/`（`kind: "dev"`）**，它**不实现**已有能力，而是：

| 它做什么 | 复用 |
|---|---|
| 把五道闸门作为**一组**跑，给出统一结论 | `import` 现有的五个 `scripts/check-*.mjs` 的**逻辑**（不是重写） |
| 注册工具让**agent 自己**能跑这些检查 | `ctx.tools.register` |
| 记录"每个插件最后一次验证的状态" | 写入一个 `data/verification.json`（可派生缓存，不是事实源） |
| 提供"新增/修改插件后的标准动作序列" | 那正是 `PLUGIN_CONTRACT.md` 的 review 清单 |

**为什么它必须存在（而不是继续叫 `scripts/`）**：
`scripts/` 是**给作者用的**；而作者的判断是**这些检查要进每个插件开发任务**。
也就是说**agent 必须能自己跑它们**——那就必须是一个插件（agent 只能通过工具调用东西）。

**它是 `kind: "dev"` 的第一个成员**，而它天然是 `lh-plugin-develop` 的**执行臂**：
- `PLUGIN_CONTRACT.md` 是**前置知识**（写之前读）
- `lh-devkit` 的工具是**验证手段**（写之后跑）
- 两者合起来才是"agent 能自己写插件"这件事的完整前提

## 依赖的前提

1. **路径无关**要先做完（决定 1）。否则部署出来的东西在别人机器上会指向错目录。
2. 部署需要用户**先配好模型**（宿主凭据在 `~/.dsh/.credentials.yaml`）——
   那是 dsh 的既有流程，LH 不介入。
3. `lh-devkit` 的工具需要**能读到插件源码**（它在 profile 层，有 fs；但要注意它读的是**安装副本**还是**源码**——
   本轮闸门已经证明这两者会不一致，见 ADR-023 的决定 1）。

## 怎么知道它错了

| 决定 | 失效信号 |
|---|---|
| 路径无关 | 出现"在我机器上对、在别人机器上错目录"的报告 → 说明还有写死的路径（**加一条闸门去扫**） |
| 部署插件先验证再写入 | 部署后 dsh 起不来 → 说明它没跑闸门，或闸门没覆盖那一类 |
| 部署要求用户同意改 `.dsh` | 用户抱怨"它擅自改了我的配置" → 同意必须是**显式一步**，不是附带 |
| 不做 integrate | 出现"两个插件必须同步改"的频繁需求 → **那时才是真的该合并**（而不是现在猜） |
| 每插件一份 `lh` 自我描述 | 字段长期与实际不符 → 需要闸门校验（**声明与 `provides` 对不上就红**） |
| `lh-devkit` 归开发类 | 它开始实现业务逻辑 → 越界了，它只该**编排检查**，不该有判断 |

## 未做的事

- 路径改写：**未做**（本 ADR 只定规则）。
- `lh-install`（部署插件）：未做。
- `lh-devkit`：未做。
- 各插件 `package.json` 里的 `lh` 字段：未加。
- **dsh 能否自动装 node 依赖**：未验证（作者也没记清）。部署工具应当**检测并报告**，不猜。
