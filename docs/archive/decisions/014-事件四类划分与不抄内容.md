# ADR-014：事件的四类划分、"可派生不进日志"、与保留原始轨迹

- **背景**：在动手写第一批记录器与分类器之前，需要先定死"什么进 LH 事件日志、什么不进"。`ADR-012` 已定物理形态与信封字段，但没定**内容边界**——而记录器一旦写下去，改分类规则的代价大得多。
- **触发讨论的两个问题**（作者提出）：
  1. 是否必须记索引，还是可以直接使用宿主已有的会话轨迹？
  2. 若提示词与采样参数固定，是否必须完整记录 LLM 的输出，还是可以跳过、只记针对输出的更高层抽象？

## 已证实的量级事实（决定"要不要为省空间而设计"）

以作者本机最大的一个会话日志为样本实测：

| 指标 | 值 |
|---|---|
| 压缩后 | 4,946,267 字节 |
| 解压后 | 10,234,856 字节 |
| 压缩比 | 2.1 : 1 |
| 事件数 | 17,298（其中 **91% 是流式 chunk**：reasoning-chunks 7312、tool-call-chunks 3389、assistant/chunk 2885、text-chunks 2130） |
| 真正有语义的事件 | 几百条（`assistant/message` 267、`tool/call` 276、`tool/result` 276） |
| 全部 31 个会话压缩后合计 | 13.79 MB |

据此推算一个自学者的规模：一天 20 轮对话 ≈ 160 KB 纯文本 → **一个月约 4.8 MB、一年约 58 MB**（未压缩），压缩后约 25–30 MB。**达到 1 GB 需要约 17 年连续记录。**

**结论：存储不是约束。** 因此不为省空间做设计；只有在"结构更清楚"或"断言可追溯"有收益时才改变记录方式。

## 决定

**1. 事件按四类划分，边界是"输入 vs 派生"，不是"大小"。**

| 类别 | 例子 | 处理 | 理由 |
|---|---|---|---|
| **输入** | 学习者的问题、**刷题结果等结构化输入** | **原样记** | 可复现性救不了"没有输入"；用户数据不可再生 |
| **宿主已跟踪的原始输出** | LLM 回复文本、思考过程、工具调用 | **不抄内容，只记坐标** | 宿主已持有权威副本；抄一份只会分叉 |
| **高级抽象** | "他在解释"、"深度是重组" | **记，它本身就是内容** | 这是 LH 真正要存的东西（契约 §4.1、§3.1） |
| **可派生缓存** | 编译好的上下文、分类结果缓存 | **不进日志；存物化视图** | 见决定 2 |

**2. 可派生的东西不进事件日志。**
- 理由：**日志一旦能存缓存，它就不再是事实源**——你会开始删它、重建它、与它不同步。
- 推论：缓存必须能被**整体丢弃并重建**。若某样东西丢掉就再也做不出来，它就不是缓存，而是事件。

**3. 保留原始轨迹：宿主继续持有全文，LH 只记指针。**
- LH 记录器只索引**语义事件**（`user/message`、`assistant/message`、`tool/call`、`tool/result`），存 `(sessionId, seq)` 与少量元数据。
- 依据：`seq` **只存在于语义事件上**，流式 chunk 没有 seq——所以"只索引语义事件"既是最省的选择，也恰好是可寻址的选择。
- 成本：按 240 天 × 20 轮 × 4 条 ≈ 2 万个指针 × 数十字节 → **不到 1 MB**，可忽略。
- **前提（已验证）**：宿主日志能被独立读取，不需要 dsh 在场。文件是**多个 zstd 帧顺序拼接**（Node 的 `zstdDecompressSync` 只解第一帧，会得出"解压后只有 177 字节"的假象），需逐帧解；实测 4.7 MB / 14,143 帧 / 17,298 事件，耗时 247 ms。

**4. 不因为"输出可能可复现"而删除原始轨迹记录。**
- 作者判断：LLM 输出的随机性作为**底层描述**有足够容错率，可在不干扰上层断言与推理的前提下丢弃——**这个判断被接受**。
- 但它**不构成省略记录的理由**，因为：
  1. 容错率来自**断言的出处链**，不来自原始文本。需要可追溯时用指针（便宜），不需要时不读（免费）。
  2. 即使 temperature=0，同一提示词在不同批次/硬件/推理优化下也可能给出不同输出。故**可复现性可以是省计算的理由，不能是省审计的理由**。
  3. 存储不是约束（见上），而"没记"不可逆（契约 §1.3）。
- 因此：**记着，但默认不读。** 这是低成本的可选项，不是必须消费的成本。

**5. 索引用于"指回证据"，不用于"避免重复存储"。**
- 宿主已经避免重复存储了。索引存在的理由是：分类器要判断"他在第 5 轮的行为"时，需要一个能指回原文的坐标。

## 依赖的前提

1. 宿主保持 append-only 会话日志与 `seq` 的稳定性（契约的"事件不动纪律"在宿主侧同样成立）。
2. 宿主会话日志的**存储格式**在未来升级中可被读取。**已知风险**：`SESSION_FORMAT_VERSION` 钉在 `0`，升级可能改变打包方式。**缓解**：LH 只记坐标、不抄内容，因此格式变化只影响"取回原文"这一步，不影响 LH 自己的事件日志。
3. 结构化输入（刷题结果等）会成为 LH 事件的主要形态，而它**不需要索引**——因为它本身就是最终形态的事件。

## 怎么知道它错了

| 决定 | 失效信号 |
|---|---|
| 只记坐标、不抄内容 | **取回器不好用**（解帧或按 seq 定位失败、耗时不可接受）→ 该路线不成立，改为抄内容 |
| 可派生不进日志 | 出现"必须靠日志才能重建的东西"（说明它不是缓存而是事件，分类错了） |
| 保留原始轨迹、默认不读 | 从未有任何断言或复盘真的用到取回原文 → 说明坐标是多余的装饰，可考虑去掉指针只留摘要 |
| 四类划分 | 出现无法归入四类的数据；或某类数据的实际处理与表中相反（说明边界定错了） |

## 补充决定（实施坐标记录器时踩出来的）

**6. preset 内的插件不得依赖"服务"跨面通信；共享逻辑用直接 import。**

- **现象**：`lh-recorder-trace`（preset 行）声明 `inject: ['lhEvents']`，想用 `lh-event-store`（profile 行）提供的服务。结果 **preset 挂载失败**，而挂载失败会连带弄坏该会话——错误为：
  `preset "lh" failed to mount: 1 row(s) did not activate: lh-recorder-trace: waiting for lhEvents`。
- **根因（两层，都要记住）**：
  1. **实现错误**：Cordis 的 `Service` 子类**必须在构造函数里调用 `super(ctx, name)`** 才会注册（`cordis/lib/types/service.d.ts:38`）。我写了一个带 `static name = 'lhEvents'` 的普通类、用默认构造函数，**服务从未被注册**——记录器等的是一个不存在的东西。
  2. **更根本的约束**：即便正确注册，preset 是 **agent 作用域**，也解析不到宿主 **root realm** 的服务。`dsh-agent-presets` 的 `mount()` 正因此拒绝"往 root realm 发布服务"的行（"a preset service must sit behind an `isolate` realm or move to the host composition"）。**"preset 插件用服务调 profile 插件"这条路被宿主堵死了。**
- **解决**：`store.js` 是纯 JS、只依赖 Node 内置模块，因此 preset 行改为**相对导入**它（`import { LhEventStore } from '../lh-event-store/store.js'`），不再需要任何服务。
- **已知代价**：profile 面与 preset 面各装载一份 `store.js`，会有两个模块实例、**写同一个文件**。同一文件以 append 模式逐行写入，每次写入是一个 write 调用，故不会交错——这对单机单用户成立。若将来出现并发写入需求，应改为单一写入者（例如把写入收进 host 面的服务），而不是继续直接 import。
- **失效信号**：出现跨面共享可变状态的需求（内存缓存、连接池等）时直接 import 不再够用 → 那时应把该状态放到 host 面并按 `isolate` realm 规则设计，而不是设法绕过 mount 的审计。

## 一条从本次故障得到的通用教训

**挂载失败的代价不是"插件不工作"，而是"整个会话不可用"。**
preset 的行未激活会让 `mountPreset` 抛错，而抛错发生在 agent 创建时——
于是该会话既建不了、已存在的会话重进也失败。因此：

- **preset 行的任何依赖都必须是"加载时就能确定可用"的**，不能是"将来某刻会可用"的；
- 新增行之后，**必须在真实会话里验证一次**，而不是只看 `discoverPresets` 的 `broken` 字段——
  后者只做 YAML 形状检查，**不会**发现"行在等一个不存在的服务"。

## 三处 specifier 解析路径（补全，别记成两处）

早前我记的是"profile 行与 preset 行两处不同"，**这个记法不完整**——后来在 dev profile 上又踩了一次。完整的是**三处**：

| 加载位置 | 裸包名 | 相对路径 | Windows 绝对路径 |
|---|---|---|---|
| **preset 行**（`agent.cordis.yml`） | 取决于宿主是否设上 base（实测常失败） | 以 preset 目录为基 | ✓ **可用**（`dsh-agent-presets` 转成 `file:` URL） |
| **profile 的 `cordis.patch.yml`** | 从宿主安装目录解析 ✓ | 以 profile 目录为基 | ✗ **失败** |
| **直接 `node` 跑文件** | 从该文件向上找 `node_modules` | 同左 | ✗ 失败（需 `pathToFileURL()`） |

**profile 行失败的原文**（在 dev profile 上实测）：

```
failed to import loader entry lh-event-store (...\index.js):
Only URLs with a scheme in: file, data, and node are supported by the default ESM loader.
On Windows, absolute paths must be valid file:// URLs. Received protocol 'd:'
```

**结论**：给 profile 的 patch 行写路径时，**一律用 `pathToFileURL()` 生成 `file://` URL**，
不要写 `D:\...`。这条已在 `scripts/dev-watch.mjs` 的实现与注释里固化。

**为什么值得单独记**：同一个"绝对路径"在 preset 行能用、在 profile 行不能用，
而两处的报错信息完全不同（一处静默解析失败、一处明确报 URL scheme）。
若只记"两处不同"，下次换一个加载位置又会踩；**记成一张表，才可以一眼查。**
