# ADR-016：模型档位——建议而非要求，告知而非阻断

- **背景**：LH 需要"多模型分工"：对话用强模型、分类与摘要用便宜模型。但 dsh 的模型选择是**会话级**的，且所有模型在宿主里**同级无区别**。这需要在宿主 adaptor 之上加一层"用途 → 模型"的映射。
- **做这一层的过程中，作者连续四轮纠正了 AI 的方案方向**（每次都是同一个类型的问题，见 `docs/COLLABORATOR_MODEL.md` A8）：从"插件写死模型名"、"不满足就拒绝服务"、"隐藏做不了的工具"、"中间件弹框问用户"，逐一被否。
- **已实测的事实**（2026-09-16，web profile）：
  - preset 作用域的插件**能**拿到 `ctx.llm`，且能看到全部 3 个 provider；
  - 对 `deepseek-official`（`deepseek-flash`）与 `xiaomi-token-plan-ams`（`mimo-v2.5-pro`）**各发过一次真实调用并收到回复**；
  - `usage` 随流返回，所以 token 成本可记入事件；
  - 宿主自己就有"政策类上下文"的注入形态（`dsh-sandbox-policy` 的 `sandbox:policy` order 110、`dsh-user-approval` 的 `approval:policy` order 115），本层的档位可用性照此形态注入（order 116）。

## 决定

**1. 插件声明"档位"，不声明模型名。**
```js
export const recommend_model = 'flash'   // 或 'balance' / 'max'
```
理由：**"哪个用途用哪个模型"是使用者的决策，不是插件的属性。**
插件写死模型名的话，换一次模型就要改所有插件。档位到模型的映射写在一处配置
（`data/model-tiers.json`），每个档位是**候选链**（按优先级试）。

**2. 档位是"建议"，不是"要求"——不满足时不阻断。**
- 理由：插件只知道自己建议了强模型；**"弱模型做不了这件事"是它不可能有的知识**。
  同一个插件、同一个弱模型，简单任务够用、复杂任务不够；同一个任务，强程序员用弱模型也能成事。
- 因此**不设 `must-not-degrade`**，**不隐藏工具**。那两者都等于"系统替用户判断你做不到这件事"，
  而且等价于**用拒绝惩罚用户**——与契约 §3.1 的反奖惩立场（"把数据显示给用户，而非扣分"）同构。

**3. 告知而非阻断：档位可用性写进运行时上下文。**
- 形态照宿主政策类上下文；内容只陈述事实与建议，**不下命令**：
  ```
  模型档位（插件可按档位建议模型；这是建议，不满足时不阻断）：
  - flash：xiaomi-token-plan-ams / mimo-v2.5-pro
  - balance：deepseek-official / deepseek-flash
  - max：deepseek-official / deepseek-flash
  若某任务建议的档位当前不可用，请在计划阶段告知用户并给出选择：照常执行（质量或成本可能受影响）、
  换一条插件组合路径、去配置对应模型、或终止。
  ```
- 理由：让 agent **在计划时就知道**，从而能在**自然边界**问用户。

**4. "问用户"由 agent 做，且在自然边界；中间件绝不弹框。**
- 作者给的体验论证：agent 调工具→立刻发现问题→马上问（两三行字）**体验好**；
  但 agent 计划 5 分钟、动工之后才发现要审批，**用户已经被排除在上下文之外，他没法决定**。
- 因此 `lh-model-tier` 用 `ctx.approval` 是**错的**：弹框时机由调用点决定，
  而调用点可能在**工作流深处**——那正是最差的时机。
- **问的时候不能只问是/否**，要给出路径选项（见决定 5）。
- `ctx.approval` 保留给宿主的**原生闸门**（工具审批、沙箱升级），不进这条路。

**5. 降级是**生态的生长机制**，不只是失败模式。**
作者提出的情景（本 ADR 最重要的一条设计输入）：

> 有一个抽象度高的插件，需要很强的智能；但有人把任务拆成若干小插件，
> 每个完成各自的部分，**使得低智能的模型通过插件的组合也能完成复杂的任务**……

因此用户面对"档位不足"时有**四种**选择：

| 选择 | 后果 |
|---|---|
| 就这样做 | 接受质量 / 成本后果 |
| **换一条拆解路径** | 用若干小插件的组合完成同一件事——**弱模型也能做** |
| 去配置对应模型 | 补齐能力 |
| 终止 | 明确不做 |

**推论**：agent 需要知道"有哪些插件、各自建议什么档位"——**插件清单成为规划输入**。
**能力缺口会催生专门插件。**

**6. 降级必须留痕（出处，不是惩罚）。**
每次调用把"建议档位 / 实际 provider+model / 降级原因 / token 用量"写进 LH 事件。
理由：契约 §5.3 说**测量仪器质量是策略评估的天花板**。若分类器是用降级模型跑的，
它的证据质量就低——这个事实必须可追溯，否则将来复盘会把"仪器降级"误判成"策略失败"。

**7. 解析分两级（已实测三种降级情形）。**
1. **预检**：只查 provider 有没有注册（便宜、无副作用）。
   **不查模型在不在目录里**——宿主明说目录是"建议性"的
   （"consumers must not turn absence into request rejection"），查它会把可用模型误判掉。
2. **失败降级**：拿候选去真实调用，**失败才换下一个**。只有真实调用才知道模型 id 是否被适配器接受。

**8. 渠道层完全复用宿主 adaptor，不改一行。**
`dsh-llm-deepseek` / `dsh-llm-pi-ai` 等负责协议、鉴权、重试、流式。
理由：渠道层是宿主代码，动它就要跟着 dsh 版本重打补丁。
**只有在某个 provider 的协议需要特殊处理时**（推理等级字段名不同、无 chat completions 接口等）
才写 adaptor——那时是照 `LlmAdapter` 抽象类写一个**新** adaptor，不是在现有 adaptor 里改。

**9. agent 自己的对话模型选择与插件的档位建议是两件事。**
- 对话用哪个模型 → 宿主 adaptor 管，会话级；
- 插件内部调模型用哪个档位 → 插件建议 + 本层解析。
- 两者**不互相审批**。用户批准一次降级，不该影响他这次对话用什么模型。

## 依赖的前提

1. 宿主继续在 preset 作用域暴露 `ctx.llm` 与 `ctx.systemPrompt`（**已实测**）。
2. 宿主继续把模型目录标为"建议性"（否则预检逻辑要改）。
3. 作者接受"档位"—"模型"的映射写在一处配置文件里，由他本人维护。

## 怎么知道它错了

| 决定 | 失效信号 |
|---|---|
| 档位是建议、不阻断 | 出现"某插件在弱模型下产出的东西系统性不可用、以致下游全都错"的实际案例 → 那时需要的是**更强的质量信号**（如让插件报告"我不确定"），不是恢复硬拒绝 |
| 可用性进上下文 | agent 仍然在工作流深处才发现档位问题 → 说明"计划时读上下文"没起到作用，该改成**工具前置检查** |
| 问由 agent 做 | agent 从不主动问、直接降级执行 → 说明上下文里的话不够显眼，或需要把它做成一个显式的"标记"而非一段文本 |
| 降级留痕 | 复盘时从未用到"当时是哪个模型"这个字段 → 说明留痕是多做的，可简化 |
| 不改宿主 adaptor | 出现必须以改 adaptor 才能满足的 provider 需求 → 那时写**新** adaptor，别改现有的 |

## 未做的事

- `lh-model-tier` 的**调用端**（`model.js` 的 `callModel`）已实现，但**尚未在真实会话里被某个功能插件用过**。
  自检（`LH_MODEL_TIER_SELFTEST=1`）能验证通道，但"被业务插件实际使用"是另一回事。
- **"档位可用性进上下文"只在离线渲染里验证过**，尚未确认它在真实会话中每轮可见。
- 分类器、学习者模型等**真正的消费方**都还没做——本 ADR 只定契约。

- **状态**：已冻结（2026-09-17）
