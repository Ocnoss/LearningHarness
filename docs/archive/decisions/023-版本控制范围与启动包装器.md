# ADR-023：版本控制的范围、以及"启动包装器"而不是"哨兵插件"

- **背景**：作者提出两件相关的事——
  1. *"版本控制是可以的，但我没有 dsh+git 控制的经验……dsh 是起在用户文件夹的，
     一部分内核文件在 `.dsh` 里，但 LH 的另一部分部件在工作区里，
     这种情况要怎么版本控制？"*
  2. *"哨兵回退可以用，但是必须要保证**哨兵回退本身也是插件化但是不会出问题的**。"*
- **作者对当下状态的判断（我核实并同意）**：*"在我的项目变得越来越重之前，
  我或许需要认真考虑这个寄生关系的具体细节。"*

## 实测事实（决定方案的那些）

| 位置 | 内容 | 体积 | 归属 |
|---|---|---|---|
| `D:\LearningHarnessv0.1\` | plugins / scripts / docs / data | — | **LH 的源码与事实源** |
| `~\.dsh\.agent-presets\` | LH 的挂载点（2 个文件） | 0.0 MB | **配置，必须入库** |
| `~\.dsh\profiles\{web,dev,headless}\` 的 **非 node_modules 部分** | patch / package.json / lock | **14 个文件，约 12 KB** | **配置，必须入库** |
| `~\.dsh\profiles\*\node_modules\` | 867 个文件 | 6.0 MB | 第三方，不入库 |
| `~\.dsh\sessions\` | 42 个文件 | 24.2 MB | **状态**（是事实源的一部分，但不是代码） |
| `~\.dsh\attachments\` | 251 个文件 | 144.4 MB | **状态，绝不上传** |
| `~\.dsh\storages\` | 6 个文件 | 0.4 MB | 状态 |
| `~\.dsh\.credentials.yaml` | 254 B | — | **凭据，绝不入库** |
| `~\.dsh\settings.yaml` | 996 B | — | 配置，但含个人偏好 |
| dsh 本体 | `%APPDATA%\npm\node_modules\@deepseek-ai\dsh` | — | **第三方（0.1.1-rc.2）** |

**关键结论**：该入库的配置**只有约 12 KB**。剩下的全是状态或第三方。
所以"怎么版本控制"这件事的规模比看起来小得多——**难点不在体积，在边界**。

## 决定

**1. 一个仓库，在 `D:\LearningHarnessv0.1`。`.dsh` 的配置以"单向快照"的形式纳入其中。**

```
D:\LearningHarnessv0.1\            ← 唯一的 git 仓库
├── plugins/ scripts/ docs/ data/  ← LH 的源码与事实源
├── dsh-config/                    ← **.dsh 配置的快照**（唯一入库的那 12 KB）
│   ├── agent-presets/lh/agent.cordis.yml
│   └── profiles/{web,dev,headless}/…
└── .gitignore                     ← data/、node_modules/、trace.log
```

**为什么是"快照"而不是符号链接**：
dsh 必须从 `~\.dsh` 读真实文件，所以不能把那些文件搬进仓库。
符号链接看似优雅（改一处两处同步），但有一个**致命失败模式**：
若 `~\.dsh` 被删或重建，链接目标没了，**dsh 直接起不来**——
那正是我们要避免的那类事故。所以选"复制 + 一个显式的同步脚本"。

**为什么不做成两个仓库**：`.dsh` 的配置与工作区的插件**是同一件事的两半**
（preset 行按绝对路径指向 `plugins/`；profile 行按 `file:` 指向 `plugins/`）。
分成两个仓库会让"一次改动要提两次"、"回退要退两处"——
而我们要的恰恰是**原子回退**。

**2. 事实源里只有"人写的"入库。**

`data/events.jsonl`、`data/model-tiers.json` 是配置或事实源，入库。
但它旁边的 trace.log 是调试痕迹，不入库。
`~\.dsh\sessions\` 与 `attachments\` **不入库**——它们是机器状态，且含隐私。

**3. 用一个"启动包装器"取代 dsh 的直接启动命令。**

这是本 ADR 的第二半，也是作者那句"哨兵回退本身不会出问题"的答案。

作者要的是"插件化的哨兵回退"，但我认为**这件事有比插件更强的形态**：

> **把哨兵放在 dsh 之外 —— 用一个包装脚本启动 dsh，而不是让 dsh 内部的插件去救 dsh。**

**为什么必须是"之外"**（这是决定性理由，不是偏好）：
哨兵的职责是"当某一行让插件树加载失败时把那一行禁掉"。
而**插件树加载失败时，树里的任何东西都没有运行**——
包括哨兵插件自己。
**一个和病人绑在一起的心脏除颤器，在病人心脏停跳时也一起停了。**

所以哨兵的正确位置是**进程之外**：它是启动 dsh 的那个东西。

```
scripts/lh-boot.mjs（包装脚本）
  ① 预检：对所有已安装的 LH 包跑那四道闸门（它们都是离线的）
  ② 预检红 → **不启动 dsh**，报出哪一行、为什么，并给出回退建议
  ③ 预检绿 → 启动 dsh
  ④ 启动后 30 秒内异常退出 → 把"上一行"写进哨兵状态，禁用该行，重试一次
```

**它为什么不会自己出问题**（作者的要求）：
| 风险 | 处置 |
|---|---|
| 它自己有 bug | 它**不是插件**，不进插件树；它坏了的话 `npx dsh web` 仍然可用（退路一直在） |
| 预检误报 → 挡住正常启动 | **预检红时不自动改配置**，只报告并让你决定。改配置只在"第 ④ 步真的崩过"之后 |
| 预检漏报 → 照样崩 | 第 ④ 步兜底：崩了就禁用可疑行并重试一次 |
| 它把配置改坏 | 只做一件事：给某一行加 `disabled: true`；且改动前把原文件复制一份 |

**4. 寄生关系的显式化：`dsh-version.json`。**

dsh 是开发预览版（`0.1.1-rc.2`），作者明确说后期可能有毁灭性更新。
所以入库一份**版本契约**，记三件事：
- 当前测过的 dsh 版本；
- LH 依赖的宿主行为（哪些是"实测行为"而不是"公开 API"）；
- 每一处的检测方式（哪道闸门能发现它变了）。

**为什么这比"锁定版本"更重要**：LH 的插件大量依赖**实测出来的宿主行为**
（架构 §0.1 已记了 10 条约束）。锁定 npm 版本能防"运行时变了"，
但**防不了"我升级时没意识到某条实测行为没了"**。
所以契约要写成"**如果 X 变了，闸门 Y 会红**"的形式。

## 依赖的前提

1. `.dsh` 的路径是 `%USERPROFILE%\.dsh`（可用 `$DSH_HOME` 覆盖）。
2. 包装器只在**开发机**上使用；学习者用正常方式启动 dsh。
   它是开发工具，不是产品的一部分。
3. `sessions/` 不入库意味着**对话历史没有备份**。
   这是刻意的：它含隐私且体积大。**代价要写清楚**——
   想留证据的话，现在就得靠 `docs/` 里的文档（这也是为什么决策都写进 ADR）。

## 怎么知道它错了

| 决定 | 失效信号 |
|---|---|
| 一个仓库 + `.dsh` 快照 | 出现"改了 `.dsh` 但忘了同步回来"导致的行为不一致 → 需要让包装器在启动前**比对**快照与实际的 hash 并提醒 |
| 快照用复制不用软链 | 同步变成负担（每次改都要手动同步）→ 那时可考虑 symlink，但**必须先解决"目标不存在时 dsh 起不来"** |
| 哨兵在进程之外 | 作者觉得"多一个命令很麻烦" → 可把它做成 npm script / 快捷方式，但**不要**为了省事把它搬进插件树 |
| 预检红时不自动改配置 | 作者抱怨"每次都要手改" → 可以加一个显式的 `--fix` 开关，默认仍不动配置 |
| `dsh-version.json` | 它长期没更新 → 说明升级时没走过它，那它就是装饰 |
