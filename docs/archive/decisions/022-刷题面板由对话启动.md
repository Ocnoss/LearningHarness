# ADR-022：刷题面板由对话启动，而不是界面上的常驻按钮

- **背景**：刷题面板（`plugins/lh-practice`）第一版往 `sidebar.footer.action` 注册了一个常驻的
  "刷题"按钮，同时在 `shell.overlay` 上放了面板。功能可用，但作者否掉了入口形态。
- **作者原话**：*"我对这个交互逻辑不太满意……刷题的启动当然可以靠点击按钮启动，
  但我更希望的是能通过对话里 agent 的调用来启动，就像对话时你给我一个链接，
  我点进去就开始刷题（当然链接可以有更好的形式），**一个出现在 dsh 界面内的刷题按钮很突兀**。"*

## 决定

**1. 去掉常驻的侧栏按钮；启动权交给对话里的 agent。**

界面上**不再有任何刷题入口**。流程变成：

```
学习者在对话里说"刷题"
  → agent 调工具 start_practice
  → 工具写一个递增的**启动信号**
  → 浏览器里的面板轮询到新信号 → 自动打开并取题
```

**为什么这个方向是对的**（不只是"作者喜欢"）：
- 刷题是一个**有时效的意图**，由对话产生、也该由对话结束。常驻按钮表达的是
  "这个功能一直在这儿"，而那不是事实。
- 学习者**不需要知道有个面板**。他要的是"我要练几道"，而不是"去点某个按钮"。
- 这也让"打开刷题"变成一次**可记录的行为**（工具调用会进会话日志），
  而点按钮不会——后者在事后完全不可追溯。

**2. 启动信号用「文件」做会合点，因为两端不在同一棵树里。**

- 工具注册在 **agent preset 作用域**（`lh-question-bank`）；
- 面板与它的 HTTP 路由在 **profile/host 作用域**（`lh-practice`）。

**内存里的信号传不过去**——这是同一个坑的第二次：早期 `lh-event-store` 想在 preset 里
等 host 面的服务，永远等不到（ADR-014 补充决定 6）。

所以用文件（`practice-signal.json`，与 `events.jsonl` 同级）。
它不需要任何新服务，也不依赖宿主的推送机制。

**3. 信号只是"计数器 + 时间戳"，不是队列。**

需要的语义只有一个：**"请打开面板"**。所以：

```js
{ seq: 3, at: "…", by: "agent", bank: "考公刷题-…", count: 5 }
```

- 面板记下它见过的 `seq`，发现更大的就打开；
- **重复读不会让 seq 变化**（读是纯的）——否则轮询会把面板反复打开；
- 文件丢了也没关系（下次工具调用会重建）。

**不做的**：可靠投递、顺序保证、ack。它不是一个任务队列——
**面板自己会取题，重复打开也无害**。

**4. 面板用轮询发现信号，不自己做推送。**

宿主**没有**服务端→客户端的通用推送通道（`ctx.provide` 是客户端插件之间发布服务的，
方向不对）。自己实现 SSE/WebSocket 能免掉轮询，但代价是长连接的生命周期管理。

这个轮询的具体代价：**3 秒一次、响应几十字节、且只在面板关闭时进行**
（打开时停掉定时器，没必要再问）。

**在这个规模上，简单比省流量重要。**

**5. 首次读取只记住 seq，不打开面板。**

这一条是必需的：否则**每次页面刷新都会自动弹面板**，
而那个信号其实是上一次对话留下来的。所以：

```js
if (lastSeenSeq < 0) { lastSeenSeq = sig.seq; return }   // 第一次：只同步
if (sig.seq > lastSeenSeq) { … 打开 … }                   // 之后：新信号才开
```

**6. 题库名对不上时不报错，而是把可选项列出来。**

`start_practice` 的职责是"打开面板"，不是"校验题库名"。
名字不对时：面板用第一个题库，而工具返回值里列出全部可选项，
于是 agent 能自己纠正并告诉学习者。

（与 `get_questions` 的处置**不同**：那里名字不对会报错，因为"取错题库的题"不可恢复。
见 `requireBank` 的注释。**同一个问题，在"打开面板"和"取题"两个语境下的正确处置相反。**）

## 依赖的前提

1. 面板所在的浏览器页面与 dsh 服务端在同一进程上下文里（同一 origin，`fetch` 可达）。
2. 学习者不关浏览器标签页——关了就收不到信号。这是可接受的：
   面板本来就是浏览器里的东西。
3. agent 会在学习者表达"刷题"意图时调 `start_practice`。
   工具描述里写明了触发时机，但**这最终是模型的判断**。

## 怎么知道它错了

| 决定 | 失效信号 |
|---|---|
| 由对话启动 | 学习者反复抱怨"不知道怎么开始刷题" → 也许需要一个**不常驻**的间接入口（如命令面板），而不是回到常驻按钮 |
| 文件做会合点 | 出现"信号写了但面板没开"且文件正确 → 说明轮询或路由出了问题；此时**不要**退回内存信号，那条路本来就不通 |
| 轮询 3 秒 | 有人抱怨延迟明显，或服务端日志里轮询请求量异常 → 再考虑 SSE；**但先量一下再说** |
| 首次只同步 | 刷新后自动弹面板 → 说明 `lastSeenSeq` 的初值逻辑被改坏了 |
| 名字不匹配时不报错 | agent 反复用错题库名且不自纠 → 说明返回值里的可选项没被用上，考虑改成报错 |

## 未做的事

- ~~**"比链接更好的形式"**：作者提到过这个方向。目前是"面板自动出现"，
  已经比链接更省一步；但**在对话流里放一个可点的卡片**（而非浮层面板）
  是另一种形态，未探索。~~ → **已做，见下面的修订 7。**
- 面板的持久化（刷新后恢复上一次的进度）：未做。
- 多会话/多工作区下的信号隔离：目前信号是**全局单例**，
  没有按会话区分。**如果将来同时开多个 LH 会话，后一个 `start_practice`
  会打开所有页面上的面板。** 这是一个已知的、被接受的粗糙处。

## 修订 7（2026-09-18）：入口改成**对话里的卡片**，取消"自动打开"

**上面决定 1 里那句"面板轮询到新信号 → 自动打开并取题"被推翻了。**

作者看了自动打开的效果之后，给的是**类比**而不是规则：

> *"刷题的按钮由 agent 的对话提供最好了，就像有的网页端 ai 在生成报告之后，
> 点击一个对话里的链接或者框，右侧就会弹出报告的页面那样。"*

### 改了什么

```
学习者在对话里说"刷题"
  → agent 调工具 start_practice
  → 工具写一个递增信号（**保留**，见下）
  → 宿主用我们注册的渲染器把**这次工具调用**画成一张卡片
  → **学习者点卡片** → 面板打开并取题
```

关键差别只有一个：**打开是学习者的动作，不是 agent 的动作。**
轮询保留，但它不再打开任何东西——它只让卡片和兜底入口知道
"agent 请了几道题、哪个题库"。

### 技术依据（来自宿主类型声明，非推测）

入口用 `tool.call.toolview` —— **keyed 插槽，按 wire 工具名分发**
（`dsh-client-ui-tool/lib/types/client/contract/slots.d.ts`）：

> Keyed atomic Tool call view, dispatched by the wire Tool name.
> Register with `key: '<tool name>'` to own how one tool's calls render inside a turn —
> the key domain is open (any wire tool name, **including a tool your own package registered**)…
> an unclaimed key falls back to the generic tool row.

即"给自己的工具定制渲染"是宿主**明说的用法**，而且键空间是开放的
（我们自己的工具名也算合法键）。

### 两个必须靠代码兜的坑

1. **键写错不报错，只是永远不渲染**（原文："a typo simply never renders"）。
   而卡片现在是**唯一入口**——它不出现，学习者就完全没有办法打开面板。
   所以保留一个**兜底入口**：仅当"agent 请过刷题 + 面板关着 + 卡片注册失败"
   三条同时成立时，右下角出现一个小按钮。
2. **注册选项形状未验证**（keyed 型要不要给 `id`？我没见过任何真实样例）。
   于是依次试三种形状、**永不抛错**。理由与 ADR-025 一致：
   客户端插件 `apply()` 抛错会让整个界面起不来，代价远大于少一张卡片。

### 决定 3/5 为什么仍然成立

- **信号仍然保留**：卡片点开时要读它才知道"agent 想刷哪个库、几道题"。
  卡片**刻意不去解析** `props.block`（那次工具调用的结果节点）——它的形状未验证，
  而猜形状的后果是**静默显示错内容**，比报错更糟。问路由是确定的。
- **首次只同步 `seq` 仍然必要**：否则每次刷新都会显示"agent 请你刷题"，
  而那是上一次对话留下的。只是现在误判的后果从"自动弹面板"降级为"多一个小按钮"。

### 怎么知道这次改错了

| 失效信号 | 说明 |
|---|---|
| 学习者说"没看到卡片" | 先看浏览器控制台有没有 `[lh-practice] 卡片已注册`；没有就是三条注册形状都被拒，右下角应出现兜底按钮 |
| 有卡片但点了没反应 | 看 `/pending` 是否可达；卡片点击路径依赖它 |
| 又变成"面板自己弹出来" | 说明 `setPendingRequest` 里被加回了打开逻辑——**那是被否掉的第二版** |

- **状态**：已冻结（修订 7 于 2026-09-18）

## 修订 9（2026-09-18）：**题目与作答归插件与事件日志，卡片只是入口的渲染**

作者提了一个该问的问题：

> *"加入刷题卡片只是对模型输出的一道题（或几道题）的渲染，而不是直接与题库插件对接，
> 那刷题数据的传回以及后期对刷题结果总结分析也会只进模型上下文，而不是进系统事件，
> 我希望这不会发生。"*

**担心的方向是对的，但目前的实现不是那样。** 把数据流的归属写清楚：

```
agent 调 start_practice(bank_name, count, style)
  └─ 工具**只写一个信号**（practice-signal.json），返回值里**没有题目文本**
       ↓
对话里出现一张卡片（tool.call.toolview 按工具名渲染那次调用）
  └─ 卡片上的题库/题数/预览都来自 GET /lh/practice/bank —— **来自插件，不是模型**
       ↓ 学习者点卡片
面板 GET /lh/practice/bank ──→ lh-practice 路由 ──→ @lh/question-bank 的 getQuestions
       ↓ 作答
面板 POST /lh/practice/attempt ──→ submitAnswer ──→ store.append(type:'lh/user/attempt')
                                                      └─→ **events.jsonl（LH 事件日志）**
```

**三个要点**

1. **卡片不承载题目内容。** 它渲染的是**工具调用**，而那次调用的参数只有
   题库名、题数与外观。题面一个字都不经过模型——"卡片 = 模型输出的渲染"这个前提不成立。
2. **题目来自插件。** 卡片预览与面板取题走**同一条** HTTP 路由，落到 `getQuestions`
   （与 agent 的 `get_questions` 工具**同一份实现**）。
3. **作答进事件日志。** 面板作答走 `submitAnswer`，它 `store.append` 一条
   `lh/user/attempt`。**界面与 agent 工具走同一条判分与记录路径**（刻意的：
   不能让界面成为第二套判分实现）。断言见 `selftest-routes.mjs`
   "每作答一次，日志刚好加一条"。

**所以"后期总结分析"的原料在系统事件里，不在模型上下文里。**

### 但有两个**真实的**缺口，如实记下

1. **界面来的作答 `session_ref` 是 null。** HTTP 路由没有会话上下文（与"拿不到
   `session.header.cwd`"是同一个限制），所以 `sessionRef: undefined`——
   **显式留空，而不是编一个**（坐标错比坐标缺更糟）。
   后果：日志里有"谁、何时、答了哪道题、对错如何"，但**没有**"这次作答属于哪场对话"。
   卡片与作答目前只靠时间 + 题库 + 题号关联。要补上，得让界面把会话身份带进请求
   （或宿主提供"当前活动会话"服务）。
2. **"在对话里问题、在对话里作答"那条路仍依赖 agent 调 `record_attempt`。**
   面板那条是硬的（点提交就写日志）；而 `get_questions` 把题交给模型、
   学习者在对话里用文字回答时，**是否落进事件日志取决于 agent 有没有调
   `record_attempt`**——那是模型判断，不是结构保证。
   不打算用"自动记录"去堵：那会把模型说的任何话都当作答，噪声更大。
   **这是"对话里刷题"相对"面板里刷题"的已知劣势；面板是硬保证的。**
