# ADR-031：开发隔离——把 dsh 的家迁进工作区（`DSH_HOME=<仓库>/.dsh`）

- 日期：2026-09-20
- 状态：已采纳（**已验证可用**；老 `~/.dsh` 保留不动）
- 相关：ADR-011（宿主采用 dsh）、ADR-023（版本控制边界与启动包装器）、ADR-025（安装期配置）、
  ADR-030（LH 会话带上基础能力）、`docs/PLUGIN_CONTRACT.md §五之五`

---

## 背景

作者的开发要同时依赖两个地方：

| 地方 | 装什么 | 问题 |
|---|---|---|
| `~/.dsh` | agent preset、profile 里的插件副本、会话日志、凭据、缓存 | "开发"被绑在**频繁唤起 dsh** 上；换个 IDE/CLI 打开工作区就做不全 |
| `D:\LearningHarnessv0.1` | 项目文件、插件源码、脚本、闸门 | 它自己已经能跑完大部分验证（不需要 dsh 在跑） |

**目标**：让**工作区自持**——用任何 IDE/CLI 打开这个仓库都能完整开发 LH，
包括起一套**属于这个项目**的 dsh，从而也能尝试"非 dsh 开发 dsh 插件"。

## 关键事实（查证过的，不是推断）

`[宿主源码]` `@deepseek-ai/dsh-home-paths` 的 `resolveDshHome`：

```
显式配置 > $DSH_HOME > ~/.dsh          （空白值的 DSH_HOME 按未设置处理）
```

而 dsh 的 CLI 文档写明：`dsh --profile <name>` 启动 `$DSH_HOME/profiles/<name>`，
组合层的顺序是 **每个 bundle 的 patch → profile 的 `cordis.patch.yml` → `$DSH_HOME/cordis.patch.yml` → `--patch`**。

**也就是说：一个环境变量就能整体搬走这个"家"。** 实测挂在 `$DSH_HOME` 下的东西：

| 内容 | 实测证据 |
|---|---|
| `.agent-presets/` | preset 发现路径是 `<dshHome>/.agent-presets`（`[宿主源码]` `dsh-agent-presets`） |
| `profiles/<名>/` | CLI 文档 + 实测 |
| `.credentials.yaml` | `[宿主源码]` `dsh-credentials-local`：`join(resolveDshHome(config.dshHome), ".credentials.yaml")`，**且支持显式 `config.path` 覆盖** |
| sessions / attachments / storages / skills | 相关包都读 `DSH_HOME`（逐一确认过） |
| `settings.yaml` | 启动时若缺则**自动生成一份默认的**（实测：新家里出现了只含 `welcomeNoticeVersion` 的一份） |

## 决定

### 1. 家 = `<仓库>/.dsh/`，用启动器设置

新增 `scripts/lh-dev.mjs`：只做三件事——**设 `DSH_HOME`、转发参数、打印家在哪儿**。
它不解析 dsh 的 flag、不猜 profile 名、不改 dsh 代码（少一处会漂移的知识）。

### 2. 什么搬、什么不搬（**按"是不是项目的一部分"划界**）

| 搬 | 不搬 |
|---|---|
| `.agent-presets/lh/`（preset 是插件挂载点，属项目） | `sessions/`（36.7 MB 历史；它是**学习记录**，不是代码） |
| `profiles/web/` 的 `package.json` / `cordis.patch.yml` / `pnpm-lock.yaml` / `pnpm-workspace.yaml` | `attachments/`（144 MB 上传物） |
| `settings.yaml`（含 provider 与默认模型配置；实测其中 apiKey 写的是**环境变量名**） | **`.credentials.yaml`**（见决定 3） |
| `lh-install.json`（由 sync 脚本生成，是插件定位数据目录的依据） | `profiles/*/node_modules/`（pnpm 拷贝出的派生物，一条命令重建） |
| | 老的 `~/.dsh` 整棵（**保留作为退路**） |

### 3. 凭据**不进仓库**

两个理由叠加：

1. **安全**：仓库里放一份密钥，就离"某次 `git add -A` 把它提交上去"只差一步；
2. **它本来也不该是项目的一部分**：密钥是**用户级**配置，跟着人走，不跟着项目走。

所以 `DSH_HOME` 指到工作区后，模型调用用的密钥仍然来自环境变量——
由**启动 dsh 的那个进程**注入（实测我自己的 shell 里就有
`XIAOMI_TOKEN_PLAN_AMS_API_KEY`、`DEEPSEEK_API_KEY` 等，来自 `~/.dsh/.credentials.yaml`）。

**如实记下这条的代价**：在一个**不经过 dsh** 的 IDE/CLI 里开发时，
需要自己导出这些环境变量（或让 IDE 读一份本地 `.env`，而 `.env` 已被 `.gitignore` 忽略）。
这是"隔离"换来的代价，不是遗漏。

### 4. 老 `~/.dsh` **不删**

它是备份，也是"新家坏了"的退路：把 `DSH_HOME` 撤掉即可回到今天之前的状态。

### 5. "两个家并存"是这次迁移**最危险的状态**，所以必须能一眼分辨

危险不在于哪个家错了，而在于**脚本 A 看新家、脚本 B 看旧家，而两边都给出结果**——
那时"闸门绿了"可能只是它看了另一份代码。

处置：

- **启动器打印** `DSH_HOME = …`；
- **闸门也打印**（新增 `scripts/lib/dsh-home.mjs` 的 `describeHome()`），
  并把**原来写死 `USERPROFILE/.dsh` 的三个闸门**改成按 `DSH_HOME` 找：
  `check-client-inject` / `check-plugin-imports` / `check-profile-apply`。
  （`sync-lh-deps.mjs` 与 `dev-watch.mjs` 本来就认 `DSH_HOME`，未改。）

**为什么必须改那三个**：`check-plugin-imports` 与 `check-profile-apply` 的全部价值是
"**import 的是生产那份副本**"；指向旧目录，它们证明的就变成了**另一份代码**。
**闸门指着错的目录比闸门红更糟**——它会让人去修一个没坏的东西。

## 验证（本次真做过，不是推算）

| 步骤 | 结果 |
|---|---|
| 临时家演练（`data/_home-test`，不碰工作区与旧家） | 起 dsh → 首页 HTTP 200、stderr 干净 |
| 正式迁移后启动（`node scripts/lh-dev.mjs`） | 首页 200 / 14859 字节；**我们自己的客户端 bundle `/plugins/@lh/theme/client.js` 200 / 9394 字节** |
| 刷题数据路由（真实调用） | `/lh/practice/pending` 200；`/bank?bank=考公刷题-片段阅读-第1册&count=2` **200 / 2436 字节** |
| 工作区解析（从副本位置问） | `workspaceDir()` = `D:\learning Harness test`，来源 `lh-install.json`（新家那份） ✅ |
| 20 项闸门（`DSH_HOME` 指向新家） | 全绿 |

**一处曾看着像故障的**：`/bank?bank=`（空）返回 **500**——查清了：那是接口的既有行为
（空题库名 → 报错并**列出可用题库名**），不是启动问题。**如实记下，免得下次有人重新查一遍。**

## 怎么知道它错了 / 怎么回滚

| 失效信号 | 处置 |
|---|---|
| 启动器报"找不到 @deepseek-ai/dsh" | 全局装 `npm i -g @deepseek-ai/dsh`，或装到本项目，或用 `npx` |
| 新家里没有 provider / 默认模型不对 | 新家缺 `settings.yaml`（启动会自动生成一份**默认的**）→ 从 `~/.dsh/settings.yaml` 复制一份 |
| 会话历史"不见了" | 正常：`sessions/` 没搬。要看旧会话就临时把 `DSH_HOME` 指回 `~/.dsh` |
| 模型调用报缺 key | 在不经 dsh 的 CLI 里开发时，要自己导出 `*_API_KEY`（见决定 3 的代价） |
| 闸门结果与预期不符 | **先看它打印的 `DSH_HOME`**——十有八九是看了另一个家 |
| 想整体回退 | 不用 `lh-dev.mjs`（或直接 `dsh web`，它会走 `~/.dsh`），并删除 `<仓库>/.dsh/` |

## 没做的（如实记下）

- **`.credentials.yaml` 的显式 `config.path` 方案没采用**：`dsh-credentials-local` 支持
  `config.path` 指到任意位置（可放在仓库外的 `~/.lh-dev/`），但那要改 profile 的 patch 层
  去注入这条配置。**当前形态**（密钥仅在环境变量里）已经满足"不在仓库里"这个目的，
  等真出现"想在别处持久化凭据"的需求再做。
- **`DSH_HOME` 之外的两个根没搬**：`agentsHome`（默认 `~/.agents`）与 `DSH_BUNDLED_SKILL_DIR`
  仍是系统级；将来给 LH 自己做技能时再定它们的归属。
- **没做 `.env` 自动加载**：启动器不读 `.env`。理由是"少一处隐式行为"；
  如果将来在做 IDE 里反复被这件事硌到，再让启动器支持 `--env-file`。
