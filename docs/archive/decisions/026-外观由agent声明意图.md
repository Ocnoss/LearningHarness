# ADR-026：外观由 agent 声明**意图**，服务端校验，客户端算对比色

- 日期：2026-09-18
- 状态：已采纳
- 相关：ADR-016（只声明档位名）、ADR-022（入口是对话里的卡片）、
  `docs/PLUGIN_CONTRACT.md` §五之二（装载期不许抛错）

---

## 背景

作者在卡片跑通之后提了两件事：

> *"刷题卡片的测试效果不错，如果可以拖动就更好了，而且如果对刷题卡片做定制化也会更好，
> 这个定制化在现有工具可实现吗？如果可以实现就将它集成到已有的工具中，
> 让负责呼出刷题卡片的 agent 有能力调整刷题卡片的样式或是颜色、布局等。"*

追问自由度时，作者没有采纳我给的"语义化 vs 自由 hex"二选一，而是说：

> *"我不是很理解这些语义化或是逃生口指的是什么，但我希望尽可能多的让 agent 编辑
> 答题卡片的样式，包括不限于一卡多少题（文字布局），框体、字体大小、背景色"*

**"尽可能多的自由" 与 "不能把配色弄坏" 看起来是冲突的。** 这份 ADR 就是那个冲突的解。

---

## 决定

### 决定 1：先查宿主的现成机制 —— 结果是"不够用，但够用的那一半我们自己有"

宿主**确实**有"渲染意图"机制：`ToolDefinition.presentCall` / `presentResult`
（`@deepseek-ai/dsh-tools/lib/types/schema.d.ts:223,230`），算出的 view 会随节点
送到客户端（`ToolResultNode.callView/resultView`）。

但它是**封闭的标签联合**，字段里**没有颜色与布局的位置**：

```
ToolCallView   = GenericCallView | TerminalCallView | DiffCallView
GenericCallView = { card:'generic', title, kind?, rawInput?, content?, locations? }
```

这是宿主的**刻意设计**（"provider-neutral"：让工具描述自己而不依赖某个客户端，
配色归 UI）。**所以这条路能表达"显示什么"，表达不了"长什么样"。**

**结论：不去和宿主的设计对抗。** 用宿主已经给的那一半 ——
`RunningToolCall.argsRaw` / `ToolResultNode.call.argsRaw`（**工具调用的原始参数**，
两种状态都有）—— 也就是"agent 在调用工具时把外观作为参数传进来"。
这条路完全在现有机制里：**扩展工具自己的参数 schema，不需要宿主任何新能力。**

### 决定 2：一层词汇表，服务端校验，**客户端不重复校验**

```
agent 调 start_practice(style: {...})
  → style.js 的 sanitizeCardStyle()   ← 唯一校验点（纯函数、离线可测）
  → 写进信号 practice-signal.json
  → 客户端从 /lh/practice/pending 取到**已合法**的 style
  → resolveStyle() 只做 token → CSS 的映射
```

**为什么校验只在一处**：两处校验 = 两套规则，迟早不一致；
而那时"哪个才对"会成为无法回答的问题。所以客户端不做校验，
只做一件事：**查表查不到就用默认值**。于是将来服务端加了新 token 而客户端没跟上，
结果只是"那个旋钮没效果"，**不会画出坏掉的东西**。

### 决定 3：颜色给两档，而自由档之所以安全是因为**文字色不由模型决定**

- **语义档**（`accent: 'focus'`）→ 映射到宿主的 `--dsw-alias-*` 变量，
  深浅色模式自动正确（`lh-theme` 与宿主主题都在管这些变量）。
- **自由档**（`accent: '#8a5cf6'` / `background_color`）→ 允许。

自由档能成立，**不是因为模型会挑颜色**，而是因为：

> **拿到自定义背景色时，客户端用相对亮度自己算一个看得清的文字色**
> （`readableOn`，Rec.709 系数；`#0000ff` 是深色，不是"中等亮度"）。

模型只能写、不能看。所以任何"写错了只是难看"的自由度，都会**稳定地**产生难看的卡片，
而且它**永远不知道**。与其禁止自由颜色，不如把"文字色"从它手里拿走。
于是这一条成立：

> **让自由档安全，就不需要在自由度和安全之间选。**

### 决定 4：词汇表里**只放真的会生效的旋钮**

`style_applied` 是工具返回值的一部分，agent 据此相信"调对了"。
所以**一个声明了却不生效的旋钮，比没有这个旋钮更糟**：
agent 以为调好了、学习者看到没变化，**两边都不会报错**。

按这条，`panel_layout`（面板一次列几道）与 `questions_per_view` 被**砍掉**——
它们要把面板的作答状态从"一题"改成"每题一份"，是一次真正的重构，
所以在这一版**不能出现**在词汇表里。面板一次取几道已经由 `count` 参数管着。

### 决定 5：`ignored` 是模型的纠错回路，必须如实

模型很容易**发明字段名**（`fontSize`、`bg`、`color`）。
静默忽略会让它反复试同一个错名字。所以：

- 不认识的字段 → 点名报告；
- 枚举值写错 → **连可选值一起报**（否则它只能瞎猜）；
- 数值越界 → **夹紧而不是丢弃**（`preview_questions: 10000` 的意图是清楚的），
  但**必须报告夹到了多少**，否则它以为 10000 生效了。

### 决定 6：工具描述**从实现生成**，不手写第二份

`start_practice` 的 description 里那份选项列表由 `describeStyleVocabulary()` 生成。
手写一份的话，改了 `style.js` 却忘了改描述，agent 就会按过时的列表调用，
而它收到的 `ignored` 又说"这个值不在允许值里"——**两边互相矛盾，模型开始瞎猜**。

### 决定 7：浮层面板可拖动，位置存在 `localStorage`

- 拖拽把手是**表头**（拖边框容易误触，而"拖标题栏"不需要解释）；
- 用 **pointer events + setPointerCapture**：鼠标/触摸/触控笔一套，
  且指针移出元素后仍能收到 move（没有它就会"拖丢"）；
- **必须夹回可视区**（写入时 + 窗口 resize 时）：窗口缩小或换屏后，
  旧坐标可能落在屏幕外——那时面板"还在"但谁也看不到，而学习者只会觉得"刷题坏了"。
  这是拖拽类功能最典型的静默失效。
- 位置存 `localStorage`，**不写进 LH 事件日志**：面板坐标是**界面偏好**，
  不是学习事实（契约 §1.4 / ADR-012 决策 4）。刷新后回到原处。

## 修订 8（2026-09-18）：确认下来的**工作模式**

作者把想要的工作模式讲明确了：

> *"首先在呼出卡片的时候，模型会提醒用户如果对卡片样式不满意，可以告诉它让它调整，
> '我可以调整卡片的 xxx，xxx 和 xxx'（并且调整之后应该怎么应用新的样式，
> 最好是不用重启整个 dsh/lh 的，最好是在回复中发起一个新的卡片，
> 新样式就已经应用在新的卡片了），卡片也支持拖拽移动和控制窗口大小。"*

三条要求，逐条落地。

### 要求 1：呼出卡片时**主动告知**能改什么

写进工具 description（而不是指望模型自己想到）：调用之后**必须做两件事** ——
告诉学习者点卡片；**并说明你能改卡片的样子，举例说出能调什么**。
例子里列的就是词汇表里的项（配色/字号/圆角边框/排布/预览几道/面板宽度/只留标题）。

**表述从词汇表生成**（`describeStyleVocabulary()`），所以"能调什么"这句话
永远不会和实现不一致——见决定 6。

### 要求 2：改样式**不重启**，且**新样式只落在新卡片上**

**"不重启"这条本来就成立**：外观随**工具调用的参数**走，每次调用都会重写信号，
所以 agent 再调一次 `start_practice(style: …)` 就等于改了——
**没有编译、没有重启、没有缓存**。重启只在"工具 schema 本身变了"时才需要（一次性）。

但**"新样式落在新卡片上"当时不成立**：卡片最初统一从 `/pending`（最近一次信号）
取样式，于是学习者一改，**对话里所有卡片一起变**——分不清改的是哪一张，
也没法把新旧两版并排比较。

修法：**每张卡片读它自己那次调用的参数**（`RunningToolCall.argsRaw` /
`ToolResultNode.call.argsRaw`，形状已由宿主类型声明核实）。

这里有个**三态语义**，是这个功能的全部依据，也是最容易写错的地方：

| 返回 | 含义 | 行为 |
|---|---|---|
| `undefined` | 拿不到自己那次调用（上下文截断把它移出窗口） | 退回 `/pending` |
| `null` | 明确**没有**声明外观 | 用**默认**（**不是**用最近一次的样式！） |
| `object` | 有 | 用这一份 |

把 `null` 也当成"回退"会让旧卡片跟着新请求一起变——**正是要修掉的那个毛病**。
所以这一条被单独写了测试（`selftest-client.mjs` 第 4 节）。

顺带：参数是"发出前的原文"，**没经过服务端夹紧**（服务端夹的是写进信号的那一份）。
所以客户端补了一层**最小**防护（数值夹紧）。这不是"两处校验"：
**词汇表仍然只在服务端一处定义**（客户端不认识就查不到映射 → 落回默认），
重复的只有两条上下界，漂移的后果是"夹到另一个也合理的数"。

### 要求 3：面板可拖动 **+ 可缩放**

拖动见决定 7。缩放补上：

- 把手在**右下角**（不挡标题、不挡内容，且是"窗口能变大"的约定方位）；
- **不用 CSS 的 `resize: both`**：它只在非 `visible` 的 overflow 上生效，
  能改尺寸**但拿不到回调**——于是没法存进 `localStorage`（刷新就丢），
  也没法在超出可视区时夹紧；
- 尺寸与位置**都夹进可视区**，并在窗口 resize 时重新夹（换屏/缩小窗口后
  尺寸可能比窗口还大，那时面板会遮住整个界面且够不着把手）。

**谁赢：agent 声明的 `panel_width` vs 学习者拖出来的尺寸**

两种直觉会打架，所以规则写死：
**学习者手动拖过 → 他的尺寸赢**（他刚表达过意图，不该被下一句对话改掉）；
**但 agent 这次带来的 `panel_width` 与上次生效的值不同 → 以声明为准**
（那正是"学习者要求改样式"的结果）。
于是"改样式"能用，而"agent 重复同一样式"不会把学习者的拖动冲掉。

**⚠ 提交前抓到的一个 bug（值得记）**：把手一开始放在带 `overflow: auto` 的同一个盒子里。
绝对定位在滚动容器内会**跟着内容滚**——题目一多，缩放把手就跑到内容末尾，
得滚到底才够得着。改成"外层定位 + 内层滚动 + 把手贴外层角"。
这类问题**只在内容足够长时才出现**，所以它属于"眼睛不容易发现"的那一类。

## 代价与已知局限

- **一屏多张卡片时，它们显示最近一次请求的外观**：卡片从 `/pending` 取数据与外观
  （唯一校验点的代价），而信号只有"最新一份"。面板本来也只按最近一次请求渲染，
  所以这个粗糙处是一致的。要修就得让每张卡片解析自己那次调用的 `argsRaw`——
  那就把校验也搬到了客户端（见决定 2 为什么不）。
  → **修订 8 已修**：卡片改为优先读**自己那次调用**的参数，`/pending` 只在
  拿不到自己那份时当退路。上面这段保留，是因为它记录了当时的取舍过程。
- **`rawInput` 那条宿主通道没被使用**：它能把任意值送到细节视图，但语义是"给读者看的
  关键输入"，拿它当私有数据通道属于误用。不占这个便宜。
- **`:has()`、网格布局等更强的手法没做**：现在的旋钮是"常用可枚举"的一组，
  不是完整的 CSS。

## 怎么知道它错了

| 决定 | 失效信号 |
|---|---|
| 校验只在服务端 | 客户端出现"颜色没生效但没理由" → 先看 `/pending` 返回的 style 是否已归一化 |
| 自由档 + 自动对比色 | 出现"看不见的字" → `readableOn` 的亮度阈值（0.45）需要按实际观感调 |
| 只放会生效的旋钮 | agent 反复调一个**描述里有、但界面没反应**的旋钮 → 说明词汇表混进了未实现的项 |
| `ignored` 如实 | agent 反复用同一个错字段名 → 说明 `ignored` 没被渲染进它看得到的地方 |
| 面板可拖 | 学习者找不到面板 → 检查坐标夹紧是否有洞（换屏 / 缩放 / 多显示器） |
