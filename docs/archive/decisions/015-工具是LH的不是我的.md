# ADR-015：工具是 LH 的，不是我的

- **背景**：作者在开发同类工具时踩过一类混淆，明确要求记录下来。原话：
  > "后面可能会涉及到一些 agent 工作，你的工作是建立 agent 工作流，然后调用我给你的大模型 api 在你建立的 loop、用你设置的 Harness 来完成，而不是自己用 dsh 的工具去完成，此前有一些 llm 会混淆这两者，我希望你明确这两者的区别"
  > "工具在宿主的注册是需要的，或者说以后我说的这些工具都是需要符合宿主的框架，宿主的插件接口协议的"

## 决定

**1. 工具的"使用者"是 LH 的 agent，不是开发用的 AI。**

一个 LH 工具（如资源索引器）的正确形态是：注册进**宿主的工具注册表**，由 **LH agent 在 LH 的 loop 里调用**。
开发用的 AI（在 dsh 会话里工作的那个）**不应当用自己手头的工具去代做这件事**。

区分两件容易混为一谈的事：

| | 是什么 | 谁执行 | 验证什么 |
|---|---|---|---|
| **建** | 写插件、注册工具、定义 schema、写工作流 | 开发用的 AI | 工具能被注册进宿主、schema 合法 |
| **跑** | 在 LH 的 loop 里，由 LH 的 agent 调用该工具完成任务 | **LH 的 harness + LH 的 agent** | 这条工作流真的能完成学习任务 |

**反例（必须避免）**：作者说"帮我索引 D:\考公资料"，开发用的 AI 就自己扫一遍文件夹、把结果贴出来。
那样做**什么也没验证**——因为真正要验证的是"LH 的 agent 会不会在对的时机调用它、参数给得对不对、
拿到结果后怎么用"。开发用的 AI 代做，等于绕过了被测的那一环。

**2. 交付物是工作流，不是结果。**

开发用的 AI 面向 agent 工作时的产出应当是：
- **agent 工作流**：什么触发、注入什么上下文、调用哪个工具、拿到结果后如何继续；
- **被这套工作流调用的工具**；
- 以及**跑通它所需的配置**（模型 api 的接法、loop 的入口）。

而不是"这件事的结果"。

**3. 工具一律符合宿主框架的插件接口协议。**

- 用 `ctx.tools.register(...)` 注册，带完整的 `description` / `parameters` / `output` 声明；
- 参数与输出走宿主的 schema 约定，不自造一套；
- 工具是插件的一部分，随插件卸载而撤销（宿主的"可逆副作用"要求）。

**已验证的推论**：工具注册进宿主后，它的 schema 会自动进入系统提示词（宿主 `dsh-tools` 的机制），
所以"工具存在"这件事模型能看见——这正是"由 agent 调用"而非"由我代做"的技术基础。

## 依赖的前提

1. LH 的 agent 工作最终在**宿主 dsh 的 loop** 里跑（ADR-011：内核机制采用宿主）。
   若将来改为 LH 自建 loop，本条的"建/跑"区分不变，只是"跑"的位置换了。
2. 作者会提供大模型 api 的接法（哪些模型、怎么配）。**这一点尚未获得**，
   因此涉及多模型编排的工作流暂时不能落地——需要时向作者索取。

## 怎么知道它错了

| 决定 | 失效信号 |
|---|---|
| 建/跑分离 | 开发用的 AI 又一次"顺手把活干完"，而不是交出一个可被 agent 调用的工具与工作流 |
| 交付物是工作流 | 交付物变成"某个资料夹的索引结果"这类一次性产物，而不是可复用的工具 + 工作流 |
| 工具符合宿主协议 | 出现"只有我这个 AI 能用、模型看不见"的工具（未注册进宿主），或自造 schema 约定 |

## 待作者确认（写下我的理解，错了好改）

作者提到"我给你的大模型 api"与"你建立的 loop"。
按 ADR-011，内核机制 = 宿主（含 loop）。所以有两种读法：

- **读法一**：只用宿主已有的 loop，多模型通过宿主的 LLM 服务接（`agent/request` 可切换 provider/model，
  工具插件也能用自己的便宜模型）。"我给你的 api"= 配置进宿主的模型路由。
- **读法二**：作者希望在宿主之上再包一层 LH 自己的 loop，由 LH 决定何时用哪个模型。

**我倾向前者**（少了要自己维护的机制），但这是承重决策，需要作者确认后再落文档。
