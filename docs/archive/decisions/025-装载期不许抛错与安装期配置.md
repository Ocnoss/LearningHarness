# ADR-025：装载期的失败不许把宿主弄坏；运行时需要的路径在**装的时候**写下

- 日期：2026-09-18
- 状态：已采纳
- 相关：ADR-023（版本控制与启动包装器）、PLUGIN_CONTRACT §五之二～§五之五

---

## 背景：一次"改对了但没到位"的重构，差一次重启就把 dsh 弄坏

这一天的起点是一件小事：把 4 处写死的绝对路径改成"环境变量 + 从仓库根推导"。
理由充分（写死路径在别人机器上会静默读错目录），测试也过了。

然后为了修另一个问题（副本陈旧），把 profile 里的插件副本同步成最新源码——
**同步本身是对的**，但它让一个一直在等的故障终于要发生了。

`paths.js` 从模块位置往上找仓库根。在源码树里，上方**确实**有仓库，所以：
- 离线测试全绿；
- 开发时手动 `apply()` 也全绿。

但装进 profile 之后，包的位置是
`<DSH_HOME>/profiles/web/node_modules/@lh/event-store/`，
**它的上方没有 LH 仓库**。于是 `dataDir()` 抛错 → `apply()` 抛错 →
**整棵插件树加载失败 → dsh 完全起不来**。

而这个故障一直被**写死的绝对路径**挡着：profile 里那份旧拷贝用的还是
`DEFAULT_DATA_DIR = 'D:\LearningHarnessv0.1\data'`，所以"能跑"。
换句话说：**那次"去掉写死路径"的重构，会在下一次重启时把 dsh 弄坏**，
而它当时看起来是成功的。

实测确认了紧迫性：`LH_DATA_DIR` / `LH_WORKSPACE` 在机器上**哪儿都没设**
（用户级、机器级、进程级都是空），而 dsh 是用朴素的 `npx @deepseek-ai/dsh web` 启动的。
也就是说：**下一次重启就会撞上**。

---

## 决定

### 决定 1：数据目录与工作区由 `lh-install.json` 给出，装的时候写下

```json
{ "repo_root": "<LH 仓库绝对路径>", "workspace": "<工作区绝对路径>" }
```

- 仓库根一份（手工维护）；`profiles/<名>/` 一份（由 `sync-lh-deps.mjs` 生成）。
- 解析顺序：**环境变量 → `lh-install.json` → `lh-workspace` 包标记 → 抛错**。

**为什么不是"只靠环境变量"**：忘了设 → 起不来 → 学习者被困在没有入口的界面里，
连"该设什么"都看不到。一个需要**每次启动都记得设**的东西，不是一个能交付的默认值。

**为什么不是"运行时猜一个"**：猜错会去读别人的工作区，而表现只是"题库是空的"——
静默错误，比崩溃更难发现。这条早在 ADR 里定过，现在仍然成立。

**配置文件两头都避开了**：它是**显式写下的**（不是猜的），又不是**每次都要记得设的**。

### 决定 2：`apply()` 绝对不许抛错；响亮发生在"用的时候"

配置缺失、目录解析不出、服务没就绪——**都不能在 `apply()` 里抛**。
装载照常完成，把错误留到真正用到它的那一刻：
HTTP 路由返回 503 + 修法；工具返回错误 + 修法；同时往 stderr 打一行。

**理由不是"优雅降级"**，而是**失败半径**：`apply()` 抛错 = 整棵插件树加载失败 =
dsh 起不来 = 学习者失去入口。而"没有入口"这个状态，恰好让他无法看到
"该改哪一行"——**最需要说明的时刻，说明被自己弄没了**。

原来的写法（抛错）理由写得很清楚："存储不可用是系统级故障，必须显式暴露，不能静默降级"。
**理由是对的，位置是错的。** 响亮应该"看得见的响亮"，不是"把门锁上"。

### 决定 3：仓库根改用 workspace 软链（`workspace:*`）

原先根 `package.json` 用 `file:plugins/lh-event-store`，并且注释里断言
*"pnpm 会用软链指回源码，所以不存在副本陈旧问题"*。

**那句话是错的**，实测：pnpm 对 `file:` **目录**依赖是**复制**到 `.pnpm` 下、
再软链到那份拷贝。源码改了它不动。这条错误注释让一个陈旧副本藏了很久，
直到 `signal.js` 引用的 `paths.js` 在副本里根本不存在、
测试报 `ERR_PACKAGE_PATH_NOT_EXPORTED` 才暴露。

现在用 `pnpm-workspace.yaml` + `workspace:*`：**根这一层是真软链，源码即生效**。
profile 那一层仍然是拷贝（它是另一个安装根），所以仍然需要同步。

### 决定 4：同步只走一条路径，且覆盖前备份

`node scripts/sync-lh-deps.mjs` —— 按 `files` 清单逐文件拷贝，纯文件操作、离线、幂等。

不用 `pnpm install` 同步的三个理由：
1. **它不会更新**：规格没变，它认为"已是最新"，直接跳过；
2. **副作用半径太大**：profile 是 dsh 自己的安装根，在里面跑包管理器等于动宿主的地基；
3. **它的拷贝规则不是我们的规则**：实测同一个包在根和 profile 里拷出来的文件集**不一样**。

覆盖前把原件备份到 `.lh-sync-backup/<时间戳>/`。
先写的是"发现副本有源码没有的代码行就拒绝同步"，**立刻否掉了**：
删代码行正是重构的常态，那样每次重构都要敲 `--force`，
而**总是被绕过的闸门比没有闸门更坏**（人会条件反射地加 --force）。
改成留备份：覆盖永远可回溯，于是不需要拦，也不依赖判断力。

## 代价与已知局限

- **多工作区仍不可用**：配置文件里只有一个 `workspace`。要支持多工作区，
  界面必须把工作区带进请求（或宿主提供"当前活动工作区"服务）。
- **配置文件里是绝对路径**：换机器要改。它是一份**安装记录**，不是可移植配置；
  将来部署工具应当生成它（见 ADR-024）。
- **profile 副本仍需手动同步**：这是拷贝语义的必然结果。闸门会红，所以不会忘；
  但"忘记"的代价从"静默跑旧代码"降级为"闸门报错"。
- **`sessions/` 不备份**：与 ADR-023 保持一致的既有取舍。

## 这一天的元教训

1. **"测试是绿的"里，"测的是哪一份代码"是一个独立的问题。**
   源码树是活链、profile 是快照，两者从外面看一模一样。
2. **拆掉一个错误行为时，要问"原来是谁在替我报警"。**
   把 `apply()` 的抛错改成拒绝服务，让 `check-profile-apply` 从红变绿——
   **而底层仍然是坏的**。所以补了 `check-paths-resolution.mjs`：
   它直接问"每个加载位置解析出的路径是否一致"，不经过 `apply()`。
3. **写死的路径有时是"承重"的。** 去掉它之前，要问"它是不是正在替谁挡着什么"。
   这一次它挡着的，是一个会在下次重启爆炸的启动故障。
