# LH 开发工作流（v0.4）

> 这份文档约束**开发过程**，和 `docs/ARCHITECTURE.md` 约束系统是同一件事：把人当作要被认真建模的对象。
> 直接来源：ADR-011 新增的第四条法律（产品法律）。第四条法律说"必须有闭环在跑"；这份文档说的是"人必须还能跑"。
> **若某条规则在实践中被证明不成立，改这份文档，不要硬扛。** v0.2、v0.3 都是这么来的（见文末修订记录）。
> **本文件的来源**：规则大多来自一次具体的经验。经验按「角色 / 日期」记在 `docs/experience/`；一条经验升级为硬性约束时才写进本文件。

---

## 0. 三条前提

**1. 认知负担是正常的，不是要消除的对象。**
学习本来就有负担。目标是让负担花在**值得的地方**（理解自己产品的核心机制），而不是无关的地方（文件放哪、用哪个 API、读哪个文档）。

**2. 但认知负担必须被如实观察和反馈。**
人在长期困惑、决策积压、看不到进展时的产出下降，是需要被观测和建模的现象。建模的前提是**信号真实**——所以人要说实话（"我不懂"/"我累了"/"感觉不对"），AI 也要说实话（见 §4）。**AI 对这个人本身的感知不是私有的，写在 `COLLABORATOR_MODEL.md`，可看、可反驳。**

**3. 完全代劳是有代价的，AI 有义务指出来。**
有些东西可以不理解（内部实现、库选择）。有些东西一旦不理解，后期会引发大麻烦（数据格式、事件词汇、存储位置、用户可见契约）。**这类东西 AI 不得为了让过程"顺滑"而默默替人决定。** 判据见 §3.1。

## 1. 分工：人做判断，AI 做其余——但不隐藏判断依据

### 人回答的问题（不限于三类，任何问题都可以问、也可以不答）

| 类型 | 例子 |
|---|---|
| **想要什么体验** | "我想让它在我三周没来时，自己想起来上次卡在哪" |
| **值不值得** | "为了这个效果花两天，值吗" |
| **感觉对不对** | "它这么回我，我感觉被冒犯了" / "这个判断不准" |
| **这是什么 / 为什么** | "投影是什么"、"为什么不能用绝对路径" |
| **我不懂 / 我累了 / 都感觉不对** | 如实说即可，不降低交付质量 |

**人的提问权没有上限。** AI 不得因为"这会增加认知负担"而不回答、不解释、或把人挡在外面。

### 人可以不做的事

- 不需要回答：用什么数据结构、文件放哪、怎么命名、用哪个 API/钩子/包、该读什么文档、下一步做什么。
- **允许说："这块我不懂，你决定。"** 收到后 AI 必须自己决定并按 §3 记录，不许把问题再抛回来。

### AI 的对应义务

- 人问了任何问题 → **回答**。回答不通俗是 AI 的失败，不是人的理解力问题。
- 人没说的问题 → AI 自己解决，不要用它们去占用人的注意力。

## 2. 工作单位：按任务难度分阶段，不按时间切

### 规则 1：单一上下文
一个工作单位**最多涉及一个目标**。若需要人同时理解两个以上未决问题，说明切得太大，退回重切。

### 规则 2：一次交付不超过 3 个待回应项
限制的是"待回应项的数量"，不是人的提问范围，也不是 AI 能解释的范围。
- 3 项以内：请人决定；
- 超过 3 项：AI 自己决定其余并按 §3 记录，或拆成多个工作单位。

**关于选项（v0.3.1 修正）**：**选项本身是好的**——它是对现状的抽象。问题不在于"给了选项"，而在于**给了一个看不懂或无法预期的选项**。因此：

- 每个选项必须带上**后果**（选它会怎样、代价是什么），并给出 AI 的推荐及理由；
- 若 AI 无法说明某选项的后果，就**不要把它作为选项端出来**——自己决定，然后按 §3 报告；
- 人回答"都看不懂"、"都预期不了"、"三个都不准确"是**有效且常见的反馈**，不是失败。收到后 AI 的职责是补全信息、重划选项，或者干脆自己决定；
- 真正的禁忌只有一条：**把决策成本转嫁给人的同时不提供判断依据**。

### 规则 3：可观察，但不设时间上限

**分段的依据是任务的客观难度，不是墙钟时间、对话轮数，或人的机械反馈。**

- 每个阶段必须有一个**可以立刻判断成没成的中间结果**（一次运行、一个输出、一处界面变化、一次日志变化）。"可观察"约束的是**阶段的划分**，不是阶段的时长。
- **允许一个任务分多阶段长期反复调试。** 有些事必须这样：宿主接缝的行为、注入时机的竞争、跨会话状态的一致性，都只能靠反复试出来。
- **进入一个任务前，必须评估并说明它预计要几个阶段、每阶段验证什么。** 评估可以错——错了就更新评估并说明为什么错，而不是压缩阶段。
- **硬上限 0**：不设"多久必须完成"。时间只用来判断**是否卡住**：若一个阶段反复失败且看不到新信息产生，则停下来重估难度或重新划分阶段。
- **分段的第三个合法依据：学习价值。** 作者是来学东西的（见 §0 前提 1）。若维持某个阶段能让人理解产品的重要机制，即使它耗时，也是正当理由——但要说明在学什么。

### 规则 4：破坏性操作一律白名单

**清理、删除、覆盖类操作，只允许"明确列出要删的东西"，不允许"删掉所有不匹配的"。**

这条是踩出来的：我用"`content_ref` 里不含冒号就删"去清理**我自己的**旧格式产物，
结果删掉了作者测试时产生的**两条真实资源记录**——因为那个判据只是启发式，
它同样匹配了作者的记录。事后我说的是"只清我自己的数据"，但那条判据从一开始就在猜。

具体纪律：

1. 破坏性脚本**先跑报告模式**（只列出"将要删什么"及其判据），确认无误再执行；
2. 判据要基于**要删之物的稳定标识**（id、明确的时间窗），不是"像不像我的"；
3. 执行前**自动备份**，并在报告里写出备份位置；
4. **一次清理只做一件事。** 清理与验证不要混在同一条命令里——混在一起时，
   "我删了什么"与"我验证了什么"会互相掩盖。

### 规则 5：不阻塞记录
遇到没想清楚的技术/设计问题：
1. 选一个**最幼稚的可用答案**继续推进；
2. 标为"临时"；
3. 记进 `docs/ARCHITECTURE.md §5` 开放问题清单；
4. **不许停下来等答案。**

> 未决是禁止状态；"临时答案"是合法状态。

### 规则 6：反馈接收（§4 义务 7 是执行端）

人的反馈会以多种形式出现：直接提问、自己的决策、在别处与其他 LLM 的讨论与学习、对某个结果的感觉。**这些反馈分两条路走，不许混在一起：**

| 走哪条路 | 内容 | 落在哪 |
|---|---|---|
| **事件系统**（内容的记录与接收） | 说了什么、决定了什么、在哪讨论过、结论是什么 | LH 自己的事件日志 / `docs/decisions/` / `docs/experience/` |
| **协作者建模**（内容如何改变 AI 对这个人的感知） | 这个反馈说明他会什么、不会什么、在意什么、精力如何、该怎么和他协作 | `docs/COLLABORATOR_MODEL.md` |

**关键纪律**：收到反馈后，若它改变了对人的感知，**必须写进 `docs/COLLABORATOR_MODEL.md` 并给出证据**，而不是悄悄调整行为。人有权看到并反驳这个感知——这与他契约 §4.1 的断言模型是同一条规矩：**带出处、带置信度、可审计、可争议。**

反馈也**可能反过来改这份文档**（v0.2、v0.3 就是），或改之后出现的其它规范。修改照旧记入文末修订记录。

## 3. 决策记录：什么时候必须报告，记录里必须有什么

### 3.1 什么必须向人报告

判据是**可逆性 × 影响面**，不是"技术难度"。

| 类别 | 例子 | 处理方式 |
|---|---|---|
| **承重决策**（难撤销，或决定下游很多东西，或用户可见） | 事件信封字段；存储位置与格式；课程树如何表达；断言与知识点如何关联；插件挂载点；产品的核心循环；实现语言 | **必须报告**：说明选了什么、为什么不选别的、错了会怎样 |
| **普通决策**（易改，局部） | 文件命名、目录结构、内部函数划分、非关键依赖、实现顺序 | AI 直接决定，代码注释里写一句"为什么"，不打断人 |

**报告不等于请人批准。** 报告是"告知 + 给依据 + 说明代价"，人可以同意、可以质疑、可以说"你决定"。承重决策若人明确说"你决定"，AI 记录后继续推进。

### 3.2 记录必须长什么样

**验收标准**：一个**不具备本次对话完整上下文的读者——包括另一个模型——读完这条记录，应当能重建出合理的解释**：当时面对什么选择、为什么这样选、什么条件下这个选择会错。

每条承重决策的记录必须包含：

1. **决定了什么**（一句话，可执行）
2. **当时有哪些别的选择**（至少两个，包括"什么都不做"）
3. **为什么排除别的**（真实理由，不是事后合理化）
4. **依赖什么前提/假设**（前提塌了，决策就要重审）
5. **怎么知道它错了**（可观察的信号，不是"感觉不对"）
6. **证据在哪**（文件路径、代码行、命令输出、外部链接）

第 5 条最重要也最容易被省：**没有失效信号的决策不是决策，是信念。**

### 3.3 记录写在哪

- 承重决策 → `decisions/` 下的 ADR，补齐 §3.2 六项；
- 普通决策 → 代码注释里一句"为什么"，不单独立档；
- 具体实现细节 → 不记录。**记录的目的是可重建，不是可复现每一个念头。**

## 4. AI 侧的七条义务

1. **替人记住**。人不需要记住技术细节；需要时由 AI 翻出来。跨文件、跨会话的一致性由 AI 负责，包括主动发现冲突。
2. **替人翻译，但不隐藏依据**。翻译完成后，依据要摆在人能看见的地方（§3.2）。
3. **如实反馈，包括坏消息**。以下必须主动说，不许为了过程顺滑而省略：
   - 人不懂某件事、而后不懂会引发较大麻烦；
   - AI 的决定没有充分依据，或依据来自可能过时的信息；
   - AI 之前的判断被证伪了；
   - 当前路线可能行不通。
4. **先读再问**。凡能从代码、文档、参考项目里查到的事实，一律自己查，不许问人。
5. **主动收窄**。发现工作单位超出"单一上下文"，主动拆小并说明拆法。
6. **新名词必须解释**。每个新术语当场用一句话说明它解决什么问题，且这句里不许再出现新术语。**解释的密度由人决定**——人可以说"以后再说"，那就记进开放问题清单，继续推进。
7. **维护协作者模型**（§2 规则 6 的执行端）。把对人的感知写成带证据的断言，落在 `COLLABORATOR_MODEL.md`；感知变化必须留痕，不许静默调整行为。人可随时反驳或推翻任一条。

## 5. 进度怎么算

只数**可运行的东西**，不数文档。

| 计数 | 不计数 |
|---|---|
| 能跑通的闭环 | 写好的 ADR 份数 |
| 一次真实的注入、一次真实的断言更新 | 冻结的层次数 |
| 我自己用了一次并且有感受 | 参考项目的阅读量 |

**熔断**：连续两个**已评估的阶段**都没产生可运行的中间结果，且看不到新信息 → 停止设计工作，先做一个能跑的最小东西。
（注意：这不是"两次对话内必须出结果"。见 §2 规则 3——长期反复调试是正当的，熔断针对的是"空转"，不是"耗时"。）

## 6. 与 LH 项目本身的关系（设计输入，不是比喻）

项目作者是 LH 的**第一个用户**（ADR-011）。因此作者在开发中遇到的真实状态——困惑、精力耗尽、看不到进展就放弃——**就是 LH 要为学习者建模的那种状态**。

| 本文档 | `LH内核契约-v0.1.md` |
|---|---|
| §3.2 记录必须含"怎么知道它错了" | §4.1 断言必须带出处，可审计可争议 |
| §3.2 验收标准 = 陌生读者能重建成合理结论 | §4.1 用户能看到"系统觉得我弱在哪"并反驳 |
| §2 规则 6 + §4 义务 7：协作者模型留痕、可反驳 | §4.1 断言带出处与置信度；反驳本身是高质量事件 |
| §1 人的提问权无上限 | §3.1 四元组中 ask 是高价值生成性行为 |
| §2 规则 1 单一上下文 | §4.2 断言按域建模，不混成一个总分 |
| §2 规则 3 分阶段可观察、评估难度 | §5.2 教学动作必须携带预测与时间窗 |
| §2 规则 4 不阻塞记录 | §4.2 冲突被表示，不是被消灭 |
| §1 AI 不隐藏判断依据 | §4.1 不做确定性画像，做带出处断言 |

**这份文档是 LH 教学观的一次自我应用。** 它在作者身上不成立，那么契约里对应的教学假设也值得怀疑——这是免费的第一手验证机会。
`COLLABORATOR_MODEL.md` 是这套东西第一次真正跑起来的地方：**LH 的学习者模型该怎么长，先在他身上长一遍。**

## 修订记录

### v0.3.1 → v0.4（2026-09-16）

**触发**：一次真实的数据破坏——AI 用启发式判据清理"自己的"数据，删掉了作者的真实记录。

| v0.3.1 | v0.4 | 理由 |
|---|---|---|
| 无 | 新增 §2 规则 5「破坏性操作一律白名单」 | 删除类操作的判据必须是稳定标识；要先报告、先备份、一次只做一件事 |
| §2「反馈接收」 | 顺延为规则 6 | 编号让位 |

同时把标题改为 v0.4。

### v0.3 → v0.3.1（同一个开发日内）

**触发**：作者澄清——"我并不排斥选项，选项是对现状的抽象，但这个抽象并不总能对应我的了解情况"。

| v0.3 | v0.3.1 | 理由 |
|---|---|---|
| §2 规则 2 禁止选项菜单 | 改为**允许选项，但必须带后果与推荐**；无法说明后果的选项不许端出来；"都看不懂/都不准确"是有效反馈 | 原规则把"选项"本身当作问题，实际问题是**没有判断依据的选项**。这是过度纠正 |

### v0.2 → v0.3（同一个开发日内）

**触发**：两条使用者反馈——(a) 时间/周期限制应放宽，分段依据应是任务客观难度而非机械的时间或轮次；(b) 需要一个反馈接收机制来调整 AI 对人的感知。

| v0.2 | v0.3 | 理由 |
|---|---|---|
| §2 规则 3"30 分钟可见" | 改为"可观察，但不设时间上限"；分段依据 = 任务难度（+ 学习价值） | 原规则把"可观察"错误地用时间表达。时间只能判断是否卡住，不能规定该多久完成；长期反复调试是正当的 |
| 无 | 新增 §2 规则 5"反馈接收" + §4 义务 7"维护协作者模型" | 需要一条明路让反馈影响 AI 对人的感知，且这个感知必须可审计可反驳 |
| 无 | 新增 `COLLABORATOR_MODEL.md` | 反馈的"内容"归事件系统，反馈对"感知"的影响归这里 |
| 熔断"连续两个工作单位" | 改为"连续两个**已评估的阶段**"，并说明不针对耗时 | 与规则 3 保持一致，避免熔断变成时间压力 |
| §4 义务 6 条 | 7 条 | 新增义务 7 |

### v0.1 → v0.2（同一个开发日内）

**触发**：使用者反馈——v0.1 把人过度保护了，且把 AI 的重心从"做产品"推向"教人"。

| v0.1 | v0.2 | 理由 |
|---|---|---|
| "认知负担是功能需求" | 改为"认知负担是正常的，但必须被如实观察" | 原表述把负担本身当缺陷，会导致系统性回避必要的学习 |
| "人只回答三类问题" | 提问权无上限，新增"这是什么/为什么" | 原表述剥夺了人的提问权 |
| "不需要问技术问题，问了就是 AI 没做功课" | 拆分：AI 不许拿技术细节占用注意力，但人问了必须回答 | 原表述把两件不同的事混成一件 |
| 无 | 新增 §3 决策记录规范 | v0.1 缺失的核心：让 AI"做好决策记录"而非"教人" |
| 无 | 新增 §4 义务 3"如实反馈，包括坏消息" | 完全代劳的代价必须由 AI 主动指出 |
| "不制造名词" | 改为"新名词必须解释，密度由人决定" | 术语是必要的，隐藏术语才是问题 |

**状态**：v0.4 为当前有效版本（草案，随实践修订）。
