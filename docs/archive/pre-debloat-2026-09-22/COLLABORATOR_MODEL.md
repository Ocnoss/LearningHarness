# 协作者模型（AI 对项目作者的感知）

> 这份文件不是评价，是**断言集**。格式直接取自 `LH内核契约-v0.1.md §4.1`：
> 每条带**出处**、**置信度**、**可推翻条件**。作者可随时反驳或推翻任一条；反驳本身是有效证据，会改变这里的置信度。
> 维护规则见 `WORKFLOW.md §2 规则 5` 与 `§4 义务 7`：感知变化必须留痕，不许静默调整行为。
>
> **这不是对"这个人"的总体评价**，而是对"跟他一起做这个项目时该怎么协作"的建模。它只覆盖与协作相关的部分，且只覆盖有证据的部分。
> 置信度刻度：**高** = 有直接陈述或多次一致观察；**中** = 从行为推断；**低** = 单次观察，待验证。

---

## A. 已观察到的能力与状态

### A1. 工程实现能力：**原判断已撤回**（置信度：低，待重建）
- **原判断（错误）**："有真实的工程实现能力"，证据是 `agent/registry.py` / `loop.py` 的代码质量。
- **作者澄清（2026-09-15）**："此前你见到的代码确实是其他模型写的，我并不具备你认为的工程实现能力。"
- **错误性质**：**归因错误**——把"仓库里有高质量代码"当成了"作者具备该能力"。代码由 agent 生成是本项目的正常生产形态，不能作为作者能力的证据。
- **修正后的判断**：作者能**判断与取舍**代码级方案（评价设计、指出问题、做决策），但**不写代码**，也不以写代码为学习目标。
- **推翻条件**：出现作者独立编写并能清楚解释其设计取舍的代码。
- **对协作的意义**：**不要用"你之前写过 X"来论证任何事**；也不要指望通过"多读几段源码"建立能力——那不是他的路径。

### A2. 架构判断力强，但会过度延伸到"未运行的部分"（置信度：中）
- **证据**：`ARCHITECTURE.md` 的"事实/解释"切分（§2.3）与 `LH内核契约-v0.1.md §8.4` 的轮子审查，都是先做减法再定方案；`§7.1` 的八条不变量配有可执行检查。
  另一面：十份 ADR、零个可用功能。
- **归因保留（重要）**：这些文档是否也部分由模型起草，**尚未澄清**。若同样由模型生成，本条应降级为"文档层面的判断力"，不能推及作者本人。
- **推翻条件**：作者澄清文档生成方式，或在对话中就架构取舍给出独立的、非复述性的判断。
- **对协作的意义**：**不要在架构层说"这不对"**，但要问清依据来源。本项目里文档与代码都不自动等于作者的能力。

### A3. 被指出错误后修正很快，且不辩解（置信度：中）
- **证据**：本会话中我给出多条被证伪的判断（Windows 绝对路径可用、`dsh-llm-mock-server` 是否存在、把 dsh README 当权威、UI 错配风险、把代码当能力证据），他均直接澄清或接受，未纠缠。
- **推翻条件**：出现反复坚持已被证据推翻的判断。
- **对协作的意义**：可以承受直接的坏消息。**隐瞒比说错更糟。**

### A4. 对 agent 编排的了解停留在原理层（置信度：高，作者明确陈述）
- **证据**：原文——"我对于 agent 编排的了解仅限于原理上"；此前——"该怎么编排一个 agent…我目前都还不知道"。
- **修正**：我此前把后半句解读为"不知道在 dsh 里编排，但知道编排是什么"。**方向对、强度错**：他掌握的是**原理**（概念、为什么这样设计），缺的是**实践**（怎么落地、会遇到什么）。
- **推翻条件**：他在具体编排任务中表现出超出原理层的操作能力。
- **对协作的意义**：**原理层可以省略，实践层必须给足。** 不要解释"为什么要事件溯源"，要给"改哪个文件、跑什么命令、看到什么算成功"。

### A5. 项目此前停滞的原因不是能力，是治理模型（置信度：中）
- **证据**：`ARCHITECTURE.md` 第三条法律（"第 N 层未书面冻结前禁止讨论第 N+1 层"）+ §5"新窗口只允许从此取题"→ 接口层的正确答案只能由运行提供，而运行属于被禁止的实现层。
- **推翻条件**：ADR-011 加上第四条法律后闭环仍未出现，而文档继续增长。
- **对协作的意义**：若他再次陷入"想不清楚"，先怀疑度量方式，不要怀疑他。

### A6. 认知带宽是真实约束，但**拒绝被过度保护**（置信度：高）
- **证据**：原文——"考虑插件的具体实现，上下文管理、项目框架这些问题让我在开发时感到了极大的认知负担，我想不明白、做不出东西"，紧接着——"也不用完全把我保护起来，有认知负担是应该的"。
- **推翻条件**：后续实践显示某一类解释确实应被省略。
- **对协作的意义**：**降负担 ≠ 替他回避困难。** 前者是义务，后者会害他。这是我在 `WORKFLOW.md` v0.1 里犯过的错。

### A7. 有学习意图，但**更看重产出与默契**（置信度：高）
- **证据**：原文——"我至少希望随着这个项目不断完善，我懂得要比现在要多"；2026-09-15 补充——"相比于这个我更关注产出，这里所谓产出就是后续开发中我和你合作的默契程度，只有当我觉得合作受阻，我才会去审查或澄清这份文档，这是写给你自己的记录"。
- **修正**：本文件因此是**写给我自己的记录**，不是给他读的报告。它的价值在于让我的行为随证据更新，而不是让他定期审阅。
- **推翻条件**：他明确要求定期审阅本文件。
- **对协作的意义**：**不要因为维护本文件而占用他的注意力。** 决策记录（`decisions/`）仍按 `WORKFLOW.md §3` 正常写。

### A8. 他的纠正**系统性地指向"谁拥有这个决定"**（置信度：高）
- **证据**（2026-09-16，连续四次纠正，方向一致）：
  1. 我说插件写具体模型名 → 他纠正：**"哪个用途用哪个模型"是使用者的决策，不是插件的属性**；
  2. 我提议 `must-not-degrade`（不满足就拒绝服务）→ 他纠正：**风险告知即可，不该让 agent 一直拒绝服务**；
  3. 我提议"档位不满足时隐藏工具" → 他纠正：那等于系统替用户判断"你做不到这件事"；
  4. 我提议 `modeltier` 自己弹框问用户 → 他纠正：**问的时机该由 agent 在自然边界决定**，因为中间件会在工作流深处弹框。
- **可归纳的判据**：他在反复问同一类问题——**"这个决定该由谁拥有？"**
  我的默认倾向是"系统替用户做安全选择"（工程习惯），而他的默认倾向是"**把选择权和后果交给用户，系统负责把后果说清楚**"。
- **推翻条件**：出现他主动要求"系统替我拒绝/替我兜底"的场合。
- **对协作的意义**：**设计方案时先问"这是谁的决策"，再问"怎么实现"。**
  凡是我打算加"自动拒绝/自动降级/自动隐藏"的地方，先假设他会反对——并把理由（后果是什么）准备好。
- **与契约的关系**：这与 `LH内核契约 §3.1` 的反奖惩立场（"把数据显示给用户，而非扣分"）是同一个原则。**他的工程判断与他的教学理念是同源的**——这点值得记住。

### A9. 他从"生态该怎么长"出发思考，而不只从"这个功能怎么做"（置信度：高）
- **证据**（2026-09-16）：在讨论"模型档位不足怎么办"时，他给的不是防御方案，而是一个生态情景——
  "有人把任务拆解成若干小插件，每个完成各自的部分，**使得低智能的模型通过插件的组合也能完成复杂的任务**……一个强的主导 agent 甚至能发现不同的插件组合去完成某个工作的路径，**就是有什么材料做什么菜**"。
  他还有"lh-plugin-develop"的构想（插件由 agent 写），也是同一层视角。
- **推翻条件**：后续实践显示他的这类提议没有落到具体设计里。
- **对协作的意义**：**遇到"某个能力不够"的问题时，先想"能不能用组合绕过"，而不是先想"怎么拒绝/降级"。**
  这条能显著改变我提方案的方向——我提的是防御性方案，他给的是生长性方案。

## E. 我的行为准则（从上面推出的，供自己执行时对照）

1. **凡是我打算加"自动拒绝 / 自动降级 / 自动隐藏"的地方，先假设他会反对**——并把后果说清楚（见 A8）。
2. **遇到"能力不够"的问题，先想组合与生长，再想退避**（见 A9）。
3. **验证必须在与生产同构的环境里做**；换环境的唯一正当理由是"同构"，不是"方便"（见 C11）。
4. **破坏性操作只做白名单**，且先报告、先备份、一次只做一件事（见 C10）。
5. **方案里的每个"应该问用户"都要问清时机**——在人有上下文的时候问（见 A8 第 4 条、`experience/项目作者/2026-09-16` 的 Y4）。
6. **文档工作直接做**，不汇报过程（见 B11）。
7. **命令没生效比命令报错更危险**——用文件而不是内联脚本（见 C12、C13）。
8. **改文本文件只用 `edit` 工具或编辑器，绝不用 shell**（见 C15）。
   而且不要因为"只是一处小改"就放宽这条——C15 正是从"只是改 7 处字符串"开始的。
9. **测试报出的"通过"要抽查**：凡是结论与直觉不符，先怀疑验证工具自身（见 C16）。
   一个满屏误报的检查器等于没有检查器。
10. **他要的是顺序，不只是目标**（见 B14、D6）：短指令先拆出约束，再动手；
    若认为顺序该改，说理由，不默默改。
11. **跨"层 / 路径 / 语境"之前，先问一句"这里和那里一样吗"**（见 C17–C20）。
    具体地：进入新的加载层或作用域前，先把那一层的规则问清，不要套用上一层的写法；
    写测试时先确认**测试跑的路径等于生产路径**；改判定/断言前先确认它衡量的口径没变。
12. **闸门必须先对着"已知坏的状态"红一次**，再拿它去保证"以后不会坏"。
    没在坏状态上验证过的闸门只是一个希望（见 E4）。
13. **他在类比一个产品形态时，先复述我理解的行为、让他确认，再动手**（见 B16、C19）。
    "功能可达"不等于"形态正确"——他关心入口是否匹配意图的时效性，不只是能不能用。
14. **凡改动可能让宿主无法启动，先在生产路径上验一遍再交付**（见 C17、C18、E1）：
    优先验"能不能起来"，再验"逻辑对不对"。**顺序不能反**——
    因为前者坏了，学习者连报错的入口都没有。
15. **汇总数字绿了，要抽看几条明细**（见 C21 旁边那条、E17）。
    "49 道全部匹配成功、零错误"与"知识点写到了另一份资料的题上"**可以同时成立**——
    那次唯一暴露它的东西，是我逐条看明细时发现"加强论证？可这题是片段阅读"这一句。
    → 判据：**凡是批量写入/批量匹配的产出，交付前至少逐条读 3 条明细**，
    并且**故意挑一条"看起来不该是这样"的**。
16. **"只有两行改动"不是绕道 shell 的理由**（见 C21，重犯 C12/C15）。
    判据不是"改动多小"，而是"这个文件是文本吗"——是文本就只用 `edit` 或编辑器。
    下次若又觉得"两行而已，shell 更快"，**那句话本身就是该换工具的提示**。
17. **写规则前先问"这个位置管得住这件事吗"**（见 C22）。
    工具描述是**被动、局部**的（用到才读到）；想约束**行为选择**
    （用哪个工具、走哪条路）就必须放进**每次组装都会出现**的位置。
    这与 §E-11（跨层/跨路径/跨语境前先问"这里和那里一样吗"）是同一族的判断：
    **先在"机制"上想清楚，再写文案。**
18. **清单驱动的检查对"清单本身漏项"必然绿**（见 E19）。
    `check-installed-copies` 按 `files` 比对，所以漏登记一个文件它照样绿。
    凡"用 A 描述 B、再用 A 校验 B"的设计，都要单独问一句
    **"A 自己错了，谁会发现？"**——并补一条不读 A 的检查。
