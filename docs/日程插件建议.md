# 日程插件建议（日历/日程落地之后）

> **这份文档的定位**：它是在 `@lh/schedule`（preset 行，投影 `lh/schedule/*` 事件、注册 `create_schedule` / `list_schedule` / `update_schedule` / `cancel_schedule` 四个工具、注入运行时上下文 `lh:agenda`（order 118））与 `@lh/schedule-ui`（profile 行，`main` 槽 `lh-calendar` + `sidebar.panellist`，服务端路由 `GET /lh/schedule/health`、`GET /lh/schedule/calendar`、`POST /lh/schedule/create|update|cancel`）**落地之后**写的功能建议清单。它不是 ADR、不是路线图、不是承诺：没有一条是"计划要做"，都只是"如果要做，可以这样做"。每条建议的验收标准是**能被单独做成一个插件**——可以整条采纳，也可以只摘其中一半。
>
> 术语全部沿用上面那版落地设计：日程项字段 `item_id / title / day('YYYY-MM-DD') / start,end('HH:MM') / kind(study|review|class|exam|rest|deadline) / status(planned|done|cancelled|skipped) / course_id / session_id / note / minutes_planned / minutes_actual`；事件族 `lh/schedule/created|updated|linked|done|cancelled`，`scope = schedule/<item_id>`；日历视图 = ①计划（日程项）②事实（`lh/trace/observed` → 哪天哪段对话有学习活动）③课程安排（`lh/course/*`）三件事按日期索引。
>
> 全文标注纪律与 `ARCHITECTURE.md` 一致：**未验证/假设** 是一等公民，凡我猜的都写明是猜的。

## 0. 先划三条边界（八条建议共用的前提）

**边界一：三个东西不能混。**

| 归属 | 它是什么 | 谁拥有 |
|---|---|---|
| 宿主「自动化任务」插件 | 到点以 user 消息投递的**提醒**（一次性/每日/每周/cron），与会话绑定 | 宿主，工具名 `schedule_create` / `schedule_list` / `schedule_update` / `schedule_delete` |
| `@lh/schedule` | **日程项**本身：创建/查询/修改/取消，append-only 事件，供模型与日历读 | LH，工具名 `create_schedule` / `list_schedule` / `update_schedule` / `cancel_schedule` |
| 本文各建议 | 在两者**之上**加判断（算、对账、诊断、桥接），不重造前两者的机制 | 各自一个插件 |

下面任何一条建议，**都不许**注册与宿主 `schedule_*` 同名的工具，也不许自建定时器。

**边界二：写日程只有一条路径。** 任何插件要写日程，都调 `@lh/schedule` 的同一份 commands（也就是 `/lh/schedule/create|update|cancel` 路由与 agent 工具背后那份），**不许自己 `append` `lh/schedule/*` 事件**——否则事件合法但字段语义漂移，日历会在几个月后开始显示谁也不认识的条目（ADR-023 的 schema 契约纪律）。这条是硬的，不是风格。

**边界三：算出来的东西不进日志。** 倒计时、完成率、冲突、FSRS 到期日都是**派生量**，属投影/缓存（ADR-014：「可派生的不进日志」）。只有"我打算给申论每周 3 小时""我把这条规律铺成日程""我提醒过他了"这类**发生过的事**才配新事件族。

以下八条按"离学习者的痛有多近"排，不按实现难度排。

## 1. `@lh/review-scheduler`：复习日程由作答证据自动生成（间隔重复）

**要解决的问题**
他在刷题面板做完第 3 册的 30 道片段阅读，插件告诉他"其中 11 题该在周四复习"。问题是**没有人把"该复习"变成日历上的一个时段**：题目级排期有几百条，日历要的是"周四 20:00–20:40，20 题"。他手工搬了两周就放弃了——不是不想复习，是"从 11 个题目 id 到一条日程"这一步没人做。这正是 `ARCHITECTURE.md` 开放问题 2「跨会话调度器接口：间隔重复、复习时机」的形状。

**做成什么插件**
`@lh/review-scheduler`，**preset 行**（要读事件、要写日程、要给模型工具）。可选再加一个 profile 行的只读卡片，显示"下一个复习时段"。
工具：`plan_reviews(range, capacity_minutes_per_day)` —— 输入时间窗与每日容量，输出"我将写入哪些复习日程项"，**先预览后写入**；写入仍走 `@lh/schedule` 的 commands。
上下文：不新增。日程一旦写进去，`lh:agenda`（order 118）本来就会告诉模型"今天有哪些日程"。

**数据从哪来**
- 纯投影部分：`lh/user/attempt`（作答事件，ADR-022 记录的就是这个类型）+ 题目资源上的知识点标签。FSRS 状态（每题的 stability/difficulty/到期日）是派生量，**不进日志**。
- 写回部分：`lh/schedule/created`（`kind: 'review'`），**不需要新事件族**。
- 但"这批复习日程是按哪几道题的到期算出来的"目前无处安放：`item_id` 是日程项，题是资源。建议二选一——(a) 在 `created` 的 `data` 里加一个 `derived_from: ['lh/user/attempt:…']` 式血缘字段（信封是否允许自定义字段**未验证**，ADR-012 说信封字段由内核注册表登记）；(b) 用 `lh/schedule/linked` 把日程项指回题目/知识点，但 `linked` 当前的 `data` 形状是否够用**需确认**。这一条是建议 1 里唯一"需新增"的东西。
- 算法：契约 §8.4-A 已决定采用 `ts-fsrs`，不自造。

**与既有插件的关系**
复用 `@lh/schedule` 的投影与 commands（不自己写事件）、复用题库/刷题插件的作答读取；**不动**宿主「自动化任务」；**不动**课程树与断言器。

**最小验证方式**
造一份假作答序列（跨 7 天、3 个知识点、30 题、每题答 2 次），喂给投影，检查：① 输出的复习日程总分钟数 ≤ `capacity_minutes_per_day × 天数`；② 同一天不出现同一知识点两次；③ 冷启动（无历史）时**不会**一次铺满 30 天日历。第 ③ 条最关键，是这类插件的典型翻车点。

**风险/代价**
- `ts-fsrs` 对"刷题"这一场景的参数（初始 stability、评分映射：答对/答错/未判 `null` 怎么折算）**未实测**；判分三态里的 `null`（判不了）不能默认算错，FSRS 侧必须有对应处理，否则统计与排期会一起错。
- 冷启动会一次性产生大量"今天到期"，这是算法性质不是 bug，插件必须自带容量上限，**但上限本身不该由插件替用户决定**（把选择权与后果说清楚，别替他拒绝）。
- token 成本主要花在"模型向用户解释为什么这么排"，不是计算。预览输出要短。
- 依赖 `lh/user/attempt` 的字段里确实有可用的题目 id 与作答时间：**未验证**，实现前先 `read` 一条真实事件。

## 2. `@lh/plan-reconcile`：计划与实际对账（把日历从愿望清单变成事实索引）

**要解决的问题**
周一他排了"周三 20:00 资料分析 40 分钟"。周三晚上他实际在跟模型聊数量关系，聊了一个半小时。周五打开日历，周三那条还是 `planned`、还是原色——日历**不知道也不需要知道**他做没做。于是他慢慢学会不信任这个日历：它显示的是他曾经打算做什么，不是他做过什么。日历于是退化成愿望清单。

**做成什么插件**
`@lh/plan-reconcile`，**preset 行**。
工具：`reconcile_day(day)`（对一天的账）、`list_plan_facts(range)`（区间对账，给模型看表格）。
上下文：可选地把"今天计划了、但当前还没观察到活动"的项追加进 `lh:agenda` 的文本里。建议**默认关**——每步都注入对账信息会烧 token，也让模型倾向于盯着计划而不是盯着学习者。

**数据从哪来**
**纯投影，不新增事件族**（这一条是全篇八条里唯一完全不需要新事件的）。
- 计划侧：`lh/schedule/*` 投影出的到期 `planned` 项（`day < today`，或 `day = today` 且 `end < now`）。
- 事实侧：`lh/trace/observed`（`tool/call` 类型）按日期分桶 + `lh/schedule/done`。
- 对账结论是派生量，不进日志。**但"自动收敛"要留痕**：如果对账发现"这条确实没做"，插件只**提议** `status → skipped`，写动作由模型或界面调 commands 完成（记 `lh/schedule/updated`）。插件不许偷偷改状态——那等于系统替用户认定他失败了。

**与既有插件的关系**
复用 `@lh/schedule` 投影与 commands、复用记录器插件的 `lh/trace/observed`；不动宿主、不动课程树。

**最小验证方式**
造一天的假 trace（三段 `tool/call` 时间戳），跑对账，检查输出**恰好分三类**：有痕迹的计划 / 无痕迹的计划 / 无计划的事实。重点看第三类有没有被错配成"完成了另一门课的计划"——**必须靠 `course_id`/`session_id` 匹配，不能靠时间接近**，靠时间接近是最容易犯且最难发现的错（静默错位在本项目真实发生过，ADR-020）。

**风险/代价**
- `lh/trace/observed` 只有 `tool/call` 粒度：他读纸质资料两小时、或者纯思考，**不会产生任何痕迹**。"无痕迹 ≠ 没学习"，文案必须写成"没有观察到活动"，不能写成"你没做"。这与内核契约 §3.1 的反奖惩立场同源（把数据显示给用户，而非扣分）。
- 判断"这段 trace 属于哪门课"依赖 `lh/course/session-bound` 与会话 id；界面来的作答缺会话坐标是**已知缺口**（`ARCHITECTURE.md` 开放问题 3，路由无会话上下文），所以从界面产生的学习行为可能对不上账——临时答案就是"如实报为未知归属"，别猜。
- 时间戳只有天粒度可用时会粗；第一版明确只支持"按天对账"，不做"按小时"。

## 3. `@lh/time-budget`：跨课程时间预算与冲突检测

**要解决的问题**
他同时学行测和申论。两周后回看才发现：申论**一次都没排上**，不是不想学，是每次排计划时注意力都在眼前那门课上。另一个画面：周三 20:00，行测和申论各排了一次，他坐下才发现只能做一个。第三个画面：距离 11 月 30 日考试还有 21 天，原来的常规计划和"冲刺计划"叠在一起，日历上一天 6 小时，他看一眼就关掉了。

**做成什么插件**
`@lh/time-budget`，**preset 行**。
工具：`check_conflicts(range)`（同一时段重叠、某课程长期零排期）、`suggest_rebalance(targets)`（在给定周预算下重排，**输出的是提案，不是自动执行**）。
上下文：**不注入**。这类计算只在被问到时跑，否则每步都烧 token 换来人根本不需要的信息。

**数据从哪来**
- 纯投影部分：`lh/schedule/*` 全族 + `lh/course/*`（建课/改名/绑会话）+ `lh/course/session-bound`。
- **需新增**（可选但推荐）：一个极小的 `lh/schedule/budget` 事件族，`data: { course_id, minutes_per_week, from, to }`。理由：「我打算每周给申论 3 小时」是一句**发生过的话**，不是从别处能算出来的派生量，所以它配进日志。如果作者觉得这个太细，第一版可以退化成"budget 只存在会话上下文里、不落日志"——代价是重启后他对自己的承诺就没了。

**与既有插件的关系**
复用 `@lh/course-tree` 的 `tree.js` 拿课程树与层级（不自己重推一套）；日程写回一律走 `@lh/schedule` commands；**不动**断言器（"该排多少"不是对学习者状态的判断，是排期计算）。

**最小验证方式**
造一份假日志：4 门课、3 周、含一次真重叠（同一天、时段相交、都非 `cancelled`）。检查：① 只报真重叠，`cancelled` 与 `done` 的项不参与冲突；② "某课 14 天 0 分钟"能被如实列出；③ 相邻不重叠（20:00–21:00 与 21:00–22:00）**不报**冲突。

**风险/代价**
- "该排多少"没有权威答案。插件只能给**显化**（你这门课 14 天 0 分钟）和**提案**，不能给分数或评级——否则它就是第 4 条那个要防的东西。
- `lh/schedule/budget` 一旦定名就是长期负担（ADR-023：schema 契约改名成本高），实现前值得先和课程树的 `lh/course/*` 词汇表对齐一次命名风格。
- 时区：他把系统时区改了、或跨时区学习，`day + HH:MM` 的解释会错。第一版只支持本地时区并写清楚，不假装处理时区。
- 冲突检测对"软冲突"（两门课各 30 分钟、中间不休息）无感。是否值得做**假设**：不值得，先不做。

## 4. `@lh/plan-diagnosis`：计划质量诊断（显化，不打分）

**要解决的问题**
他连续三周每天都排 5 小时，实际平均 1.2 小时。日历上看不出"这个计划从一开始就不可完成"，因为失败的信息散在 30 多条日程里，每条单独看都挺合理。他需要的不是被提醒"你完成率只有 24%"，而是看到一句大白话：**你每天排 300 分钟，实际 60 分钟，已经持续 14 天了**——然后他自己决定是降计划还是加时间。

**做成什么插件**
`@lh/plan-diagnosis`，**preset 行**（要能算，要能给模型一个工具）；可选一个 profile 行只读面板。
工具：`diagnose_plan(range)`，返回**一组显化陈述**：计划总量 vs 观察到的实际时段、完成率随时间的走向、被反复推迟的 `kind` 排名、`minutes_planned` 与 `minutes_actual` 的分布。
上下文：默认不注入。

**数据从哪来**
**纯投影**。
- `lh/schedule/done` + `lh/schedule/updated`（改期历史）+ `lh/trace/observed`。
- 关键前提：**"被推迟了 6 次"必须可数**。`lh/schedule/updated` 是 append-only、每次改一条，所以改期次数天然可数——**但需要确认落地实现没有做"覆盖式写入"**（如果 update 只记最终值，这条诊断就没有数据源了）。这是实现侧要核对的一处，不是文档能定的事。
- 诊断结论**不回流为课程断言**。它是对"计划"的评价，不是对"学习者"的评价；一旦变成断言，它就会沿课程树上行，变成系统对一个人的判断。

**与既有插件的关系**
复用 `@lh/schedule` 全族与记录器的 `lh/trace/observed`；与课程树、断言器**完全不动**，这是有意为之。

**最小验证方式**
造"每天排 300 分钟、实际 60 分钟、连续 14 天"的假日志，检查输出第一句是否直接给出"计划 300 / 实际 60、持续 14 天"，并且**全文不含任何鼓励/敦促/评价性措辞**（"你应该更努力""完成率偏低"这类都算不合格）。文案本身是这条建议的验收项——§3.1 的反奖惩不是理念声明，是文案测试。

**风险/代价**
- **最容易滑向奖惩面板的一条**。任何"红黄绿""分数""打星"都会让它背离立场。建议里明写：只显示事实与比值，不评级、不排名、不推送给别人。
- 数据质量依赖 `minutes_actual`，而它靠模型或用户手填：**脏数据会让诊断的可信度低于它的说服力**——这比没有诊断更糟。所以输出里要带"N 条日程缺 `minutes_actual`"的诚实提示。
- 输出若进 `lh:agenda` 会每步烧 token，因此默认只在被问时算。

## 5. `@lh/reminder-bridge`：提醒投递（借宿主的定时器，不自建）

**要解决的问题**
日历里排了 20:00 的复习，但 20:00 他在写代码，**没打开 LH**。日程安静地躺在那里变成 `skipped`。他需要有人推一下，而且推送要能在他不主动打开应用时到达（宿主的自动化任务能做到这一点：到期以 user 消息投递）。

**做成什么插件**
`@lh/reminder-bridge`，**preset 行**。它**不注册任何自己的定时器**，只做"日程项 → 宿主提醒"的翻译。
它可能有两种形态，可靠性完全不同：
- **(a) 让模型兼任桥**：模型看到 `lh:agenda` 里的日程，自己调宿主的 `schedule_create`。零宿主假设，但时机不可靠（取决于模型什么时候想起）。
- **(b) 插件代码直接调用宿主的调度服务或宿主工具**：可靠，但**未验证**——ADR-014 实测只保证 preset 作用域拿得到 `ctx.llm` / `ctx.systemPrompt` / `ctx.tools` / `ctx.sessions`，能不能直接触发一次宿主工具调用、能不能拿到任务调度服务，都没实测。
建议：先做 (a) 并把不确定性写进提示词（"若用户要求到点提醒，用宿主提醒工具，而不是承诺自己会记得"），把 (b) 列为一条**独立的宿主验证任务**。

**数据从哪来**
纯投影 `lh/schedule/*`（`planned`、`day`/`start`、非 `rest`）。
**可选新增** `lh/schedule/reminded`（`item_id` + 投递方式 + 时间）：宿主的提醒状态在宿主自己的家里，LH 日志里没有，于是"重复投递/漏投递"在 LH 侧**无法审计**。想要可审计就得自己留痕——但也要接受"LH 记了我提醒过，宿主实际没投递"的偏差。是否值得，取决于他多信任那条链路。

**与既有插件的关系**
明确**不重造**宿主「自动化任务」的定时器与投递管线；**不与其工具重名**（LH 侧工具叫 `bridge_reminders` 之类，绝不能叫 `schedule_create`）；不动 `@lh/schedule` 的事件语义。

**最小验证方式**
手工建一条 3 分钟后到期的日程，跑桥，观察会话是否在到期时收到一条 user 消息，且该消息里**能指回 `item_id`**（否则他没法知道这条提醒对应哪条日程、也就没法从提醒回到日程）。再做一次"应用没打开"的情况——那才是真实场景。

**风险/代价**
- 宿主的「自动化任务」是开发者预览版：工具 schema、投递时机、跨会话行为**都未实测**。
- **两个家**的风险（ADR-031 那个"最贵的失败形状"的同构版）：仓库 `.dsh` 与 Electron desktop 的 `~/.dsh` 是两套自动化任务状态，设了提醒却不响，症状与"忘了重启"一模一样。
- 每小时级精准投递宿主是否保证**未知**；如果只有分钟级轮询，20:00 的提醒可能 20:03 到，文案上别承诺精确。

## 6. `@lh/exam-context`：让日程（尤其是倒计时）成为上下文

**要解决的问题**
日历上标了 11 月 30 日考试。但模型每一步都不知道"离考试还有 9 天"，仍然按平时的节奏慢条斯理讲知识点、顺着他的好奇心往外扩。他想要的顺序是"先补最可能丢分的、后讲拓展"——而这个顺序信息此刻只存在于日历里，没进模型的视野。

**做成什么插件**
`@lh/exam-context`，**preset 行**。不注册新工具，只**扩展 `lh:agenda` 这个上下文**。
两种实现路线：
- 路线 1（干净）：`@lh/schedule` 对外暴露一个"agenda 文本片段"接缝，本插件往片段里追加自己的段落。**这需要动 `@lh/schedule` 的代码**（新增一个接缝，与"宿主接缝要尽量少"的立场一致——这是 LH 内部接缝，代价小）。
- 路线 2（不动别人）：本插件自己再读一遍事件日志，注册**第二个**运行时上下文（比如 order 118.5 或紧随其后）。代价是重复投影。
若走路线 2，必须先验证两个上下文能否共存并按 order 都注入——**未验证**。

注入文本示例（保持两行内）：`距考试（2026-11-30 行测）9 天；本周已排 6 小时、已完成 2 小时；今天还有 2 项未完成。`

**数据从哪来**
**纯投影**：`kind = 'exam' | 'deadline'` 的日程项 + 已完成项的 `minutes_actual` 汇总。倒计时是派生量，不新增事件。

**与既有插件的关系**
不动 `@lh/schedule` 的投影与四个工具（除非采纳路线 1 的接缝）；与 `@lh/course-tree` 的 `lh:course`（order 117）并列不冲突。

**最小验证方式**
建一条 `day = 明天`、`kind = 'exam'` 的日程，开新会话，检查系统提示词里出现倒计时且数字正确；再跨一次午夜（把系统时间或 `day` 改成昨天）确认不会出现"距考试 -1 天"这种输出。

**风险/代价**
- 每步都注入 = 每步都花 token。文本必须压到一两行，且要有上限（比如只在 30 天内的考试才注入）。
- `exam`（考试）与 `deadline`（截止）语义相近，混用会让倒计时含糊：建议文案里区分"距考试"与"距截止"。
- 如果 `@lh/schedule` 的 `lh:agenda` 是"独占 order 118 且整体覆盖"的形态，路线 2 会失败。**未验证**：先开第二个上下文实测，再决定路线。
- 倒计时会让模型倾向于"催"（"离考试只有 9 天了，建议你…"）。这是概率性副作用，靠提示词约束不可靠——真正能做的是**只注入事实，不注入指令**（"距考试 9 天"是事实，"要抓紧"是指令，不要写进上下文文本）。

## 7. `@lh/calendar-export`：数据出口（.ics 导出，本地优先）

**要解决的问题**
他的日程只有 LH 知道。出门在手机上、或者要把它和公司日历里的会议排开时，他看不到自己的学习安排。他要么凭记忆，要么干脆不在 LH 排了——**数据出不去，入口就留不住**。

**做成什么插件**
`@lh/calendar-export`，**profile 行**：界面一个导出按钮 + 一条只读路由 `/lh/schedule/export.ics?from=&to=`。
可选 **preset 行**：给模型一个 `export_schedule(range, format)` 工具，让它直接把 `.ics` 文本贴出来（他复制粘贴到别处）。默认**只导出，不同步**。

**数据从哪来**
**纯投影**：`lh/schedule/*` → `VEVENT`；`lh/course/*` → `CATEGORIES`（课程名）；`kind = 'exam'` → 附 `VALARM`。不新增事件族。

**与既有插件的关系**
不改 `@lh/schedule` 的任何事件或字段；只读；不动宿主。

**最小验证方式**
导出一周 `.ics`，过一遍 iCalendar 校验器（或直接导入 Google Calendar / Outlook 各一次），确认：① 时区正确（不要所有事件差 8 小时）；② `cancelled` 的项**不出现**；③ 课程名作为分类可见；④ 中文标题不乱码。

**风险/代价**
- **双向同步风险最大，建议长期不做**。一旦允许外部日历回写，就出现第二个事实源，直接违反"事件溯源唯一事实源"。可接受的中间态是"外部日历只读订阅 LH 导出的 feed"，而不是双向。
- `.ics` 里带课程名、题目范围、考试日期 = **学习隐私**。路由必须只绑本机（127.0.0.1）、不可被公网订阅、URL 里不要放可猜测的长期 token。这一点比功能重要。
- ICS 的 `RRULE` 与本设计"每次 `create` 一条日程项"的形态不匹配：重复安排要么导出成 N 条 `VEVENT`（文件变大但语义直白），要么等第 8 条那个"规律"层。建议第一版选前者。
- 已知缺口：写路由没有会话上下文（`ARCHITECTURE.md` 开放问题 3）。导出是只读路由，不受影响——这也是它适合先做 profile 行的原因。

## 8. `@lh/schedule-routine`：例程模板（把"每周一三五"铺成条目）

**要解决的问题**
他每周一三五晚 20:00 学资料分析 40 分钟。要手工建 12 周 = 36 条日程，建到第四周就烦了，于是他的计划永远只有未来两周——恰好是"永远在重新开始"的形状。

**做成什么插件**
`@lh/schedule-routine`，**preset 行**（工具）+ **profile 行**（一个"铺排"按钮，复用与 `@lh/schedule-ui` 写路由同一份 commands，保证界面与 agent 字节同形）。
工具：`apply_routine(routine, weeks)`（幂等展开）、`list_routines()`。

**数据从哪来**
**需新增**一个 `lh/schedule/routine` 事件族：`data: { routine_id, title, kind, course_id, weekdays[], start, end, minutes_planned, from, to }`。理由：「这是一条规律」本身是发生过的事实，且"规律改了"要能回放。
展开出的具体条目仍走 `lh/schedule/created`——**这里有一个真正的设计岔口**：展开出的 36 条算事实还是派生量？
- 方案 A（本文倾向）：**也算事实**。因为"取消其中某一次"是有意义的动作，取消必须能表达在日志里。
- 方案 B：routine 是事实、展开是投影（日历时算）。省日志、天然幂等，但"取消一次"就无处安放，只能退化成"例外表"——复杂度反而更高。
选 A 就必须做**防重**：同一 routine、同一天只能展开一次。

**与既有插件的关系**
**必须与宿主「自动化任务」划清边界**：宿主负责"到点推一条消息"，本插件负责"把规律铺成日历上看得见的条目"。两者可以同时存在（他会想要两者都有），但 UI 上不要混为一个按钮，否则他会以为"铺排了就会响"。
其余复用 `@lh/schedule` commands，不动课程树。

**最小验证方式**
建"周一三五 20:00–20:40 资料分析"、铺 2 周 = 应生成 6 条；手动 `cancel` 其中一条后**重跑同一铺排**，检查那条**不会被复活**、其余也不会重复（幂等/防重）。再跑一次"把 weekdays 从 3 天改成 2 天"，确认旧条目是否该清理——**建议不清理**，改为记录 `updated`，让日历如实显示"这条曾经属于旧规律"。

**风险/代价**
- 一次操作写 36 条事件，日志体积与 UI 噪音都会上去。存储不是约束（ADR-014：单学者一年约 58 MB），但**界面可读性**是约束。
- 防重逻辑有 bug 时日历会变乱——好消息是**可见失败**，他会立刻发现（这比静默错位好，ADR-020 的教训是反过来的）。
- 与第 4 条叠加时：铺出来的条目会把"计划总量"推高，`plan-diagnosis` 必须能区分"routine 展开项"与"手工安排项"，否则诊断会把例程当成他的野心。

## 9. 取舍建议

**如果只做一条：做第 2 条 `@lh/plan-reconcile`。**

理由有三条，都不是"因为它简单"：
1. **它是唯一一条不依赖任何未实测宿主行为的建议**——纯投影，只读 `lh/schedule/*` 与 `lh/trace/observed`，写入也走既有 commands。哪怕宿主接缝明天变了，它坏的方式也是"少显示几行"，不是"起不来"。
2. **其他建议的价值都建立在"计划 vs 实际有对账口径"之上**：`plan-diagnosis` 是对账结果的聚合，`time-budget` 需要知道"排了但没做"才算得出真实负担，`review-scheduler` 的复习量也要靠"实际做了多少"来校准。没有对账，日历只是一堆意图；有了对账，日历才开始是**索引**。
3. 它与本项目的立场（显化而非评判、事实归内核、事件溯源）同向，且**天然会暴露第 4 条要防的那个诱惑**——做到"只说没有观察到活动"这一句，就等于把 §3.1 落成了代码。它的文案本身就是一次立场测试。

次选是第 1 条 `@lh/review-scheduler`——如果他的真实痛点确实是"不知道今天该复习什么"而不是"计划落不了地"。但它依赖 `ts-fsrs` 参数与作答数据的成熟度，属于"数据够了再做"的类型（ADR-017/019 已经表达过同样的克制）。

**哪些建议依赖未实测的宿主行为（必须先验证再动工）**

| 建议 | 依赖的未验证行为 | 先验证什么（都是小实验） |
|---|---|---|
| 5 `reminder-bridge` | preset 作用域能否直接触发宿主工具调用 / 拿到调度服务（ADR-014 只实测了 `ctx.llm`/`systemPrompt`/`tools`/`sessions`） | 写一个 20 行插件，在 `apply()` 里打印 `ctx` 上可见的服务键名（**不许抛错**，ADR-025），看有没有调度相关的键 |
| 5 `reminder-bridge` | 宿主自动化任务的工具 schema 与到期投递时机 | 手工建一条 3 分钟后到期的任务，看它是否以 user 消息到达、晚到多少 |
| 6 `exam-context` | 两个运行时上下文能否共存并都注入（order 117 / 118 的叠加语义） | 注册第二个上下文，开一次会话 `read` 系统提示词，看两段是否都在 |
| 6 `exam-context` | `@lh/schedule` 的 `lh:agenda` 是否独占 order 118 | 读 `@lh/schedule` 的注入实现（一处分叉，代码里就能看出） |
| 7 `calendar-export` | 只读路由实际绑定的地址/端口，是否真的只本机可达 | 从另一台设备 `curl` 一次；本机 `netstat` 看绑定 |
| 8 `schedule-routine` | 投影在几百条日程下的耗时（影响日历首屏） | 造 300 条日程的日志，量一次投影耗时 |
| 1 `review-scheduler` | `lh/user/attempt` 的真实字段（是否含可用题目 id 与时间） | `read` 一条真实事件；不够就先补字段 |
| 2 `plan-reconcile` | `lh/schedule/updated` 是"每次改一条"而非覆盖式写入 | 改同一条日程两次，数事件条数 |
| 4 `plan-diagnosis` | 同上（改期次数可数） | 同上 |

**落地顺序建议**（按"风险低 + 立刻改变他的使用体验"排）：
`plan-reconcile` → `exam-context` 或 `time-budget`（都是纯投影，看他要不要倒计时）→ `review-scheduler`（等作答数据）→ `reminder-bridge`（**先做完上表的两项宿主验证**）→ `calendar-export` → `plan-diagnosis` → `schedule-routine`。

**一句话总结**：日程插件的护城河不在"能排日程"（宿主自己的提醒插件已经能做一半），而在**排出来的日程会被证据校正**——所以先做能看见"计划 vs 实际"的那一条，其余的才有意义。

## 10. 核验补记（2026-10-09，落地当天补）

上面那张"依赖未实测宿主行为"的表里，有两条**当天就查清了**，从"待验证"改成"已核验"（依据见 `archive/decisions/037-学习日历与日程.md`）：

| 原待验证项 | 结论 | 依据 |
|---|---|---|
| 第 4 / 2 条：`lh/schedule/updated` 是"每次改一条"还是覆盖式写入 | **是逐次 append-only**。`commands.js` 的补丁只写**真的变了的键**，一次 `update_schedule` 可能写 0~3 条事件（`updated` / `linked` / `done`），且 `changed` 为空时**一条都不写**。所以"这条计划被推迟过几次"有数据源（`history` + 多条 `updated`），第 4 条 `plan-diagnosis` 的前提成立。 | `plugins/lh-schedule/commands.js` 的 `applySchedulePatch` |
| 第 6 条：两个运行时上下文能否共存（`lh:course` order 117 与 `lh:agenda` order 118） | **能共存**。`systemPrompt` 服务的 `context()` 是"ordered dynamic context"，组装结果 `PromptAssembly.contexts` 是一个**数组**；契约原文是"scoped entries shadow global entries **with the same name**"——**只有同名才遮蔽**，不同名会一起进 prompt。所以 `exam-context` 不必去动 `@lh/schedule` 的代码：**另起一个不同名的上下文即可**（路线 2 成立，路线 1 那处"开接缝"的必要性下降）。 | Cordis Inspect `systemPrompt` 服务契约（`PromptAssembly` / `PromptContext`），属 `[宿主源码]` |

另外两条与本文相关的**已核验事实**（写在这里免得下次再查）：

- 宿主「自动化任务」那个 bundle（`@deepseek-ai/dsh-experimental-schedule-bundle`）在本机是 **enabled: false**——所以宿主那四个 `schedule_*` 工具现在**根本没注册**，"重名冲突"暂时不是风险，但边界仍要守着（哪天作者打开它就会有冲突）。
- `@lh/schedule` 的 `lh:agenda` **不是独占**的：order 只是一个排序数值，多个上下文可以共用或紧邻（同名才遮蔽）。第 1 条 `review-scheduler` 因此不需要新增上下文——日程一旦写进去，`lh:agenda` 本来就会把今天的复习时段告诉模型。
