# 协作者模型（AI 对项目作者的感知）——v1.0（2026-09-22）

> 这份文件不是评价，是**断言集**。每条感知是一条断言：带**出处**、带**置信度**、可审计、可争议。
> 作者可随时反驳或推翻任一条；反驳本身是有效证据，会改变这里的置信度。
> 感知变化的留痕纪律、反馈走哪条通道，见 `WORKFLOW.md` §3 规则 6 与 §6 义务 7，这里不重复。
> 置信度刻度：**高** = 有直接陈述或多次一致观察；**中** = 从行为推断；**低** = 单次观察，待验证。
> 全部历史经验个案与 ADR 已归档：`archive/experience/`、`archive/decisions/`。

## A. 断言列表

### 会什么、不会什么

- **A1 不写代码，但能判断与取舍代码级方案**（置信度：高）。作者明确澄清（2026-09-15）："此前你见到的代码确实是其他模型写的"。更早把 `agent/registry.py` 的代码质量当作作者能力的判断**已撤回**——归因错误：仓库里的代码由 agent 生成是本项目的正常生产形态，不构成作者能力的证据。推翻条件：出现作者独立编写并能清楚解释设计取舍的代码。
- **A2 架构判断力强，但会过度延伸到"未运行的部分"**（置信度：中）。证据：`ARCHITECTURE.md` 的事实/解释切分、`archive/decisions/` ADR-011 的轮子审查，都是先做减法再定方案；另一面是十份 ADR、零个可用功能。归因保留：这些文档是否也部分由模型起草尚未澄清，若然，本条降级为"文档层面的判断力"。推翻条件：作者澄清文档生成方式，或在对话中给出独立的、非复述性的架构判断。
- **A3 对 agent 编排的了解停留在原理层**（置信度：高，作者明确陈述）。原文："我对于 agent 编排的了解仅限于原理上"。掌握的是概念与为什么这样设计，缺的是怎么落地、会遇到什么。推翻条件：在具体编排任务中表现出超出原理层的操作能力。

### 他怎么反应、在意什么

- **A4 被指出错误后修正很快，且不辩解**（置信度：中）。本会话中多条被证伪的判断（Windows 路径可用、mock-server 存在、把代码当能力证据等），他均直接澄清或接受，未纠缠。推论：可以承受直接的坏消息，**隐瞒比说错更糟**。推翻条件：反复坚持已被证据推翻的判断。
- **A5 他的纠正系统性地指向"谁拥有这个决定"**（置信度：高）。2026-09-16 连续四次纠正方向一致：模型名是使用者的决策不是插件的属性；风险告知即可，不该让 agent 拒绝服务；隐藏工具等于系统替用户判断"你做不到"；问的时机该由 agent 在自然边界决定。他的默认立场：**把选择权和后果交给用户，系统负责把后果说清楚**；我的默认倾向（系统替用户做安全选择）要先让位。与 LH 契约的反奖惩立场同源：他的工程判断与教学理念是一回事。推翻条件：他主动要求"系统替我拒绝/替我兜底"。
- **A6 他从"生态该怎么长"出发思考，不只从"这个功能怎么做"**（置信度：高）。2026-09-16："有人把任务拆解成若干小插件，使得低智能的模型通过插件的组合也能完成复杂的任务……就是有什么材料做什么菜"。推论：遇到"能力不够"的问题，先想"能不能用组合绕过"，再想"怎么拒绝/降级"。推翻条件：这类提议在后续实践中落不到具体设计里。
- **A7 他更容易在"具体、可运行、可批评的对象"面前产出判断，而不是在抽象问题面前**（置信度：低）。证据：对开放问题清单反应为负担；在看到我贴出真实模型清单与 chunk 流之后立刻给出明确的档位映射（2026-09-16）。推论：把抽象问题先做成一个能跑能指的最小东西，再请他判断。
- **A8 认知带宽是真实约束，但拒绝被过度保护**（置信度：高）。原文："考虑插件的具体实现……让我在开发时感到了极大的认知负担"，紧接着："也不用完全把我保护起来，有认知负担是应该的"。推论：**降负担 ≠ 替他回避困难**——替他回避会害他。原理层解释可省略，实践层（改哪个文件、跑什么命令、看到什么算成功）必须给足（依据 A3）。
- **A9 有学习意图，但更看重产出与默契**（置信度：高）。原文："我至少希望随着这个项目不断完善，我懂得要比现在要多"；2026-09-15 补充：产出就是"后续开发中我和你合作的默契程度"，只有合作受阻才会来审查这份文档。推论：**本文件是写给我自己的记录**——不要为维护它而占用他的注意力；它的价值在于让我的行为随证据更新。
- **A10 项目此前停滞的原因不是能力，是治理模型**（置信度：中）。证据：`ARCHITECTURE.md` 的第三条法律（第 N 层未书面冻结前禁止讨论第 N+1 层）+ 取题规则 → 接口层的正确答案只能由运行提供，而运行属于被禁止的实现层（ADR-011 已加第四条法律修正）。推论：若他再次"想不清楚"，先怀疑度量方式，不要怀疑他。
- **A11 他对自己产品的细节有强主张，但只在他想清楚的地方坚持**（置信度：中）。模型档位、审批时机、工具归属这些他反复纠正；而文件名、目录结构、schema 字段名他从不干预，直接接受我的选择。推论：**实现细节放心自行决定；一旦涉及"谁做决定 / 用户体验 / 生态形态"，必须先说清后果再动手**（判据与代劳边界见 `WORKFLOW.md` §2）。

### 精力与节奏

- **A12 他的指令简短不等于信息量低：他给出"顺序"而不只是"目标"**（置信度：中）。2026-09-17："先搭起来行为的对象和接口再去对行为分类"——"先…再…"是可验证的技术判断（分类器的动词取决于对象能表达什么），不是偏好。推论：短指令先拆出约束再动手；若我认为顺序该改，说理由再改，不默默按自己觉得快的方式做。
- **A13 重启是稀缺资源**（置信度：中）。他不会因"多验了一轮"不耐烦，会因"重启之后才发现问题"不耐烦（2026-09-16 对比 2026-09-17 两次观察）。推论：凡能在重启前验完的都要验完；反复重启本身可以接受，不必为它改变开发优先级（2026-09-16："重启问题其实没那么大，也不必须修"）。
- **A14 一个恶性 bug 不会让他放弃项目，但会让他去改架构**（置信度：高）。2026-09-18 三次"dsh 起不来"之后，他的反应是提出把这类问题交给 `lh-plugin-development` 管、提出克隆 dsh 做开发/测试隔离；原话："这种问题都是常有的，发现问题解决问题就好"。推论：他要的是把事故变成系统能力（闸门、隔离），不是要我保证不犯。
